# 范本 — 写出这样能读下去的文章

`src/content/blog/zh/amazon-kiro-spec-driven-ai-ide-vs-claude-code-2026.md` 是这个博客想要的专栏。八个 H2。下面是它的骨架。

**要偷的是呼吸和表态的方式。要丢的是排版。** 那篇的 `---` 分隔线，以及四种语言共用的 H2 顺序，现在都违反约定并且会让构建失败。

---

## 开头 — 两段

第一段用**带日期的事件**，或者**你真的被问过的问题**切进去。

> AI 编程工具市场来了新玩家。Amazon 在 2025 年 7 月公开的 Kiro 不是又一个 AI 自动补全，而是一个建立在「写代码之前先写规格」这个想法上的 IDE。作为每天用 Claude Code 的人，我想搞清楚这件事在实际使用中意味着什么。

第二段**先给结论**。这是给读者继续读下去的理由，不是摘要。

> 先说结论。Kiro 和 Claude Code 不是直接竞争关系，它们在解不同的问题。但如果搞不清这个差别，两个都会用错。

原文第三段有一句告知，说这是 Source Review 分析、没跑过的功能不会写成跑过。**这一段不写。** 没做过的事不写成做过就够了，每次都挂的告知本身就成了模板。

## 正文 — 九选六到八

| 板块 | 做什么 |
|---|---|
| 事实梳理 | 变了什么。写短 |
| 机制与结构 | 为什么会这样。目录树和代码块放这里 |
| 数字核对 | 跑分说了什么，没说什么 |
| 成本 | 价格、配额、时间。表格唯一合适的地方 |
| 对比轴 | 和现在用的东西差在哪。三到四轴 |
| **明确的反方** | 拿出一整节写反对意见。必须有 |
| 能不能落地 | 自己上手会卡在哪 |
| 适合谁 | 适合 / 不适合，成对写 |
| 限制 | 可选 |

**顺序你自己定。** 四个以下太浅，九个全上就成目录了。挑一个和其他语言不重合的顺序 — 四种语言用同一个顺序，构建会失败。

对比轴是这个样子。立一个轴名，两边各一段。

> **速度和灵活性。** Claude Code 不走规格步骤，直接执行。小 bug、快速重构、探索性的活儿，它快得多。Kiro 生成规格是有价值的，但要花时间。十分钟能改完的东西先写规格，那就是额外开销。

## 收尾 — 不带 H2 的三拍

最后一个 H2 之后，接两三段没有标题的文字。

**把立场说死。** 不往中立躲。按条件二分。

> 我的判断是这样。如果是几个人一起设计新功能，Kiro 合适。如果大部分时间是一个人快速修东西，规格那一步就只是开销。

**再说一次边界。** 这不是辩解，是标范围。

> 等我有能真正上手的环境，会另外写。公开资料能比较的东西，和用过之后才能说的东西，是两回事。

**用一个超出主题的观察结尾。** 不是总结，也不是教训。

> 有意思的是 Amazon 把 Claude 授权进来驱动 Kiro。他们在 AWS 的基础设施上做了一个跑 Anthropic 模型的 IDE。这与其说是竞争，不如说是不同层上的合作。
