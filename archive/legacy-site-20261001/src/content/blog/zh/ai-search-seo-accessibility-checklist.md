如果需要修改资费说明页面，让它更容易出现在 AI 搜索中，应该先检查什么？在修改页面标题或添加结构化数据之前，应先确认搜索系统能否抓取该页面，以及正文是否准确表达了资费条件。因为页面在搜索中无法展示与回答中价格传达错误，可能有不同的原因，需要修改的位置也可能不同。

本文中的 AIO 指的是改善内容在 AI 搜索中的可发现性和使用准确性的工作。AIO 有时也被用作 Google AI Overviews 的缩写，但这里并非仅指该功能。不过，有关搜索工作原理的说明以 Google 为基准，而操作浏览器的智能体的可用性则与搜索回答分开讨论。

## 为什么 AI 搜索仍然需要 SEO

Google 的 AI 搜索基于现有的搜索索引以及排名和质量系统查找相关文档。以找到的资料为依据组织回答的方式，就是检索增强生成，即 RAG。根据问题的不同，还会使用 query fan-out，将问题扩展为多个相关查询并行搜索。例如，要回答比较资费方案的问题，可能不仅需要查找价格，还需要查找合同期限或服务范围的资料。

在这个过程中，生成回答之前需要的是可作为依据的文档。如果无法发现页面，或者抓取和索引存在问题，该文档就很难被搜索利用。即使已经抓取，如果标题和正文没有明确说明页面在介绍什么，也会缺少判断其与问题相关性所需的信息。这就是 SEO 中围绕发现、抓取、索引和信息理解开展的工作，在 AI 搜索中仍然必要的原因。

开始应对 AI 搜索时，也应先检查现有页面的抓取状态和内容。Google 的说明指出，无须为 AI 添加特殊标记，也无须强行将内容拆成小块。独立的 AI 文件或专用 schema 也不是必备条件，因此不能根据是否存在 `llms.txt` 来判断 Google AI 搜索的准备情况。

实际工作中还需要检查找到文档之后的信息传达。如果价格数字读取正确，却遗漏了合同条件，仅解决索引问题并不足够。需要将实际传递的内容与基于这些内容生成的回答进行对照。

## 为什么要在 HTML 中表达标题、标签和资费条件

设想一个虚构的服务资费说明页面。屏幕上，“个人方案”下方醒目地显示着“9,900 韩元”，卡片底部则用小字写着“以年度合同为准，每位用户的月均折算金额，含增值税”。即使人能理解这些内容属于同一张卡片，如果仅通过字号和布局表达关系，在以其他方式读取页面时，这种关系也可能无法充分传达。

网页无障碍要求通过文档结构表达这类关系。标题使用标题元素，输入框提供与之关联的标签。如果是资费对比表，则需要将行标题和列标题与数据单元格关联起来。使用辅助技术的人可以利用这种结构浏览内容、理解各项的含义，而不必依赖屏幕布局。

以下是一段明确表达资费与条件关系的 HTML。资费、日期和功能均为说明而作的假设，并非在实际服务中测得的改进结果。
```html
<section aria-labelledby="personal-plan">
  <h2 id="personal-plan">个人方案</h2>
  <p>签订年度合同时，每位用户的月均折算金额为 9,900 韩元。
    含增值税，12 个月的费用一次性支付。</p>
  <p>此资费自 2026 年 9 月 1 日起适用。</p>
  <form action="/estimate" method="get">
    <label for="seats">个人方案使用人数</label>
    <input id="seats" name="seats" type="number" min="1" value="1">
    <button type="submit">查看支付金额</button>
  </form>
</section>
```
标题和标签向辅助技术传达结构和输入目的。将价格连同适用对象、单位和条件写入正文，也让提取文本后更容易确认其含义。SEO、无障碍和 AI 搜索相关工作之所以存在部分重叠，是因为它们都在改善同一份内容及其 HTML 表达，而不是因为无障碍检查分数会作为加分项计入搜索排名。

如果用户将资费计算交给 AI，还需要检查页面操作。这时，浏览器智能体会打开页面、输入人数并查看支付金额。智能体可能根据实现方式使用截图、HTML·DOM 或无障碍树。使用无障碍树时，元素的角色、名称和状态就是识别操作对象的信息。上例中关联的标签和原生按钮，也能通过这种路径传达含义。

这并不意味着所有 LLM 都会读取无障碍树。检查搜索回答时，应核对抓取的文档和回答；如果要支持浏览器智能体，则需要确认该智能体使用的输入以及实际操作结果。

## 不只看屏幕，还要确认实际抓取路径

不能仅凭浏览器中能看到价格，就排除抓取问题。服务器最初返回的 HTML 中可能只有空白区域，价格要在 JavaScript 执行后才出现。登录状态、所选结算周期、地区设置等导致页面内容变化的情况，也应纳入检查条件。

首先保存响应头和初始 HTML，再单独获取浏览器渲染后的 DOM。通过 `curl` 等 HTTP 客户端获取的响应，并不等同于 JavaScript 执行后的文档。同时记录最终 HTTP 状态、重定向、身份验证要求和 CDN 访问限制，有助于确认正文在哪个阶段缺失。不直接使用开发工具的负责人，可以先从要求分别提供这些资料开始。

公开页面的初始响应可以按以下方式保存。将示例地址替换为待检查的 URL 后，响应头会保存到 `headers.txt`，HTML 会保存到 `page.html`。
```sh
curl --fail --show-error --location --max-time 30 \
  --dump-header headers.txt \
  'https://example.com/service/' --output page.html
```
Google 提供会渲染 JavaScript 的搜索抓取路径，因此不能仅因初始 HTML 中没有正文，就断定 Google 无法读取。反过来，也不能因为普通浏览器中能看到内容，就假定其他抓取路径接收到的也是相同内容。

检查时，应将原始响应、渲染后的 DOM 和提取的文本联系起来查看。如果虚构资费页面的初始 HTML 中有价格，但年度合同条件只在渲染后出现，那么仅读取初始 HTML 的路径所获取的信息就不完整。如果 DOM 中有条件，但提取的文本中遗漏了条件，还需要检查提取方式。如果无法确认目标服务实际收到的内容，就不应将本地获取的资料认定为该服务的输入，而应记录尚未确认的范围。

访问策略也需要结合意图判断。希望在搜索中展示的公开页面被误拦截，与有意限制非公开内容，对应的处理方式不同。不应将用于训练的访问、用于搜索的抓取和按用户请求进行的访问视为相同目的，而应记录对象和允许范围。为了在 AI 搜索中展示而解除所有限制，并不是合适的做法。

## 区分代码、LLM 和人工各自需要确认的内容

代码适合先确认规则明确的事实。例如，可以提取响应状态、标题元素、标签关联、`alt` 属性是否存在，以及 JSON 是否解析成功。不过，观测结果与错误判定并不相同。不能仅凭存在多个 `h1` 就认定会受到搜索扣分或违反无障碍要求；如果应用了团队的编写规则，应标明这是依据该规则作出的判定。

结构化数据也要将语法和事实分开检查。即使 JSON 有效，价格仍可能过时，或者合同条件与正文不同。如果虚构页面的正文说明的是年度合同价格，而 JSON-LD 中却将其记录为不附带条件的月费，就需要对照这两种表达。对于结构化数据，应检查所采用类型的要求，以及其与可见内容是否一致，而不是因为页面没有 JSON-LD 就一律判为错误。

可以让 LLM 比较这些值并审查上下文。例如，检查“月均折算”是否可能被误解为实际按月支付的价格、提取过程中是否遗漏了条件，以及回答是否添加了正文中没有的内容。结果应包含规则 ID、原文位置、比较的值和判断理由。仅有“说明含糊”这样的意见，很难决定具体应修改什么。

输入的局限也应反映在判定中。如果只提供了 HTML 而没有图片，就无法确定替代文本是否充分说明了实际图片的信息。也不应将可能适用于装饰性图片的空 `alt` 一律视为错误。如果没有提供响应头，就应将响应头策略保留为“无法确认”。

最终，事实和操作行为需要由人工确认。内容负责人依据实际资费政策确定标准答案；可用性审查则检查键盘操作、焦点移动、错误提示和屏幕对比度等。智能体点击了按钮，并不能证明页面对使用键盘的人同样可用。应结合自动化与人工审查，同时保留每项结果实际确认的范围。

## 在代表性页面上检查并比较修改前后的顺序

与其一开始就强制全站采用统一的句式，不如先选择一个包含会影响用户判断的信息的代表性页面。如果是资费说明，应优先检查价格和合同条件，再扩展检查使用相同模板的其他页面是否也存在已发现的问题。

1. **准备经人工确认的基准事实和问题。** 在虚构页面中，将个人方案、每位用户月均折算 9,900 韩元、年度合同、预付 12 个月费用、含增值税和生效日期，与原文位置关联起来。对于“只用一个月也是 9,900 韩元吗？”这一问题，需要说明这是年度合同下的月均折算金额，不能编造页面未说明的按月支付价格。

2. **固定抓取条件并保存输入。** 记录 URL、抓取时间、是否经过身份验证以及所选资费选项。将初始 HTML 和渲染后的 DOM 分别保存，并记录文本提取所用的工具和设置。如果只向 LLM 提供了 URL，就需要确认它是否实际访问，以及读取了哪些范围；无法确认这些情况的结果，应与基于已获取 HTML 的审查结果区分开来。

3. **整理自动检查结果，再审查语义和操作行为。** 将 HTML、无障碍和结构化数据的检查结果与规则 ID 关联。如果正文和 JSON-LD 中的价格不同，应同时记录两个值及其单位。将 LLM 指出的问题与原文对照，并由人工在实际页面上检查输入框、按钮、键盘焦点和提示文案。

4. **在相同条件下比较修改前后。** 使用相同的模型、问题、提示词、提取方式和输入类型。如果修改前提供初始 HTML，修改后提供渲染后的 DOM，就很难区分内容修改与输入路径变化各自的影响。记录能够获取的运行设置和模型标识信息，并保存相同条件下重复运行的结果。

5. **部署后的搜索结果单独观测。** 将受控的提取实验与实际 AI 搜索是否引用分别记录。检查实际搜索时，记录服务及其功能、问题、检查时间，以及回答中显示的来源 URL。即使用 Bing 的 AI Performance 这类展示引用次数和来源 URL 的工具，也应在该工具能够观测的范围内解释结果。

回答评估应以必要事实是否得到保留为准，而不是只看语句是否自然。即使价格数字正确，如果遗漏了按用户收费的条件或年度合同，也不能视为准确回答。应区分原文中存在但被遗漏的事实、被错误理解的事实，以及文档中没有却被编造的事实。如果同时加入询问页面未提供的信息的问题，例如提前解约的退款比例，还可以确认模型是否会承认信息缺失。

## 页面检查清单

可以将以下清单复制到工作文档中，逐页使用。勾选表示该项审查已经完成。结果另行记录为“未发现问题、需要修改、需要审查、不适用、无法确认”中的一项，并保留依据。对于“不适用”或“无法确认”，应同时注明原因。

条目旁的**自动**表示由脚本或检查工具确认的部分，**LLM** 表示提供资料后进行语义审查的部分，**人工**表示确认运营意图或页面显示与操作行为的部分。实际检查使用前文介绍的工具和流程。标有多种方式的条目，需要同时审视各方式负责的范围。“优先”是首次检查时的建议，并非标准中的严重程度等级。

### 访问与主题

- [ ] **A1. 符合公开意图的 URL 访问**（自动 · 人工 · 优先）

  记录最终 HTTP 状态、重定向、身份验证和 CDN 限制，并与公开意图比较。依据非公开策略设置的限制，不视为失败。

- [ ] **A2. title 与主要标题的主题一致**（自动 · LLM · 优先）

  提取元素是否存在及其当前值，再审查它们是否说明同一主题。不能仅因没有共同词语就判定不一致。

- [ ] **A3. 准确概括正文核心内容的 description**（自动 · LLM）

  记录是否缺失及其长度，并通过阅读确认是否准确说明正文核心内容。不将特定字数作为搜索展示的绝对标准。

- [ ] **A4. 符合页面意图的 canonical·lang·viewport**（自动 · 人工）

  确认规范 URL、实际语言和移动端显示设置。不能仅凭标签存在，就判断其值也正确。

- [ ] **A5. 符合公开策略的 robots 元标记与响应头**（自动 · 人工 · 优先）

  检查 noindex·nosnippet·max-snippet 和 X-Robots-Tag，并与公开策略比较。不自动解除有意设置的限制。

### 结构化数据

- [ ] **B1. 根据页面目的选择结构化数据**（自动 · 人工）

  记录页面需要的功能和采用的规范。不能仅因没有 JSON-LD，就将所有页面判为失败。

- [ ] **B2. JSON-LD 语法有效且满足所采用类型的必需项**（自动 · 优先）

  记录解析结果、@context·@type 以及该类型的必需属性。不使用 JSON-LD 的页面标记为“不适用”。

- [ ] **B3. 可见内容与结构化数据中的事实一致**（自动 · LLM · 优先）

  将标题、日期、价格等的表示方式和单位归一化后，比较其值和来源。区分措辞是否完全相同与事实是否一致。

- [ ] **B4. 类型和说明反映页面的实际目的**（LLM · 人工）

  审查类型和说明是否符合页面目的，不随意添加无关类型或不可见的事实。不能仅因页面上没有显示日期，就断定存在篡改。

- [ ] **B5. 重复信息的管理来源与修改责任**（自动 · 人工）

  记录信息在 CMS、静态 HTML 或通用模板中的生成位置，以及负责修改的人员。不能仅因多种格式中存在重复信息，就声称会受到搜索扣分。

### 文档与内容

- [ ] **C1. 说明文档层级的主要标题和子标题**（自动 · LLM · 优先）

  检查 h1 数量、标题级别，以及视觉标题所使用的标记。根据上下文和团队的编写规则，判断检测到的模式是否适当。

- [ ] **C2. 能从开头理解的页面目的**（LLM · 优先）

  检查是否能通过标题和首段说明服务、对象和目的。不假定理解所需的阅读时间是一个固定值。

- [ ] **C3. 用 HTML 表达列表、定义和数据表的关系**（自动 · LLM）

  对使用 br 罗列的内容，考虑采用合适的列表；对键与值的关系，考虑采用 dl 或表格。不强制所有内容使用相同标签。

- [ ] **C4. 可理解的表格标题及表头关联**（自动 · 人工）

  检查 caption 或等效上下文，以及 th·scope/headers 的关联。对于复杂表格，审查其关联方式是否符合该表格的结构。

- [ ] **C5. 重要数字同时保留对象、单位、条件和基准日期**（LLM · 优先）

  从价格、业绩和数量中，选出一旦被误解就会影响用户决定的事实，检查其上下文。对于上下文充分的固定事实，不要求添加不必要的日期。

- [ ] **C6. 机器与人能够按相同含义读取的日期**（自动 · LLM）

  如果使用了 time，检查 datetime 值是否有效，并与页面显示值比较。不要求所有日期都使用 time。

### 无障碍与信息传达

- [ ] **D1. 提供符合图片作用的 alt**（自动 · LLM · 优先）

  分别检查 alt 属性是否缺失，以及说明的质量。装饰性图片的空 alt 可能是合适的；如果未提供图片，则将说明的准确性标记为“无法确认”。

- [ ] **D2. 传达图片重要信息的文本**（LLM · 人工 · 优先）

  检查图表、价目表和说明图片中的数值与关系，是否也能通过文本理解。将页面上的图片与说明一起比较。

- [ ] **D3. 在上下文中明确的链接和按钮目的**（自动 · LLM · 优先）

  提取“这里”或“查看更多”等文案，作为审查候选项。不仅凭文案判定，而是同时检查无障碍名称和周围上下文。

- [ ] **D4. 确认主要功能的键盘操作和焦点**（自动 · 人工 · 优先）

  通过实际 Tab·Enter 操作，确认菜单、表单和对话框的行为及焦点。不以仅审查 HTML 文本的结果判定通过。

- [ ] **D5. 有助于使用的对比度、表单标签和错误提示**（自动 · 人工 · 优先）

  在自动无障碍检查结果的基础上，补充页面显示检查和实际操作审查。不将工具的通过结果解释为符合全部 WCAG 要求。

- [ ] **D6. 在目标抓取路径中能够确认的主要内容**（自动 · LLM · 优先）

  区分初始 HTML 与渲染后的文档，并比较标题、正文和核心事实。不将使用 JavaScript 本身作为失败原因。

### 网站运营

- [ ] **E1. 按服务和目的审查 robots.txt 策略**（自动 · 人工 · 优先）

  记录训练、搜索等目的，以及目标机器人、允许范围和负责人。不试图通过一律允许所有机器人来解决问题。

- [ ] **E2. 通过站点地图和内部链接发现主要公开 URL**（自动 · 人工）

  检查站点地图是否包含预期的规范 URL，并检查内部链接。不要求将非公开 URL 或重复 URL 也全部纳入。

- [ ] **E3. 内部链接与资源正常工作**（自动 · 人工）

  对照目录列表和实际链接，区分有意删除与误报。图片和 PDF 也要直接打开，确认其工作正常。

- [ ] **E4. 记录规则的适用范围和例外**（自动 · 人工）

  记录是新建网站还是已运营网站、检查版本和负责人。对于暂缓的项目，同时记录原因和复查日期。

### 提取评估

- [ ] **F1. 区分基准事实的提取与遗漏进行测量**（自动 · LLM · 人工）

  由人工确定标准答案后，固定模型、问题和提取条件进行评估。事实的对象、单位和基准日期也应纳入评分。

- [ ] **F2. 确认是否生成了文档中没有的事实**（自动 · LLM · 人工）

  询问文档中没有的信息，区分无依据的答案与承认无法得知的回答。在相同条件下重复测试，并将结果与实际引用成效分开解释。

### 检查结果的记录格式

对于发现问题的项目，同时记录位置、依据和下一步措施，便于修改负责人复核。自动检查或 LLM 指出的问题，应与原文和实际操作行为对照后再记录。不能仅凭勾选数量，判断是否符合全部无障碍要求，或是否会被 AI 搜索引用。
```text
检查 URL:
检查日期 / 负责人:
检查的资料: 初始 HTML / 渲染后 DOM / 页面画面 / 响应头等

项目 ID:
结果: 未发现问题 / 需要修改 / 需要审查 / 不适用 / 无法确认
确认的位置与原文、数值:
判断理由:
待修改内容 / 负责人:
修改后的确认方法:
```
## 请求 LLM 审查的提示词

```text

- 记录项目 ID、原文位置、证据、判断理由、修改建议和复查方法。
```

修改建议应分为事实错误、需要解释判断的问题，以及单纯的文风偏好进行审查。没有必要仅因一次提取失败，就在所有段落中重复价格和日期，或将内容按固定长度切成小块。应先确认是原文缺少条件、条件在传递过程中遗漏，还是输入中已有条件但模型理解错误，再针对相应原因修改。

## 在 CMS 和运营规则中修正反复出现的错误

如果代表性页面中发现的问题只在该文档上修改，之后仍可能再次出现相同错误。合同条件录入错误属于内容负责人的修改范围，但如果所有资费页面都只用图片输出条件，就需要检查模板。如果正文和 JSON-LD 引用了不同价格，应先追踪这两个值分别在哪里生成。

在 CMS 中，可以考虑不只录入金额，而是同时管理计费对象、单位、合同条件和是否含税。正文与结构化数据使用同一份数据，可以减少分别维护不同值的负担。但不应强迫每个页面填写不需要的字段。应区分需要生效日期的可变信息与不需要单独日期的说明，并根据实际内容政策确定必填项。

修改责任也应明确分配。内容负责人可以核实资费和条件的事实，开发负责人可以检查 HTML 结构以及渲染、提取问题，搜索与运营负责人可以检查索引和访问策略。提前确定发现问题后由谁核实内容、谁能够实际修改，有助于加快响应。同时记录为什么应优先审查向用户告知错误金额、阻碍主要功能使用或在多个页面上重复出现的问题。

运营规则中应记录依据、版本、适用范围和负责人。如果允许例外，应注明原因，以及复查时间或条件。如果受现有模板限制而难以立即修改，应记录该限制、临时应对措施和再次确认的时间安排。仅记录“因为是现有网站而排除”，会让后续负责人难以判断是否可以继续保留该例外。

可以将修改后的页面和曾经回答失败的问题保存为复查资料。当 CMS 模板、提取工具、模型或提示词发生变化时，使用相同资料再次确认，就能检查此前解决的错误是否复发。除了完成率，还记录误报导致的返工和部署后仍存在的缺陷，可以为根据实际运营情况调整检查规则提供依据。
