## 改设置之前，先确认报告究竟回答了什么

人工智能工具，也就是 AI 工具，生成了一份自动检查报告。报告写着“正常结束”。

同一份报告又写着“找到项目 0 个”。

你可能正准备根据它修改网站设置。

你也可能打算缩短交给 AI 阅读的文档。

但这两件事都先别急着做。

“正常结束”通常只说明某段处理走到了结尾。

它不一定说明工具拿到了正确资料。

它也不一定说明原来的问题已经有答案。

这次报告涉及 Google-Extended 和 Codex。

robots.txt 是网站公开提供的一份访问规则文件。

它告诉自动读取网页内容的程序应如何访问网站。

Google-Extended 是其中用于指定一组 Google 内容使用规则的名称。

Codex 是处理代码和项目文档的产品名称。

AGENTS.md 是放在项目中、供 Codex 阅读的说明文档。

这次实验想了解 Codex 如何处理较长的这类文档。

KiB 是文件大小的单位。

实验关注文档超过 32 KiB 后会发生什么。

报告中的关键问题并不是“程序有没有跑完”。

真正要问的是，这份报告有没有弄清楚两项具体行为。

一项是 Google-Extended 的控制范围。

另一项是 Codex 会截短文档，还是跳过整个文件。

因此，看到绿色状态或正常结束还不够。

还要检查输入资料是否正确。

也要检查结果是否能区分待验证的几种可能。

怎样区分表示执行正常结束的标志和真正能回答问题的证据？

## robots.txt 检查同时留下了空列表、HTTP 200 和命令错误

第一组实验读取了实际网站的 robots.txt。

正则表达式是一种按文字格式寻找内容的方法。

实验用它收集 robots.txt 中每个 User-agent 字段后面的名称。

这里的 User-agent 字段用来指定规则适用于哪些抓取程序。

实验先查找 Google、OpenAI 和 Anthropic 的专用名称。

解析结果只有通配名称 `*`。

通配名称表示规则没有按这些提供方单独列出。

token 在这份输出中指 robots.txt 里识别抓取方的名称。

这次解析只找到 `*`，没有找到 Google、OpenAI 或 Anthropic 的专用名称。

报告的完整输出是：

`All tokens: ['*'] / Google tokens: [] / OpenAI tokens: [] / Anthropic tokens: []`

其中，`[]` 表示列表为空。

这项解析的记录是 hits 0/3。

hits 0/3 表示 3次运行都没有找到目标内容。

它同时记录了 exit 0,0,0。

退出代码是命令结束时返回的状态数字。

exit 0 通常表示该命令没有报告执行失败。

但同一批日志也记录了命令错误。日志中的 bash 是执行文字命令的程序；command not found 表示它找不到指定命令：

`bash: Fetch: command not found / bash: Send: command not found (exit 0,0,0)`

这表示 Fetch 和 Send 被当成了待执行命令。

bash 没有找到这两个命令。

这样的错误在 3次执行中都出现了。

可是后面的处理仍产生了输出。

最终记录也仍然是 exit 0,0,0。

因此，有解析结果，不代表整个检查过程都有效。

实验还换了 6 个用户代理名称发送请求。用户代理名称是访问者向网站报出的身份名称。

它使用了 HEAD 和 GET 两种网页请求。

HEAD 只询问网页是否可用等信息，不取回网页内容。

GET 则请求取回网页内容。

结果如下：

HTTP 是浏览器等程序与网站交换请求和答复时使用的规则。

HTTP 200 是网站表示本次请求成功的状态码。

本次测试的 6 个名称都收到了这个状态码：

- Google-Extended
- Googlebot
- GPTBot
- ClaudeBot
- OAI-SearchBot
- Mozilla/5.0

这 6个名称都没有在响应层被拒绝。

这项检查同样记录为 hits 0/3。

不过，HTTP 200 不能证明 robots.txt 允许抓取。

它也不能证明真实抓取程序会遵守对应规则。

robots.txt 的规则与 HTTP 响应状态不是同一项判断。

前者需要有效规则和真实行为作为证据。

后者只说明这次请求收到了成功响应。

所以，这份报告包含了性质不同的记录。

一个记录说明没有找到专用名称。

一个记录说明请求收到 HTTP 200。

另一个记录说明执行中发生 command not found。

它们不能合并成“产品行为已确认”这一结论。

同一份报告中的空名称列表、成功响应和命令错误，需要分开看。

## 网站与保存库的 robots.txt 比较没有真正成立

下一项检查想比较两个 robots.txt。

一份来自实际网站。

另一份来自电脑上用 git 管理的项目文件集合。

git 是记录文件版本和修改历史的工具；它管理的文件集合叫保存库。

这项比较没有产生可用的对照结果。

报告中的原始记录是：

`live_vs_git_robots — hits=0/3 usable=0/3 — exit 1,1,1`

usable_runs 表示能继续用于判断问题的运行次数。

usable=0/3 表示 3次运行都不能用于最终判断。

exit 1,1,1 表示 3次比较都以失败状态结束。

因此，这次检查没能有效比较网站和仓库中的文件。

失败过程中仍留下了两个文件行数：

`/tmp/live_robots.txt` 是 22行。

`/tmp/git_robots.txt` 是 0行。

这个差异本身不能证明部署内容发生了变化。

原因是保存库一侧为什么是 0行并没有查明。

它可能没有取得目标内容。

它也可能确实取得了空文件。

现有记录无法区分这两种情况。

所以，22行与 0行只是失败路径留下的数值。

它们不是有效比较得出的部署差异。

报告还单独检查了 Google-Extended。

它尝试提取对应的 blocks 列表。

blocks 列表表示发现的限制规则集合。

这次提取结果是空列表。

报告还检查文档是否同时包含 training 和 grounding。

training 指利用内容进行 AI 训练。

grounding 指回答时利用搜索资料提供依据。

结果记录为：

Google-Extended blocks 列表为空。

检查结果是 False，也就是“否”：这次文字检查没有同时找到 training 和 grounding。

完整实验记录是 hits 0/3。

空列表说明没有取得可供比较的规则。

False 只说明这次文字检查没有同时匹配两个目标。

它没有证明 Google-Extended 不具备相关控制能力。

它也没有证明一个名称能否同时控制两类用途。

要回答原问题，需要先取得正确规则或文档。

还需要安排能区分不同产品行为的检查。

这两项条件在现有记录中都没有满足。

因此，这部分只能判为没有得到答案。

## Codex 的正常运行只确认了搜索结果和边界算术

第二组实验关注 Codex 如何读取 AGENTS.md。

问题是文件超过 32 KiB 后会怎样处理。

一种可能是截断。

截断是只读取文件的一部分。

另一种可能是跳过整个文件。

实验原本想从文档说明和源代码中找出答案。源代码是开发者编写的程序指令，可以用来查看程序怎样处理文件。

报告把这些检查记为可用运行。

但它们没有找到能判明行为的内容。

完整状态是：

`doc-wording — hits=0/3 usable=3/3 — exit 0,0,0; source-impl — hits=0/3 usable=3/3; boundary-math — hits=0/3 usable=3/3`

doc-wording 是查找文档说明的步骤。

source-impl 是查找源代码实现的步骤。

boundary-math 是核对容量边界算术的步骤。

3项检查都记录了 hits 0/3。

文档搜索没有找到目标措辞。

源代码搜索也没有找到目标实现。

不过，这些步骤仍被记录为 usable=3/3。

其中还出现了 exit 0,0,0。

这说明搜索命令本身可以正常执行完。

它不说明搜索位置就是正确资料。

收集到的引用不是文件读取说明，而是一段网页菜单代码。原文如下：

`k hover:text-default hover:bg-primary-ghost-hover ' data-mobile-nav-link> Site tools (WebMCP)`

这是一段 HTML 导航标记。

HTML 是网页用来组织文字和页面元素的格式。

WebMCP 出现在网站菜单内容里。

这段文字与 AGENTS.md 的处理方式无关。

因此，收集路径抓到了无关页面内容。

搜索结果为 0，也就不能证明目标文档没有答案。

如果本应从教科书正文找答案，却只读了目录，那么搜索结果为 0，也不能说明正文没有答案。

实验还制作了几个大小接近 32 KiB 的测试文件。

文件大小分别是 32767、32768、32769 字节。

字节是记录文件大小的基本单位。

每个文件中都放入了用于定位的标记字节。

这种标记也称为 canary byte。

它的作用是让检查者知道指定内容位于哪里。

3个文件中的标记位置分别是：

32763、32764、32765。

这一步还检查了一个大小关系：32768 字节是否小于或等于 32 KiB。

原始记录是：

`32768 <= 32KiB ? true`

true 表示“是”。这个结果只确认了大小关系的计算。

它也说明标记位置随文件大小改变。

但这一步没有实际运行 Codex 的读取行为。

它没有展示 Codex 读到了哪个标记。

它也没有展示 Codex 忽略了哪个文件。

所以，32767、32768、32769 是测试文件的大小。

32763、32764、32765 是标记所在的位置。

这些数字不能单独证明截断单位。

它们也不能区分截短读取与整份跳过。

## 失败没有阻止后续输出，判别失败也没有成为成功条件

Fetch 和 Send 被当作命令执行，报错后处理仍在继续。

没有取得目标资料，或只取得无关网页代码，也没有阻止后续输出。

因此，执行完成不代表问题已有答案。

第一类问题是命令执行错误。

日志明确出现了 command not found。

第二类问题是目标资料没有正确取得。

robots.txt 的保存库文件是 0行。

Codex 检查又取得了无关的 HTML 菜单。

第三类问题是没有检查结果能否区分几种可能的行为。

列表为空、搜索没有找到目标内容时，流程仍能正常输出。

某些步骤还被计入 usable_runs，也就是可用运行次数。

这 3类问题不能混成同一个原因。

命令失败不等于资料一定错误。

资料错误也不等于每个命令都失败。

命令和资料都存在，也仍可能无法回答原问题。

真正缺少的是一道明确的成功条件。

这个条件应检查输出能否区分待验证的行为。

现有材料没有提供准确的 shell 代码。

shell 是接收并执行文字命令的环境。

现有材料也没有给出掩盖错误的具体语句。

所以不能确定 Fetch 与 Send 为何进入了命令位置。

也不能断定这些名称与 shell 自带的命令发生了冲突。

同样不能断定它们与 shell 留作特殊用途的词发生了冲突。

能够确认的范围更小。

它们被当成命令后产生了 not found。

错误没有阻止后续处理产生输出。

报告最终仍留下了正常结束状态。

## exit 0 和 usable_runs 仍有价值，但不能替代行为证据

最有力的反对意见需要先承认。

exit 0 本来就可以表示某个命令正常执行。

算术检查成功完成时，exit 0 没有问题。

搜索命令成功完成但没有匹配时，也可能返回正常状态。

报告也并非完全没有暴露失败。

网站与保存库的比较明确写着 usable 0/3。

它还写出了 exit 1,1,1。

报告中的 boundary 也描述了判别边界。

boundary 在这里指报告标出的适用范围和失败条件。

因此，不能说所有错误都被报告完全隐藏。

这些字段确实提供了有价值的检查线索。

但反对意见只能证明单个步骤完成了。

它不能证明原来的产品问题已有答案。

Codex 的步骤就是明显例子。

它们记录了 usable 3/3。

它们也记录了 exit 0,0,0。

可是文档和源代码仍然都是 hits 0/3。

取得的引用还是无关的 WebMCP 菜单。

边界步骤也只完成了算术。

所以，“可用运行”至少有两种可能含义。

它可以表示命令产生了格式正确的输出。

它也可以表示输出足以判断产品行为。

这两种含义在本报告中不能视为相同。

判断应继续追问资料来自哪里。

还要检查结果能排除哪些可能。

如果输出无法区分截断与跳过，就没有判明 Codex。

如果没有 Google-Extended 规则，也没有判明其控制范围。

正常结束、usable_runs 和 boundary 都不应被丢弃。

它们可以帮助定位实验在哪一步失去判别能力。

但把其中任一项单独当成产品证据，范围就扩大了。

## 改变设置前，工具制作方和报告使用方应分别把关

开头的问题可以用两层检查来回答。

先检查命令是否执行完。

再检查输出是否真的回答了原问题。

两层都通过，报告才适合成为设置变更的依据。

仅有 exit 0，只能支持第一层中的部分判断。

仅有 hits 0/3，也不能证明功能不存在。

空列表只有在资料正确且检查有效时才有明确含义。

这两组实验没有满足上述条件：资料正确，而且检查有效。

因此，当前适合采取的动作是暂缓产品结论。

不同角色还需要承担不同的检查任务。

- **自动检查工具制作方：** 检查命令是否出错、资料是否正确，以及结果能否区分待验证的行为。条件不满足时，应在结束状态、报告首句和后续汇总中写明“未能回答问题”。不要只用可用运行次数表示检查是否成功。
- **报告使用方：** 不要把这两项实验的“命中 0/3”和空列表当成功能不存在的证据。在正确资料和可判别的复查结果出现前，不要据此修改设置。

工具制作方应规定：出现上述问题时，整项检查不能标为成功。

只在详细字段中留下失败，还不够稳妥。

报告使用方则需要寻找与问题直接对应的证据。

Google-Extended 需要有效规则和可比较结果。

Codex 需要能区分截短读取与整份跳过的实际证据。

如果这些证据缺失，合适的结论是“暂不能判别”。

这不是说产品一定没有对应行为。

也不是说报告中的每个数字都没有价值。

它只是把结论限制在证据能够支持的范围内。

## 本文未能核实的部分

- 爬虫是自动访问网页并收集内容的程序。实验尚未测量真实爬虫是否遵守 robots.txt 规则。屏蔽列表为空，也没有另一组结果可供对比。使用 6 个用户代理名称收到 HTTP 200，不能证明真实爬虫遵守规则。这也不能证明 robots.txt 是唯一的控制手段。
- 尚未确认 Google-Extended 这一个名称能否同时控制两种用途：用内容训练 AI，以及用搜索资料为答案提供依据。列表为空和检查结果为 False，都不能说明该功能不存在。
- 尚未确认 /tmp/git_robots.txt 为0行的原因。由于无法知道是路径错误还是实际为空文件，因此不将其扩展解释为存储库原始文件或部署状态存在差异。
- 尚未确认Codex是以字节为单位截断超过32 KiB的AGENTS.md，还是跳过整个文件。标记字节位置和算术并非实际执行Codex读取行为的结果。
- 日志显示，Fetch 和 Send 被当作命令执行，并出现了“找不到命令”的错误。报告也记录了最终退出代码。但现有材料没有提供具体执行代码，也没有说明错误如何被掩盖。因此，不能断定这些名称与 shell 自带的命令或特殊用途的词发生了冲突。
- 空列表和搜索命中0并不总是失败。本文讨论的两项实验由于未确认目标数据的获取和检查有效性，无法回答原始问题。
- 报告已记录可用运行次数，也说明了哪些结果不能用来判断产品行为。尚不清楚“未能回答问题”是否直到审查时才被发现。也不清楚后续汇总或决策是否误把这类结果当成了成功。
- 参考资料 1 至 4 的验证状态均为 unconfirmed，意思是“尚未确认”。列出网址不代表实验日志或产品行为已经得到验证。本文也不把来源 4 当作说明 Codex 内部处理方式的权威依据。
- 本文不讨论各提供方使用的抓取程序名称如何随时间变化。也不讨论整套测试工具出错的频率，以及改进它需要多少成本。
- 如果同一次运行的新证据表明，工具取得了正确文档和源代码，并区分了实际行为，就应调整“未能回答问题”的判断。如果新证据表明，未得出答案的运行没有被计入最终成功汇总，也应调整“失败仍被当作成功汇总”的判断。
