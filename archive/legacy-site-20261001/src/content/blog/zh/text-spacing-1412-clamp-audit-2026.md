我的关联文章列表里，每条推荐都配一句话，说明「读完这篇为什么值得再看那篇」。四种语言各写一遍，全是手写的，平均 108 个字符。

这次测量告诉我，读者实际能看到的是其中的 35%。

不是加了无障碍的文字间距之后才变成 35%，是一直如此。而我是为了测一条 WCAG 标准才发现的。

## 标准要求什么，规则又读了什么

先把标准本身摆清楚。WCAG 2.2 的成功标准 1.4.12 Text Spacing 属于 AA 级，由四个值组成：行高至少为字号的 1.5 倍，段后间距至少 2 倍，字距至少 0.12 倍，词距至少 0.16 倍。当用户自己把这四个值设上去时，<strong>不能有内容或功能的丢失</strong>——这才是标准的正文。

为什么会有这条标准，值得先说一句。有阅读障碍、低视力或某些认知障碍的读者，遇到行距过密时会找不到下一行，视线掉回刚读完的那一行。所以他们会用扩展或用户样式表把间距强行撑开来读。1.4.12 不是要求你把间距做宽，它问的是<strong>读者自己撑开的时候，你的版式扛不扛得住</strong>。作者要交付的是余量，不是排版风格。

[W3C 的 Understanding 文档](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)用图示列了三种失败形态：文字被纵向切掉、被横向切掉、与后面的句子重叠到读不出来。同时它也写明，省略号本身不算失败，只要提供了显示被截断文字的办法。这一句请先记住，本文的结论会落在它上面。

那自动检查器怎么判？axe-core 里对应 1.4.12 的规则只有 `avoid-inline-spacing` 一条。Deque 给出的规则说明是："Ensure that text spacing set through style attributes can be adjusted with custom stylesheets."

它读的是行内 `style` 属性。它不会把间距加上去，也不看加上去之后版式变成什么样。

把这条规则单独在我站点上跑一遍：

```
axe-core 4.13.0  ·  runOnly: avoid-inline-spacing
24 pages
violations: 0   passes: 24   incomplete: 0   inapplicable: 0
```

24 页全通过。我从没用行内样式钉死间距，判通过是对的。规则把自己那份活干得很准。

[昨天我用 W3C 的 1,213 个 ACT 测试用例量 axe 的守备范围时](/zh/blog/zh/act-rules-axe-coverage-wcag-sc-2026)，1.4.12 是 14 中 13，稳稳落在覆盖良好的那一档。那个数字也是诚实的。只不过那 13 个用例全是行内 style 的例子。标准答案考的东西，和真实站点会踩的东西，压根不是一类。

## 把四条声明拆开，一次只加一条

于是我写了个脚本，不跑规则，直接把标准加上去：`scripts/audit-text-spacing.mjs`。做的事很简单，用 Playwright 打开页面，先记录所有元素的几何信息，再用 `!important` 注入四个值，然后再记一次，比差异。

丢失的判定分三条路：

- 处在 `overflow: hidden` 或 `clip` 盒子里、`scrollHeight` 超过 `clientHeight` 的元素
- 带 `-webkit-line-clamp` 的盒子里，被藏起来的行数变多的元素
- 整个文档新长出横向滚动条的页面

样本取 24 个 URL，四种语言的首页、文章列表、静态页、正文页和 404 都混在里面。视口两种，桌面 1280×800 和移动 390×844，合计 48 个画面。

四个值全加上，结果如下。

| 指标 | 数值 |
|---|---|
| 新被切掉的元素 | 570 |
| 在钳制盒里多丢了行的元素 | 1,438 |
| 出现新丢失的画面 | 48 中 29 |
| 新长出横向滚动条的页面 | 0 |
| 页面高度增幅 | 最小 1.006 倍，中位数 1.123 倍，最大 1.487 倍 |

横向滚动零，这个数字挺让人踏实的。流式布局在字距变宽之后仍然守住了文档宽度。出事的地方全在盒子里面。

可是光有 570 这个总数，还是不知道该改哪儿，因为不知道四个值里谁是元凶。所以我又跑了四遍，每次只加一条。

![横向条形图，比较 SC 1.4.12 的四条声明分别单独应用时新被切掉的元素数。line-height 1.5 和段后间距 2em 都是 0，word-spacing 0.16em 是 122，letter-spacing 0.12em 是 523，四条同时应用是 570](../../../assets/blog/text-spacing-1412-clamp-audit-2026/declaration-decomposition.png)

| 声明 | 新被切掉的元素 | 丢掉的钳制行 | 页面高度中位数 |
|---|---|---|---|
| `line-height: 1.5` | 0 | 0 | 1.000 倍 |
| `margin-bottom: 2em`（段后） | 0 | 0 | 1.064 倍 |
| `word-spacing: 0.16em` | 122 | 225 | 1.004 倍 |
| `letter-spacing: 0.12em` | 523 | 1,316 | 1.036 倍 |
| 四条全上 | 570 | 1,438 | 1.123 倍 |

结果完全偏向一边。纵向的那两条<strong>一件丢失都没造成</strong>。丢失全部来自横向的两条，其中字距一条就占了 523 件，是全部的 92%。

## 让你注意到的那个轴，不是丢内容的那个轴

看到这张表，我才意识到自己脑子里把这条标准的顺序排错了。

讲 1.4.12 的文章几乎都从行高 1.5 开头，我也是这么记的。可行高调到 1.5 会发生什么？行间拉开，段落变长，页面往下伸。带 `-webkit-line-clamp` 的盒子也跟着伸，因为钳制盒的高度是行数乘行高。三行还是三行，能看见的字数一个没少。

段后间距同理。它把页面高度中位数推到 1.064 倍，丢失是 0。纵向被推开的部分，滚动条会吸收掉。

字距是另一码事。0.12em 意味着每个字都变宽，也就意味着一行能装的字变少。三行钳制盒还是三行，但这三行装的内容少了。盒子没动，里面的东西胀出来了。

一句话概括：<strong>让你察觉到的轴，和让你丢内容的轴，是两个不同的轴。</strong>开了用户样式表的读者，体感是「这页变长了」；真正消失的却是被横向挤出去的句尾。而在肉眼过一遍的 QA 里，容易发现的偏偏是前者。

这里还得再确认一个测法上的问题。常用的文字间距书签脚本都是把 `line-height: 1.5` 直接写死。可我的正文本来就是 1.58，用 1.5 覆盖它是在<strong>调小</strong>。数据里也验证了：只加行高那一轮，页面高度的最小值是 0.926 倍，有些页面短了 7%。

于是我换了第二种读法，只把低于 1.5 的元素提到 1.5，48 个画面重跑。结果是新被切掉 570 件、丢掉的行 1,438 件，和第一种读法<strong>一模一样</strong>。变的只有页面高度中位数，从 1.123 倍变成 1.168 倍。不管怎么解释行高这一条，丢失的数字都不动。这又是一条证据：行高从来不是原因。

## 词间有空格的语言，和没有的语言

把只加 `word-spacing` 那一轮的 122 件按语言拆开，出来一张我没预料到的表。

| 语言 | 新被切掉的元素（桌面 / 移动） |
|---|---|
| 日文 | 1 / 1 |
| 中文 | 3 / 4 |
| 韩文 | 40 / 15 |
| 英文 | 0 / 55 |

中文和日文基本免疫，原因很直白：词与词之间不放空格，`word-spacing` 几乎没有落脚的地方。Understanding 文档对此也有交代，不使用其中某项属性的文字体系，可以只用存在的属性来达成符合。

韩文那 40 件才是关键。韩文常被一并归进 CJK，但它<strong>是分写的</strong>，词与词之间有真实的空格，所以这条声明照常生效。W3C 那条例外管得住中文和日文，管不住韩文。

对做多语言站点的人来说，这个区分是有实际后果的。要是把「CJK」当成一整块、认定词距影响不到，那在所有韩文页面上都会悄悄判错。我自己此前就是这么想的，看到这张表才改过来。

英文移动端的 55 件是另一回事。英文摘要平均 168 个字符，是四种语言里最长的。在 390px 宽度下，这个长度正好卡在三行钳制的边界上，词距稍微一开就越界。桌面端是 0，也是同一个道理，宽度够就有余量。

`letter-spacing` 则不挑语言，因为它按字加宽。韩文桌面端 164 件受创最重，中文也有 42 件。

## 能截的句子，和不能截的句子

以上是标准的部分。真正要改什么，是另一个问题。

测量数据里带钳制的组件一共三种。我对每一种都算了「盒子显示出自己内容的百分之多少」，分基线和加间距后两栏。

| 组件 | 观测数 | 基线 | 加间距后 |
|---|---|---|---|
| 文章卡片摘要（`line-clamp: 3`） | 2,688 | 86.2% | 76.6% |
| 首页最新文章摘要（`line-clamp: 2`） | 24 | 49.4% | 40.8% |
| 推荐语（`line-clamp: 1`） | 42 | <strong>35.1%</strong> | 30.7% |

我在第三行停住了。

`.item-reason` 就是开头说的那句手写推荐语。一行钳制只让它露出 35%。

![修复前的关联文章列表。三条推荐语都在第一行被省略号截断](../../../assets/blog/text-spacing-1412-clamp-audit-2026/item-reason-before.png)

这个发现跟 1.4.12 没有直接关系。它不是加了文字间距之后冒出来的问题，而是本来就在那儿。为了量一条无障碍标准而造的仪器，顺手把一个内容缺陷叼了出来。这种事其实常有。[之前用全量扫描找出 26 页抽样漏掉的违规](/zh/blog/zh/wcag-em-2-sampling-vs-full-sweep-audit-2026)，路径也是这样的。

而前面请你记住的那句话，这时候回来了。省略号不算失败，前提是<strong>有办法把被截断的文字显示出来</strong>。用这个条件重新审视三个组件，判定立刻分开了。

文章卡片摘要点进去就是全文，办法在。降到 76.6% 是设计好的摘要，不是丢失。首页摘要同理。

推荐语没有办法。没有展开按钮，也没有别的页面登载同一句话。被截掉的那 65% 谁也看不到。在用户动间距设置之前，它就已经是丢失了。

所以我没有把钳制放宽，而是直接去掉。

```css
.item-reason {
  margin: 0;
  font-size: 0.8125rem;
  color: var(--ink-2);
  line-height: 1.5;
  /* 这句话是每条推荐单独写的，站内别处不再出现。
     在这里截断就没有办法显示剩下的部分，所以不截。 */
}
```

`line-height` 也从 1.4 提到了 1.5，理由从前面的拆解里就能推出来：<strong>作者写死的行高只要已经满足标准的 1.5 下限，用户覆盖行高就压不小这个盒子。</strong>停在 1.4 的话，遇到强制 1.5 的读者，盒子会变大，版式跟着晃。定在 1.5，这个轴上就什么都不会发生。凡是用钳制的文字，我认为都可以照这条来。

首页最新文章摘要从两行放宽到三行。它有通往正文的链接，所以截断本身保留。

![修复后的同一个列表。三条推荐语都换行到第二行，完整显示到句末](../../../assets/blog/text-spacing-1412-clamp-audit-2026/item-reason-after.png)

## 改完之后，指标反而变差了

重新构建，48 个画面再测一遍。然后我看到这个：

```
修复前：新被切掉的元素 570
修复后：新被切掉的元素 574
```

多了四个。

一开始我怀疑是回退，结果不是，是指标本身的性质问题。「新被切掉」数的是<strong>基线状态下没被切、加间距之后才被切</strong>的元素，只捕捉跨过阈值的那一瞬间。修复前的 `.item-reason` 在基线状态下就已经被切了。一直被切的盒子，不可能「新」被切，它压根不在这个指标的视野里。

去掉钳制腾出了那些位置；与此同时首页摘要从两行变三行，基线上有了余量，于是它的四个元素进入了可观测区间，然后在加间距后溢出。

同一份数据换个指标看，方向是反的。

| | 修复前 | 修复后 |
|---|---|---|
| 出现新丢失的画面 | 48 中 29 | 48 中 <strong>18</strong> |
| 首页摘要基线显示率 | 49.4% | <strong>74.2%</strong> |
| 推荐语基线显示率 | 35.1% | <strong>100%</strong> |

特意写下这一段，是因为它对 CI 有直接含义。我们把无障碍卡进流水线时，通常就盯一个数：违规数。那个数只登记跨阈值的动作。<strong>长期处于失败状态的元素，永远不会出现在里面。</strong>一直被切的盒子今天还是被切着，没有变化，也就没有报告。一门心思把这个数压到零，就会成建制地漏掉这一整类失败。

这就是为什么要在计数旁边留一个比率指标。[之前量吸顶头部会不会遮住焦点时](/zh/blog/zh/focus-not-obscured-sticky-header-scroll-padding-2026)，答案取决于你往哪个方向按 Tab，是同一种陷阱。数什么，决定了你能看见什么。

## 这次测量没有说的事

把结论的边界老实收窄。

一种浏览器引擎、一台 Mac、24 个 URL，不是全部 1,356 页。Firefox 和 WebKit 在 `letter-spacing` 的次像素处理和 `-webkit-line-clamp` 的实现上都不一样，数字可能会变，我没有验证。

重叠根本没测。我的判定只有裁剪盒溢出和钳制行数两项。文字在没有裁剪祖先的情况下压到后面元素上的那种失败，这个脚本完全抓不到。Understanding 文档明确列出的三种失败形态，我整整漏了一种。

「横向滚动零」是文档层面的说法，意思是页面没有横向错位，不等于上面每个元素都安然无恙。

还有，axe 没有错。`avoid-inline-spacing` 精准地做完了规则说明里写的事，而我的站点没有它要找的那种行内声明，判通过是正确的。这篇不是在批评检查器，而是<strong>用数字把规则的射程和标准的射程之间的距离量了一遍</strong>。

## 先决定这句话能不能截

这次测量里真正能拿去用的，只留这几条。

- <strong>用钳制之前先过一个问题：</strong>被截掉的部分有没有路径能读到？摘要通往正文的链接是路径。只存在于那个盒子里的句子没有路径，这种不能截。
- <strong>带钳制的文字，作者先把 `line-height` 写到 1.5 以上。</strong>自己先满足标准的下限，用户的覆盖在这个轴上就改变不了任何东西。
- <strong>该担心的声明是 `letter-spacing`。</strong>523 对 0。行高和段后间距只会把页面拉长。评审的时间花在横向轴上。
- <strong>多语言站点别把「CJK」当一整块。</strong>词距对中文、日文几乎无害，对韩文照常生效。分界线是有没有词间空格，不是文字体系。
- <strong>违规计数旁边留一个比率。</strong>计数只登记跨阈值的瞬间，长期失败的元素不会出现在计数里。

复现步骤都留在仓库里。把 URL 列表喂给 `scripts/audit-text-spacing.mjs`，用 `--mode` 把四条声明分开各跑一次，三十秒左右就能知道自己站点里是谁在切哪儿的文字。

把检查器判绿的标准真正加上去再量一遍，这件事占了我工作的相当一部分。哪怕还停在「不知道该从哪儿下手」的阶段也没关系，想问就到[联系页面](/zh/contact/)来问。
