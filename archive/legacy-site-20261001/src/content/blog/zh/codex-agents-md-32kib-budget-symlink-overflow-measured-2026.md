## 两个 AI 编程助手需要读同一份指南，你自然会想用符号链接共享

如果你所在团队同时使用 Codex 和 Claude Code 这两个 AI 编程助手，你大概希望它们遵守同一套规则，比如代码风格、提交信息格式、禁止使用的 API。规则写在一个文件里，两个工具都能读到，最省事。

AGENTS.md 就是这样一个文件。它是给 AI 助手看的说明书，Codex 和 Claude Code 都认它。

问题来了：说明书只有一份，两个助手都要看。你不想复制两份，因为改起来要改两遍，迟早会不一致。于是你听说了一个办法——用符号链接。符号链接不复制文件，只指向同一个文件。你把它放在两个助手各自找文件的位置，它们打开后看到的是同一份内容。

这个办法听起来很完美。但有一个问题你还没弄清楚：如果这个文件越来越大，超过某个大小限制，两个助手会怎么读它？是只读前面一部分，还是整本都读？本文就来回答这个问题。

## 实验证实：从子目录和主目录都能通过符号链接找到共享文件

先验证符号链接本身是否真的有效。实验是在一台单独的电脑上做的，用的工具版本是 Node 20。

Claude Code 会从项目最外层文件夹和它上面的文件夹读取规则文件，所以你把规则放在这些地方，在里面的子文件夹工作时也能读到。这意味着你不需要在每个子目录里都放一份指南，只要放在项目根目录，Claude Code 在任意子目录工作时都能找到它。

实验数据也证实了这一点。从子目录向根目录的符号链接进行上级访问，3 次测试全部成功，标记文件通过目录遍历被找到 1 次。也就是说，在子文件夹里工作时，Claude Code 确实能通过符号链接读到最外层的指南文件。

这意味着，不管你在项目的哪个子目录里工作，都能读到根目录的这份指南。

主目录路径的符号链接同样成立。实验确认，主目录里两个助手各自默认读取的文件位置，都通过符号链接指向同一个 shared.md 文件。两个助手各自习惯去读的位置，现在都指向同一份内容。

到这里，符号链接共享指南文件这件事，在文件解析和目录可达性上，是行得通的。你有了一个单一来源，改一处，两个助手都看到新内容。

## 共享文件超过 32KiB 后，符号链接会传递完整文件，而不是截断后的部分

符号链接能打通，但大小限制才是真正的坎。实验测量了共享指南文件在 32KiB 预算下的表现。

先解释一下 32KiB 是什么。KiB 是计算机的容量单位，1KiB 等于 1024 字节，32KiB 就是 32768 字节。这相当于约三万两千个英文字符。对大多数团队的指南来说，这个空间够用，但也不是永远够用。

实验准备了两份文件。v31 版本的大小是 31769 字节，低于 32768 字节的预算线，属于安全范围。v33 版本的大小是 33817 字节，超出预算 1049 字节。关键结果在这里：当符号链接指向 v33 这个超限文件时，工具读取的完整大小是 33817 字节，也就是整个文件都被读进去了，没有被截断。

符号链接会直接把整个文件送过去，不会只传一半。

所以，一旦共享指南文件超过 32KiB，两个 AI 助手都会把整个文件读进去。它们不会因为文件超限就只读前半部分，而是把全部内容都读进去。这听起来好像是好事，信息不丢失。但问题在于，两个工具对超限文件的处理方式可能不同，有的可能报错，有的可能忽略后面的指令，有的可能行为异常。共享的前提是"两个工具看到的内容一样"，但超限后，它们各自怎么处理这份内容，就不好说了。

## 32KiB 预算对大多数团队够用，符号链接共享并非对所有人都有风险

你可能会说，32KiB 的预算在现实中几乎不会超。大多数团队的指南文件只有几 KiB，就算超了，把文档拆开或者写个摘要就行。如果团队指南文件一直只有几 KiB，这个说法是成立的。

Codex 默认读取一个规则文件，但它允许你为特定文件夹准备一个优先级更高的替代规则文件。这意味着 Codex 本身提供了覆盖机制，你可以在不修改主指南的情况下，为特定目录指定不同的规则。这样一来，主指南可以只写常用规则，特殊情况单独处理。

所以，符号链接共享的风险，对每个团队来说不一样。如果你的团队指南文件一直不大，那么用符号链接共享是省心的好办法，改一处，两个工具都同步更新。但如果你觉得指南以后会越写越长，比如团队变大、规则变多，那么符号链接共享就是一个隐患。它让你觉得"反正只有一个文件，改起来方便"，但这种感觉在文件超限那一刻就没了。

## 从明天起，测量你的指南文件大小，超限就解除符号链接或拆分文档

如果你的团队指南文件还不到 32KiB，符号链接共享可以继续用。但你要把这当作一项需要定期检查的安排，而不是一劳永逸的设置。具体做法是按两类情况分别处理。

对于指南文件可能超过 32KiB 的团队，请你今天就在 CI 里加上一个文件大小测量步骤。CI 能在你每次提交代码后自动运行一遍检查流程，帮你提前发现问题。测量对象是你们共享的指南文件。当文件大小超过 31769 字节（约 31KiB）时（此时尚未超出预算），就要准备处理了。当文件大小达到 33817 字节时，就已经超出 32KiB 预算 1049 字节。超过 32KiB 的时刻，就是符号链接共享必须解除的时刻。你要么解除符号链接，让 Codex 和 Claude Code 各自读取自己的文件。你要么把文档拆分成多个小文件，让每个文件都在预算以内。把这个检查做成一个门禁，超过限制就阻止合并，这样就不会在不知不觉中超限。

如果你的指南文件一直都不大，可以继续用符号链接共享，但最好每周检查一次文件大小。测量很简单，就是查看文件占用的字节数。一旦发现大小在往 31769 字节靠近，就要提前规划。当接近 33817 字节时，你已经有了 1049 字节的预警空间。早期发现，早期处理，就不会被迫在紧急时刻拆分文档。

现在回到开头的问题：符号链接连接的共享指南文件，超过 32KiB 后会怎样？答案是，它不会被截断，而是完整读取。这意味着共享的前提已经不成立了。你不需要等到出问题才行动。今天就可以去测量你的指南文件大小，然后根据测量结果决定：继续共享，还是解除符号链接或拆分文档。

## 从明天起，测量你的指南文件大小，超限就解除符号链接或拆分文档

回到开头的问题：共享指南文件超过大小限制后，两个助手会怎么读？是只读前面一部分，还是整本都读？实测已经给出了答案：符号链接会把整个文件都送过去，不会只送一半。

因此，你可以从明天起按这三步来做。在自动检查流程中加入一条命令，测量 AGENTS.md 或 shared.md 的字节数，一旦超过 32768 字节就触发警告。如果文件确实超限，那就解除符号链接，改成按需引用，避免一次载入太多内容。或者把文档拆成几个小文件，让每个文件都不超限。

这样，符号链接共享就不会成为隐患，两个工具看到的规则始终一致。

## 符号链接传文件：是“完整读取”，不是“截断”

刚才我们说，当共享文件超过 32KiB 这个预算后，符号链接会把整个文件传过去，而不是只传一部分。这里要特别说明一下：我们实测确认的是，符号链接指向的文件大小是 33817 字节，比 32KiB 的限制多出了 1049 字节。整个文件都被工具读取了。

但“工具看到了这个文件”和“工具把里面每条规则都用了”是两回事。就像快递员把整个纸箱送到你家，但你不一定会把箱子里的每件东西都拿出来用一遍。我们只确认了文件送到了，没确认工具把内容都用上了。

所以，准确的说法是：符号链接送来了完整的文件，但工具是否把内容全部用上，我们没验证过。这一点不能当作事实。

## 本文未能核实的部分

- Codex 和 Claude Code 是否真的会读取通过符号链接连接的指南文件，本次实验没有验证。实验确认了符号链接在文件系统层面能被正确解析。
- 当优先级更高的替代规则文件存在时，符号链接共享会发生什么变化，本次实验没观察到。因为测试中替代文件从未被用到，所以无法判断它和符号链接同时存在时的情况。
- 32KiB 预算在两个工具中是否以相同单位计算，本次实验没有确认。一个工具可能按字符数算，另一个按别的单位算，结果就会有差别。如果两个工具的计算单位不同，那么"超过 32KiB"这个判断本身，在两个工具中可能指向不同的文件大小（此问题未获确认）。
