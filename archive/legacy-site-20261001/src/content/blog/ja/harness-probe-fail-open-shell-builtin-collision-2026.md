## 設定を変える前に報告書の成功条件を確かめる

AIが作った点検報告に「正常終了」と書かれている。  
同じ報告には「見つかった項目は0個」とも書かれている。

この報告だけでサイト設定を変えてよいのか。  
AIが読む文書を減らしてよいのか。  
今日の判断に使うなら、数字の意味を分けて読む必要がある。

今回の報告には、Google-ExtendedとCodexを調べた結果が記されていた。Codexは、プログラムを書く作業を助けるAIである。  
Google-Extendedはrobots.txtに現れるGoogle向けの名前である。  
robots.txtは、サイトを読む相手への指示を書くファイルである。

もう一方では、CodexがAGENTS.mdをどう読むかを調べていた。  
AGENTS.mdは、Codexに作業上の情報を伝える文書である。  
調査では、その文書が32 KiBを超えた場合にCodexがどう扱うかを確かめようとした。KiBは、ファイルの大きさを表す単位である。KiBはデータ量の単位である。バイトもデータ量を数える単位である。

報告書には、処理が終わったことを示す数字がある。  
一方で、製品動作を直接示す資料は得られていない。  
この違いを見落とすと、未確認の動作を確認済みと読んでしまう。

正常終了は、調査用の処理が最後まで進んだ印かもしれない。  
それは、目的の資料を取得できた証拠とは限らない。  
検索処理が動いても、検索先が正しいとは限らないからである。

終了表示は「実行が終わったか」を確かめる手がかりになる。「質問に答えたか」を確かめるには、質問に合う資料と検証結果を見る必要がある。

## robots.txtの名前、HTTP応答、命令エラーは別の観察である

最初の実験はrobots.txtから相手別の名前を探した。  
点検では、文字の並び方を指定して探す正規表現という方法を使った。集めたのは、アクセスするソフトが名乗るUser-agentという名前である。

この名前ごとにrobots.txtの記述を分けられる。  
点検はGoogle、OpenAI、Anthropic向けの名前を探した。

専用の名前は見つからなかった。  
記録は次の内容だった。

`All tokens: ['*'] / Google tokens: [] / OpenAI tokens: [] / Anthropic tokens: []`

`*`だけが収集されていた。  
Google tokens、OpenAI tokens、Anthropic tokensは空だった。  
検索の記録はhits 0/3だった。hitsは、探した項目が見つかった回数を示す欄である。  
処理の終了記録はexit 0,0,0だった。

exitは、処理が終わった状態を数字で返す仕組みである。  
exit 0は、実行した処理が成功として終わった印になる。  
ただし、探していた名前が見つかったという意味ではない。

点検では、6個のUser-agent名を使って要求も送った。  
使った方法はHEADとGETだった。  
HEADは本文なしで応答情報だけを受け取る要求である。  
GETは対象の内容を受け取る要求である。

結果は6個とも同じだった。

`Google-Extended, Googlebot, GPTBot, ClaudeBot, OAI-SearchBot, Mozilla/5.0 はすべて HTTP 200を返しました。`

HTTP 200は、要求に対して成功応答が返った状態である。  
この測定の記録もhits 0/3だった。

ここで確認できたのは応答の状態である。  
実際のクローラーがrobots.txtを守ったかは測っていない。  
クローラーは、ウェブ上のページを自動で読むソフトである。

HTTP 200は、robots.txtの応答を受け取れたことを示す。  
Google-Extendedなどの規則が有効かは示さない。  
応答成功と規則の適用は別の確認事項である。

さらに、3回の実行すべてに命令エラーが残った。

`bash: Fetch: command not found`

`bash: Send: command not found`

bashは、FetchとSendを説明文ではなく命令として解釈した。  
bashは、入力された命令を実行するシェルである。  
シェルは、人が書いた命令をプログラムに渡す仕組みである。

命令が見つからない記録とexit 0,0,0が同時に残った。  
つまり、途中に失敗があっても出力は生成された。  
最終的な正常終了だけでは途中の状態を説明できない。

この報告には、専用の名前が見つからなかったこと、HTTP 200が返ったこと、命令エラーが起きたことの3種類の記録がある。それぞれが示す内容は異なるため、1つの記録だけでほかの記録の意味まで判断することはできない。

## 実サイトと保存先の比較は成立していなかった

次の処理は2つのrobots.txtを比べようとした。  
対象は実際のサイトと手元のコンピューターにある保存先だった。保存先では、ファイルの変更履歴を管理するgitという仕組みを使っていた。

しかし、比較処理は3回とも成功しなかった。  
実行できた回数を示すusableも0/3だった。  
記録には次の値が残っている。

`live_vs_git_robots: hits=0/3 usable=0/3, exit 1,1,1`

usable_runsは、結果を検討に使える実行回数である。  
この値が0/3なら、使える比較結果はなかったことになる。  
exit 1,1,1も3回の処理が失敗したことを示していた。

それでも、一時ファイルの行数は出力された。

`/tmp/live_robots.txtは22行、/tmp/git_robots.txtは0行`

実サイト側の一時ファイルには22行あった。  
git側の一時ファイルには内容がなかった。  
ただし、0行になった理由は確認されていない。

対象ファイルが本当に空だった可能性は残る。  
読み込む場所が違っていた可能性も残る。  
この実験だけでは、どちらだったかを選べない。

比較には、両方の資料が正しく取得された確認が要る。  
片方が空なら、比較結果より先に取得状態を確かめる。  
ここではその確認を終えないまま処理が止まっていた。

別の処理はGoogle-Extendedの記述を探した。  
Google-Extended blocksの一覧は空だった。  
blocksは、対象名に結び付いた規則のまとまりである。

同じ処理はtrainingとgroundingも調べた。  
trainingはAIの学習に関する調査語だった。  
groundingは回答作成で検索資料を使うことを指す。

両方を同時に含むという判定はFalseだった。  
Falseは、検査した条件を満たさなかったという出力である。  
この処理もhits 0/3だった。

空のblocks一覧では対象動作を測れない。  
Google-Extendedの記述がないため、比較条件を作れない。  
Falseは機能が存在しないという判定ではない。

確認できたのは、取得した資料内の検査結果である。  
確認できなかったのは、Google-Extendedの制御範囲である。  
資料が空なら、その範囲を実測したことにはならない。

ファイルの行数が違っても、配布された内容が違うとは限らない。Falseという出力だけでは、Google-Extendedで何を制御できるかも決められない。

## Codexの検索と境界計算は読み方を判別していない

Codex側ではAGENTS.mdの32 KiB超過時を調べていた。  
途中で文書を切るのかが質問の一部だった。  
文書全体を読まないのかも区別する必要があった。

点検では、説明文書と、動作を決めるプログラムの記述を検索した。プログラムの記述をソースコードと呼ぶ。検索には、指定した文字を文書内から探すgrepという処理を使った。  
3つの処理は実行可能な結果として数えられた。

記録は次のとおりだった。

`doc-wording: hits=0/3 usable=3/3, exit 0,0,0`

`source-impl: hits=0/3 usable=3/3`

`boundary-math: hits=0/3 usable=3/3`

doc-wordingは文書内の表現を探していた。  
source-implは、動作を決めるプログラムの記述を探していた。  
boundary-mathはサイズの境目を計算していた。

3つともusable 3/3だった。  
doc-wording、source-impl、boundary-mathの終了記録はいずれも0,0,0だった。  
しかし、探していた項目が見つかった回数はすべて0/3だった。

引用用に収集された文字列も対象とは無関係だった。

`k hover:text-default hover:bg-primary-ghost-hover ' data-mobile-nav-link> Site tools (WebMCP)`

これは判別したいCodexの説明ではない。  
HTMLのメニュー部分に当たる文字列だった。  
HTMLは、ウェブページの構造を記述する形式である。

WebMCPという名前も含まれていた。  
だが、AGENTS.mdの上限処理を説明してはいなかった。  
収集経路が判別対象とは違う文書を取得していた。

教科書本文で答えを探す必要があるのに、目次だけを読んだとする。検索結果が0個でも、本文に答えがないとは判断できない。調べた場所が違えば、0という結果の意味も変わる。

境界計算では3種類のファイルを作った。  
サイズは32767、32768、32769バイトだった。  
バイトは、ファイル量を数える単位である。

各ファイルには確認用の印を置いた。  
この印はカナリバイトと呼ばれていた。  
位置はファイルサイズに応じて異なった。

32767バイトでは位置が32763だった。  
32768バイトでは位置が32764だった。  
32769バイトでは位置が32765だった。

計算結果には次の表示もあった。

`32768 <= 32KiB ? true`

この結果が確認したのは大小関係の計算である。  
カナリバイトの位置も計算上の値である。  
実際にCodexへ各ファイルを読ませた結果ではない。

この計算だけでは2つの動作を区別できない。  
32 KiBを超えた部分だけを切る動作かもしれない。  
ファイル全体を読まない動作かもしれない。

文書検索とソース検索にも該当箇所がなかった。  
そのため、説明や実装からも区別できていない。  
usable 3/3は、判別成功の回数ではなかった。

実行回数や容量の計算結果は、Codexが実際に文書を読んだ証拠ではない。文書の途中まで読むのか、全体を読み飛ばすのかは分からない。

## 完了と回答が分かれた経路を3つに分ける

FetchとSendが命令として扱われ、失敗した後も処理は続いた。空の資料や無関係なHTMLも、そのまま結果に含まれた。処理は終わったが、質問には答えられなかった。

ただし、正確なシェル構成は提供されていない。  
どの書き方が最終状態を隠したのかは確定できない。  
FetchやSendの名前だけで原因を決めてはならない。

観察された問題は3つに分けられる。  
最初は、命令として実行された文字列のエラーである。  
ログにはcommand not foundが残っていた。

次は、判別に必要な資料を取得できなかったことである。  
/tmp/git_robots.txtは0行だった。  
Codex側では無関係なHTMLが取得されていた。

最後は、得た資料で質問に答えられるかの検査である。  
空の一覧やhits 0/3が、そのまま出力になっていた。  
判別不能を成功から外す条件が十分ではなかった。

この3つは同じ失敗ではない。  
命令が失敗しても、対象資料は取れる場合がある。  
命令が動いても、違う資料を取る場合がある。

正しい資料を取っても、判定条件が足りない場合がある。  
各段階を別々に確かめなければ原因を絞れない。  
終了コードは、処理が終わった状態を示す数字である。その数字一つだけでは、どの段階で何が起きたかは分からない。

処理が最後まで進んでも、質問に答えられたとは限らない。答えるには、製品がどう動いたかを見分けられる証拠が要る。処理の完了だけを成功とすると、調べていない動作まで確認済みと受け取られる。

## 正常終了の表示が正しい範囲を先に認める

exit 0が間違っているとは限らない。  
計算処理が正常に終わればexit 0になり得る。  
検索処理が最後まで動いた場合も同じである。

境界計算は指定された算数を実行していた。  
文書検索も検索処理そのものは完了していた。  
その狭い意味では正常終了という表示に理由がある。

usable_runsも失敗を一部示していた。  
robots.txt比較はusable 0/3だった。  
この値を読めば、比較が成立しなかったと気付ける。

報告にはboundaryもあった。  
boundaryは、判別できた範囲を示す記録である。  
そこには、元の質問への答えを確定できなかったことが記されていた。

したがって、報告が失敗を完全に隠したとは断定しない。  
検討時に初めて失敗が見つかったとも確認できない。  
後続の集計へ誤って渡ったかも分かっていない。

それでも、別の問題は残る。  
usable 3/3は質問への回答を保証していなかった。  
Codex側では対象外のHTMLが収集されていた。

boundary-mathも計算を終えただけだった。  
実際のCodexの読み方は実行していない。  
そのため、実行可能と判別可能は同じではない。

報告内に失敗の印があることは評価できる。  
だが、その印を製品動作の証拠にはできない。  
各欄が示す範囲を超えて読まないことが必要である。

正常終了は処理単位の状態を説明する。  
usable_runsは利用可能と数えた実行を説明する。  
どちらも元の質問への回答を単独では証明しない。

## 設定変更は判別できる証拠がそろうまで保留する

正常終了と回答済みは、証拠の種類で見分けられる。  
質問に合う資料があり、動作を区別できる必要がある。  
その検証がなければ、結果は判別保留として読む。

Google-Extendedでは専用のblocks一覧が必要だった。  
空の一覧では制御範囲を比べられない。  
6個のHTTP 200も代わりの証拠にはならない。

Codexでは実際の読み方を区別する証拠が必要だった。  
境界の算数だけでは動作を選べない。  
無関係なHTMLの検索結果も判断材料にならない。

**自動点検を作る側:** 命令が失敗していないか、対象資料を取れたか、その結果で質問に答えられるかを確かめる。条件を満たさない場合は、usable_runsとは別に「判別できなかった」と記録する。処理の終了状態、報告の冒頭、その後の集計にも記録する。

**報告を使う側:** 2つの実験のhits 0/3や空の一覧は、機能がない証拠として扱わない。正しい資料を使って調べ直し、動作を見分けられるまでは、設定変更の根拠にしない。

この読み方なら、処理の記録を捨てずに利用できる。  
同時に、未確認の製品動作を確定せずに済む。  
判断基準は終了表示ではなく、質問に合う証拠である。

## この記事が確認できなかったこと

- 実際のクローラーがrobots.txt規則を守るかは測定していない。差を比べるための遮断一覧が空だった。6個のUser-agent名で受けたHTTP 200は、実際のクローラーが規則を守る証拠ではない。robots.txtが唯一の制御手段である証拠でもない。

- Google-Extendedがtrainingとgroundingを同じ名前で制御するかは確認していない。groundingは、回答作成で検索資料を使うことを指す。空の一覧とFalseは、その機能がないという判定ではない。

- /tmp/git_robots.txtが0行だった理由は確認していない。読み込み先の誤りか、実際の空ファイルかは分からない。保存先の原本や配布状態の差へ広げて解釈しない。

- Codexが32 KiBを超えるAGENTS.mdをバイト単位で切るかは確認していない。ファイル全体を飛ばすかも確認していない。印の位置と算数は、実際のCodex読み取り結果ではない。

- Fetch・Sendが命令として扱われたnot foundログはある。最終的な終了コードもある。しかし、命令を実行したプログラムの全文や、エラーが表に出なくなった書き方は示されていない。2つの名前が、命令を実行する仕組みに最初から備わる命令や、特別な役割を持つ語なのかは確定しない。

- 空の一覧と検索の適中0が常に失敗とは限らない。この記事の2つの実験では、対象資料と検査の有効性を確認できなかった。そのため、元の質問には答えられなかった。

- 報告にはusable_runsと判別失敗を説明するboundaryがある。失敗が検討時に初めて分かったかは確認していない。後続の集計や意思決定へ誤って渡ったかも確認していない。

- 参考資料1から4までの検証状態は、すべて未確認を意味するunconfirmedである。URL自体を実験ログや製品動作の検証根拠にはしない。特に参考資料4をCodex実装の権威ある根拠には使わない。

- 時期による提供会社別の名前体系の変化は範囲外である。点検全体での失敗頻度も範囲外である。改善に必要な費用も確認していない。

- **この判断が覆る条件:** 同じ実行から、正しい文書やプログラムの記述が見つかる必要がある。実際の動作を見分ける証拠も加われば、判別できなかったという判断を修正する。回答できなかった実行が最終成功集計から除外済みなら、失敗の伝達不足という判断も修正する。
