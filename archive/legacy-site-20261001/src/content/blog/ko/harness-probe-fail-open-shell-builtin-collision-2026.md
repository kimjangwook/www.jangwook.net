## 설정을 바꾸기 전에 보고서가 무엇을 확인했는지 묻습니다

AI가 만든 점검 보고서를 받았다고 가정해 보겠습니다.  
보고서에는 ‘정상 종료’라고 적혀 있습니다.  
그 옆에는 ‘찾은 항목 0개’라는 결과도 있습니다.

이 보고서만 보고 사이트 설정을 바꿔도 될까요?  
AI가 읽을 문서를 줄여도 되는지도 판단하기 어렵습니다.  
정상 종료라는 표현이 확신을 주기 때문입니다.

하지만 정상 종료는 처리 절차에 관한 표시일 수 있습니다.  
검사 프로그램이 마지막 단계까지 갔다는 뜻일 수 있습니다.  
원래 질문의 답을 찾았다는 뜻과는 다릅니다.

Google-Extended는 구글의 AI용 자료 이용 규칙을 지정하는 이름입니다.
이 실험에서는 해당 설정의 효과를 물었습니다.  
robots.txt는 방문 프로그램에 규칙을 알리는 파일입니다.  
Google-Extended 전용 규칙이 어떤 범위를 제어하는지 물었습니다.

Codex는 코딩 작업을 돕는 AI 도구입니다.
이 실험에서는 Codex가 문서를 읽는 방식을 물었습니다.  
AGENTS.md는 Codex에 작업 지침을 전달하는 문서입니다.  
KiB는 파일 크기를 세는 단위입니다.
이 문서가 32 KiB를 넘을 때 어떻게 처리되는지 물었습니다.

두 질문에 답하려면 실제 대상 자료가 필요합니다.  
그 자료에서 원하는 정보를 찾을 수 있어야 합니다.  
마지막에는 서로 다른 동작을 구별할 결과도 필요합니다.

실행 완료와 자료 확보는 같은 단계가 아닙니다.  
자료 확보와 동작 판별도 서로 다른 단계입니다.  
각 단계를 따로 확인해야 결론을 믿을 수 있습니다.

따라서 보고서에서 먼저 볼 것은 종료 표시가 아닙니다.  
검사 대상이 올바르게 확보됐는지를 봐야 합니다.  
그 결과로 원래 질문에 답할 수 있는지도 확인할 필요가 있습니다.

보고서가 정상적으로 끝났다는 표시가 있을 수 있습니다.  
그렇더라도 답을 알아냈다는 증거는 별도로 필요합니다.

## robots.txt 검사에는 성공 응답과 명령 오류가 함께 남았습니다

첫 실험은 배포된 robots.txt를 읽으려 했습니다.  
그 안에서 크롤러별 이름을 찾는 절차였습니다.  
크롤러는 웹 문서를 자동으로 요청하는 프로그램입니다.

먼저 정규식으로 User-agent 이름을 수집했습니다.
이처럼 규칙 적용 대상을 나타내는 이름을 이 검사에서는 토큰이라고 부릅니다.  
정규식은 일정한 글자 모양을 찾는 검색 규칙입니다.  
User-agent는 요청 프로그램이 자신을 밝히는 이름입니다.

파일에서 이름을 추려 낸 결과는 다음과 같았습니다.

`All tokens: ['*'] / Google tokens: [] / OpenAI tokens: [] / Anthropic tokens: []`

`*`는 파일을 요청하는 모든 프로그램에 규칙을 적용한다는 표시입니다.  
반면 제공사별 목록은 모두 비어 있었습니다.  
배포된 파일에서 전용 토큰을 잡지 못한 결과입니다.

이 검사는 3번 실행됐습니다.  
기록은 `hits 0/3, exit 0,0,0`이었습니다.  
검색 적중은 3번 모두 없었습니다.  
종료 코드는 프로그램이 끝난 상태를 숫자로 나타낸 값입니다.
이 값은 3번 모두 0이었습니다.

그다음에는 6개 이름으로 요청을 보냈습니다.  
HEAD와 GET 요청을 사용했습니다.  
HEAD는 본문 없이 응답 정보만 받는 요청입니다.  
GET은 해당 주소의 자료를 요청하는 방식입니다.

관찰된 응답은 모두 같았습니다.

`Google-Extended, Googlebot, GPTBot, ClaudeBot, OAI-SearchBot, Mozilla/5.0 모두 HTTP 200을 반환했습니다.`

HTTP 200은 요청에 성공 응답이 왔다는 상태입니다.  
이 6개 이름으로 보낸 요청은 응답 단계에서 거부되지 않았습니다.  
이 결과의 검색 적중 기록은 `hits 0/3`이었습니다.

그러나 HTTP 200만으로 규칙 준수를 알 수는 없습니다.  
요청한 주소가 응답했다는 사실만 확인됐기 때문입니다.  
실제 크롤러가 규칙을 지켰는지는 다른 질문입니다.

같은 보고서에는 명령 실행 오류도 남았습니다.  
Fetch와 Send가 실행할 명령으로 해석됐습니다.  
3번의 실행 모두에서 찾을 수 없다는 오류가 났습니다.

정확한 로그는 다음과 같습니다.

`bash: Fetch: command not found / bash: Send: command not found (exit 0,0,0)`

중간에는 명령을 찾지 못했다는 오류가 있습니다.  
그런데 최종 종료 코드는 0으로 기록됐습니다.  
하네스는 이런 검사를 반복하고 결과를 모으는 도구입니다.

따라서 이 보고서에는 서로 다른 정보가 섞여 있습니다.  
전용 토큰 목록은 비어 있었습니다.  
6개 요청에는 모두 HTTP 200이 돌아왔습니다.  
Fetch와 Send는 명령으로 실행되다가 실패했습니다.  
그럼에도 전체 출력은 만들어졌습니다.

각 출력으로 확인할 수 있는 내용도 서로 다릅니다.  
빈 토큰 목록은 파일 안에서 찾은 이름을 보여줍니다.  
HTTP 200은 요청에 대한 응답 상태를 보여줍니다.  
명령 오류는 검사 절차 일부가 실패했음을 보여줍니다.

이 값들을 모두 성공의 증거로 보기는 어렵습니다.  
하나가 정상이어도 다른 하나는 실패할 수 있습니다.  
종료 코드 0도 이 차이를 자동으로 설명하지 않습니다.

이 보고서에는 빈 이름 목록과 요청 성공 기록이 함께 있습니다.
명령 오류도 있어, 각각 무엇을 뜻하는지 따로 볼 필요가 있습니다.

## 실제 파일과 저장소 파일의 비교는 성립하지 않았습니다

다음 검사는 실제 사이트의 robots.txt와 비교하려 했습니다.  
비교 대상은 작업용 컴퓨터의 Git 저장소에 있는 robots.txt였습니다.
Git 저장소는 파일과 수정 이력을 보관하는 곳입니다.
하지만 비교 검사는 3번 모두 종료 코드 1로 끝났습니다.

기록은 다음과 같습니다.

`live_vs_git_robots — hits=0/3 usable=0/3 — exit 1,1,1`

`usable`은 판별에 쓸 수 있는 실행을 뜻합니다.  
이 기록에서는 쓸 수 있는 실행이 하나도 없었습니다.  
즉, `usable 0/3`이므로 비교가 성립하지 않았습니다.

실패한 실행에도 임시 파일은 남았습니다.  
줄 수 기록은 다음과 같습니다.

`/tmp/live_robots.txt는 22줄, /tmp/git_robots.txt는 0줄`

실제 사이트 쪽 임시 파일에는 22줄이 있었습니다.  
저장소 쪽 임시 파일에는 내용이 없었습니다.  
그러나 왜 0줄이 됐는지는 확인되지 않았습니다.

파일 경로를 잘못 찾은 것인지는 확인하지 못했습니다.  
원래 저장소 파일이 비어 있었는지도 모릅니다.  
따라서 22줄과 0줄만으로 배포 차이를 말할 수 없습니다.

별도의 Google-Extended 검사도 있었습니다.  
이 검사는 관련 규칙을 모아 놓은 부분인 블록을 추려 내려 했습니다.  
또 문서에 2가지 용도가 함께 있는지도 검사했습니다.

기록의 ‘training’은 AI 학습용을 뜻합니다.
‘grounding’은 답변을 만들 때 검색 자료를 활용하는 용도를 뜻합니다.  
관찰 결과는 다음과 같습니다.

`Google-Extended blocks 목록이 비어 있고, 문서가 training과 grounding을 동시에 포함하는지 여부는 False로 확인되었습니다.`

이 검사의 기록은 `hits 0/3`이었습니다.  
Google-Extended 블록 목록 자체가 비어 있었습니다.  
비교할 내용이 없어, 하나의 이름으로 두 용도를 함께 제어하는지도 확인하지 못했습니다.

여기서 False는 검사 조건에 맞지 않았다는 결과입니다.  
제품 기능이 없다는 직접 증거는 아닙니다.  
검사 대상이 비어 있어도 False가 나올 수 있습니다.

결국 실제 사이트 파일과 저장소 파일의 비교 결과는 판별에 쓸 수 없었습니다.  
별도 검사에도 판별할 블록이 없었습니다.  
두 출력 모두 원래 질문에 답하지 못했습니다.

파일 줄 수가 다르다는 사실만으로 실제 사이트와 저장소의 차이를 확정할 수는 없습니다.
False라는 출력만으로 Google-Extended의 제어 범위를 알 수도 없습니다.

## Codex 검사는 문서 처리 방식 대신 검색과 산수만 확인했습니다

Codex 실험은 AGENTS.md의 길이를 살펴봤습니다.  
질문은 32 KiB 초과 문서의 처리 방식이었습니다.  
일부만 읽는지 전체 파일을 건너뛰는지 구별하려 했습니다.

문서의 설명과 실제 작동 방식을 적은 프로그램 코드를 찾는 검사가 실행됐습니다.
각 검사는 3번 모두 실행 가능한 것으로 집계됐습니다.  
종료 코드도 정상으로 기록됐습니다.

상세 기록은 다음과 같습니다.

`doc-wording — hits=0/3 usable=3/3 — exit 0,0,0; source-impl — hits=0/3 usable=3/3; boundary-math — hits=0/3 usable=3/3`

`doc-wording`은 문서 표현을 찾는 검사였습니다.  
`source-impl`은 실제 처리 방식을 담은 프로그램 코드를 찾는 검사였습니다.  
두 검사 모두 검색 적중이 `0/3`이었습니다.

`boundary-math`도 적중은 `0/3`이었습니다.  
그러나 실행 가능 횟수는 `3/3`으로 기록됐습니다.  
여기서 실행 가능과 판별 가능은 같지 않습니다.

수집된 인용도 질문과 관련이 없었습니다.  
가져온 내용은 문서 본문이 아니었습니다.  
HTML은 웹페이지의 내용과 구성을 적는 형식입니다.
수집된 것은 사이트 이동 메뉴를 나타내는 HTML이었습니다.

실제 수집 문자열은 다음과 같습니다.

`k hover:text-default hover:bg-primary-ghost-hover ' data-mobile-nav-link> Site tools (WebMCP)`

WebMCP라는 메뉴 문구가 포함돼 있습니다.  
하지만 AGENTS.md 처리 방식의 설명은 아닙니다.  
소스에서 실제 처리 코드를 찾은 결과도 아닙니다.

교과서 본문에서 답을 찾아야 하는데 목차만 읽었다고 가정해 보겠습니다.
목차에서 답을 못 찾았다고 본문에도 답이 없다고 할 수는 없습니다. 이 검사도 대상 문서 대신 메뉴를 읽었으므로, 적중 0을 기능 부재로 해석할 수 없습니다.

문서 크기 기준의 바로 아래·위와 기준값에 맞춰 3가지 크기의 파일을 만들었습니다.  
각 파일 끝부분에는 위치 확인용 데이터를 넣었습니다.
바이트는 데이터 크기를 세는 단위입니다.
기록에 나오는 ‘카나리 바이트’는 이 확인용 표식을 뜻합니다.

관찰된 숫자는 다음과 같습니다.

`32767, 32768, 32769 바이트 파일에서 카나리 바이트가 각각 32763, 32764, 32765에 위치하며 32768 <= 32KiB ? true`

파일 크기는 32767, 32768, 32769바이트였습니다.  
표식 위치는 32763, 32764, 32765였습니다.  
파일 크기에 따라 표식 위치가 함께 달라졌습니다.

또 `32768 <= 32KiB ? true`를 확인했습니다.  
이 결과는 크기 비교 산수가 참이라는 뜻입니다.  
Codex가 해당 파일을 읽었다는 뜻은 아닙니다.

실제 처리 방식을 구별하려면 동작 증거가 필요합니다.  
일부만 읽었을 때 나타나는 결과가 있어야 합니다.  
전체를 건너뛸 때와 다른 결과도 관찰해야 합니다.

이번 크기 비교 검사는 실제 읽기 방식의 차이를 시험하지 않았습니다.  
파일 크기와 표식 위치만 계산했습니다.  
따라서 잘라 읽기와 전체 건너뛰기를 구별하지 못했습니다.

실행 횟수와 파일 크기 계산만으로는 Codex의 문서 처리 방식을 알 수 없습니다.
문서를 일부만 읽는지, 파일 전체를 건너뛰는지는 아직 확인되지 않았습니다.

## 실행 완료와 답 획득은 검사 부족으로 분리됐습니다

Fetch·Send가 명령으로 해석돼 실패한 뒤에도 처리는 이어졌습니다.
자료가 비었거나 엉뚱한 HTML이어도 답을 낼 수 없는 상태로 걸러 내지 못했습니다.
그래서 실행은 끝났지만 원래 질문에는 답하지 못했습니다.

셸은 입력한 명령을 해석하고 실행하는 프로그램입니다.
다만 정확한 셸 구성은 제공되지 않았습니다.  
어떤 구문이 오류를 가렸는지도 확인되지 않았습니다.  
따라서 세부 원인을 특정 구문으로 확정할 수 없습니다.

관찰된 문제는 적어도 3가지로 나눌 수 있습니다.  
첫째, 실행할 명령을 찾지 못한 오류가 있었습니다.  
둘째, 필요한 자료가 비어 있거나 잘못 수집됐습니다.  
셋째, 답을 판별할 수 있는지 검사가 부족했습니다.

이 구분은 수정 지점을 찾는 데 중요합니다.  
명령 오류만 고쳐도 빈 자료 문제는 남을 수 있습니다.  
자료만 확보해도 판별 기준이 없으면 답을 못 냅니다.

종료 상태도 별도의 문제입니다.  
중간 실패가 최종 상태에 반영되지 않을 수 있습니다.  
보고서 출력이 생겼다고 판별까지 성공한 것은 아닙니다.

빈 목록 자체가 항상 오류인 것은 아닙니다.  
실제로 대상에 항목이 없으면 올바른 결과일 수 있습니다.  
다만 대상 자료가 맞다는 확인이 먼저 필요합니다.

검색 적중 0도 같은 방식으로 읽어야 합니다.  
올바른 문서에서 찾았다면 의미가 있을 수 있습니다.  
무관한 HTML에서 찾았다면 결론을 만들 수 없습니다.

명령 실행 오류와 잘못된 자료 수집은 서로 다른 문제입니다.
질문에 답할 수 있는지 확인하는 검사도 따로 필요합니다.

## 종료 코드와 usable_runs가 알려주는 범위는 제한적입니다

가장 강한 반론부터 인정할 필요가 있습니다.  
종료 코드 0은 해당 계산의 정상 실행을 뜻할 수 있습니다.  
검색 명령이 끝까지 실행됐다는 표시일 수도 있습니다.

실제로 모든 실패가 숨겨진 것도 아닙니다.  
파일 비교에는 `usable 0/3`이 기록됐습니다.  
종료 코드도 `1,1,1`로 분명하게 남았습니다.

보고서에는 확인할 수 있는 범위를 설명하는 항목도 있었습니다.
원문에서는 이 항목을 ‘boundary’라고 부릅니다.
여기에는 두 실험이 답을 확정하지 못했다는 설명이 있었습니다.

따라서 보고서 전체가 무가치하다고 할 수는 없습니다.  
개별 명령의 실행 상태를 확인하는 데 쓸 수 있습니다.  
어디에서 자료가 비었는지도 일부 보여줍니다.

그러나 반론이 옳은 범위는 여기까지입니다.  
개별 명령의 정상 실행은 제품 동작 검증과 다릅니다.  
실행 가능 횟수도 질문에 답했는지 보장하지 않습니다.

Codex 검사에서는 `usable 3/3`이 기록됐습니다.  
그런데 수집 인용은 무관한 HTML이었습니다.  
문서와 소스 검색도 모두 `hits 0/3`이었습니다.

기준 크기와 파일 크기를 비교하는 계산도 정상적으로 끝났습니다.  
하지만 실제 Codex 읽기 동작은 실행하지 않았습니다.  
정상 실행과 동작 판별이 분리된 사례입니다.

Google-Extended 검사도 비슷합니다.  
HTTP 200은 응답 성공을 알려줍니다.  
전용 블록이 빈 상태에서는 제어 범위를 못 잽니다.

중요한 기준은 표시 하나가 아닙니다.  
올바른 자료와 구별 가능한 결과가 함께 있어야 합니다.  
그때에만 원래 질문에 답했다고 말할 수 있습니다.

보고서에서 실행 상태에 관한 정보는 참고할 수 있습니다.
다만 정상 종료나 실행 횟수만으로 제품 동작까지 확정하기는 어렵습니다.

## 설정 변경 전에는 판별 가능한 증거를 확인해야 합니다

도입에서 제기한 질문에는 기준을 나눠 답할 수 있습니다.  
정상 종료는 실행 절차의 상태로 읽어야 합니다.  
답을 알아냈다는 판단에는 별도 증거가 필요합니다.

설정을 바꾸기 전에는 3가지를 확인해야 합니다.  
명령 오류 없이 필요한 단계가 실행됐는지 봅니다.  
질문에 맞는 대상 자료를 확보했는지도 봅니다.  
서로 다른 동작을 구별할 값이 있는지도 봅니다.

이 기준을 적용하는 방법은 도구를 만드는 쪽과 사용하는 쪽이 다릅니다.
각각 다음 사항을 살펴볼 수 있습니다.

- 자동 점검 도구를 만드는 쪽은 명령 오류와 자료 확보 여부를 함께 검사할 필요가 있습니다. 결과가 원래 질문에 답하는지도 확인해야 합니다. 답하지 못했다면 실행 가능 횟수와 별도로 기록하는 방식이 도움이 됩니다. 종료 상태와 보고서 첫 문장, 이후 집계에도 그 차이를 남길 수 있습니다.
- 결과를 사용하는 쪽에서는 두 실험의 ‘적중 0/3’과 빈 목록만으로 기능이 없다고 보기 어렵습니다. 설정을 바꾸려면 올바른 자료로 다시 확인한 결과가 필요합니다. 그 결과로 실제 동작을 구별할 수 있을 때 설정 변경의 근거로 삼을 수 있습니다.

첫 번째 행동은 판별 불가를 성공 집계에서 뺍니다.  
실행 완료와 답 획득을 다른 상태로 기록합니다.  
후속 집계도 그 차이를 유지할 수 있습니다.

두 번째 행동은 성급한 설정 변경을 막습니다.  
빈 목록은 기능 부재가 아니라 미판별일 수 있습니다.  
적중 0도 잘못된 자료에서 나온 값일 수 있습니다.

이 기준은 정상 종료를 무시하자는 뜻이 아닙니다.  
정상 종료가 답하는 범위를 정확히 읽자는 뜻입니다.  
설정 변경에는 원래 질문에 맞는 증거가 필요합니다.

보고서를 설정 변경의 근거로 삼으려면 질문에 맞는 자료가 필요합니다.
그 자료로 실제 동작을 확인한 결과도 있어야 합니다.

## 이 글이 확인하지 못한 것

- 실제 크롤러가 robots.txt 규칙을 지키는지는 측정하지 못했습니다. 차단 목록이 비어, 차단 여부를 비교할 대상이 없었습니다. 6개 사용자 에이전트 이름으로 받은 HTTP 200도 규칙 준수의 증거가 아닙니다. robots.txt가 유일한 통제 수단이라는 증거도 아닙니다.

- Google-Extended가 AI 학습과 답변용 검색 자료 활용을 함께 제어하는지는 확인하지 못했습니다. 하나의 규칙 적용 이름으로 두 용도를 모두 조절하는지 확인되지 않았다는 뜻입니다. 빈 목록과 False는 해당 기능이 없다는 판정이 아닙니다.

- `/tmp/git_robots.txt`가 0줄이었던 이유는 확인하지 못했습니다. 경로 오류인지 실제 빈 파일인지 알 수 없습니다. 저장소 원본이나 배포 상태의 차이로 확대 해석하지 않습니다.

- Codex가 32 KiB를 넘는 AGENTS.md를 바이트 단위로 자르는지는 확인하지 못했습니다. 파일 전체를 건너뛰는지도 확인하지 못했습니다. 표식 바이트 위치와 산수는 실제 Codex 읽기 결과가 아닙니다.

- Fetch·Send가 명령으로 해석돼 ‘명령을 찾을 수 없음’ 오류가 난 기록은 있습니다. 최종 종료 코드도 남아 있습니다. 하지만 정확한 셸 코드와 오류가 가려진 구문은 제공되지 않았습니다. 두 이름이 셸에 기본으로 들어 있는 명령인지는 확정하지 않습니다. 특별한 용도로 정해 둔 단어인지도 확정하지 않습니다.

- 빈 목록과 검색 적중 0이 언제나 실패인 것은 아닙니다. 이 글의 두 실험은 대상 자료 확보가 확인되지 않았습니다. 검사 유효성도 확인되지 않아 원래 질문에 답할 수 없었습니다.

- 보고서에는 실행 가능 횟수를 나타내는 ‘usable_runs’가 이미 있습니다. 답을 확정하지 못한 범위를 설명하는 ‘boundary’도 있습니다. 실패가 검토 시점에 처음 발견됐는지는 확인하지 못했습니다. 실제 후속 집계나 결정에 잘못 전달됐는지도 확인하지 못했습니다.

- 참고 자료 1, 2, 3, 4의 검증 상태는 모두 ‘미확인’입니다. 참고 자료의 주소를 실험 기록이나 제품 동작의 검증 근거로 쓰지 않습니다. 특히 출처 4를 Codex 구현의 권위 있는 근거로 사용하지 않습니다.

- 여러 시점의 제공사별 토큰 체계 변화는 범위 밖입니다. 하네스 전반의 실패 빈도도 다루지 않습니다. 개선 비용 역시 이 글에서 확인하지 않았습니다.

- 같은 실행에서 올바른 문서와 소스가 추가로 발견될 수 있습니다. 실제 동작을 구분한 증거가 나오면 판별 실패 판단을 수정해야 합니다. 답을 못 낸 실행이 최종 성공 집계에서 제외됐다고 확인될 수도 있습니다. 이 경우 실패 전달 부족에 관한 판단도 수정해야 합니다.
