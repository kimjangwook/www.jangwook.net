## 같은 사진을 세 곳에 넣으면, 대체 텍스트도 같아야 할까요?

온라인 매장의 재킷 사진을 떠올려 보겠습니다. 상품 상세 페이지에서는 앞면의 모양과 색상을 보여줍니다. 상품 목록에서는 사진을 누르면 상세 페이지로 이동합니다. 안내 페이지에서는 색상과 앞면 특징을 글로 이미 설명한 뒤 같은 사진을 덧붙입니다.

세 곳에서 사용하는 파일은 같지만 이용자가 해야 할 일은 다릅니다. 상세 페이지에서는 상품의 특징을 알아야 합니다. 목록에서는 링크가 어디로 이동하는지 알아야 합니다. 안내 페이지에서는 본문에 있는 설명을 읽고, 같은 정보를 불필요하게 다시 듣지 않을 수 있어야 합니다. 따라서 사진 파일에 대체 텍스트 하나를 저장하고 모든 위치에 재사용하는 방식만으로는 충분하지 않을 수 있습니다.

이번 글은 WCAG 2.2의 **1.1.1 비텍스트 콘텐츠(Non-text Content), 수준 A**를 다룹니다. 상품 설명과 와이어프레임, 예제 수치는 이해를 돕기 위한 가상의 사례입니다. 뒤에서는 공개된 개요에 프롬프트를 적용한 실제 실행 결과도 살펴봅니다.

## 1.1.1이 요구하는 것은 같은 목적을 수행하는 텍스트 대안입니다

기준은 사용자에게 제시되는 비텍스트 콘텐츠에 그 콘텐츠와 동등한 목적을 수행하는 텍스트 대안을 요구합니다. 사진이나 아이콘뿐 아니라 도표, SVG, 의미 있는 배경 이미지 등도 검토 대상이 될 수 있습니다. 특정 HTML 속성의 존재만 요구하는 기준으로 읽으면 적용 범위를 놓치기 쉽습니다.

`alt`는 HTML의 `img` 요소에 대안을 제공하는 대표적인 방법입니다. 텍스트 대안은 화면을 보기 어려운 이용자가 정보를 읽거나 듣는 경로를 제공합니다. 조작 요소라면 이름을 통해 어떤 행동을 실행할지도 알 수 있어야 합니다. SVG나 캔버스처럼 표현 기술이 다르면 대안을 연결하는 구현 방법도 달라집니다.

실무에서는 다음 두 가지를 나누어 확인하면 좋습니다. 하나는 이미지가 전달한 정보나 기능이 텍스트로 표현되어 있는지입니다. 다른 하나는 그 텍스트가 실제 요소와 연결되어 이용자에게 전달되는지입니다. 글을 잘 써도 연결이 끊어져 있으면 대안을 사용할 수 없습니다. 반대로 속성이 연결되어 있어도 내용이 파일명이나 잘못된 설명이면 목적을 전달하지 못합니다.

W3C의 Understanding 문서와 이미지 튜토리얼은 이 판단을 설명하는 자료입니다. WCAG의 요구사항과 해설의 구현 예시를 구분해야 하며, 아래의 사례별 절차는 이를 팀의 작업에 적용하기 위한 제안입니다.

## 먼저 이미지가 맡은 일을 정합니다

이미지를 잠시 가리고 남은 화면을 생각해 보면 판단이 쉬워집니다. 이용자가 정보를 얻거나 작업을 끝내는 데 무엇이 없어지는지 기록합니다. 이미지가 보기 좋다는 이유만으로 장식이라고 분류하지 않고, 정보를 담고 있다는 이유만으로 모든 시각적 세부를 설명하지도 않습니다.

| 사용 상황 | 이용자에게 남겨야 할 것 | 대안의 방향 |
| --- | --- | --- |
| 상품의 특징을 보여주는 사진 | 현재 선택한 상품의 구별에 필요한 특징 | 문맥에 맞는 짧은 설명 |
| 내용이 이미지에만 있는 안내 배너 | 행사 조건과 기간 등의 실제 문구 | 읽을 수 있는 텍스트로 같은 정보 제공 |
| 이미지가 유일한 내용인 링크 | 이동할 대상과 목적 | 링크의 이름으로 목적 전달 |
| 아이콘만 있는 버튼 | 실행할 작업 | 버튼의 접근 가능한 이름 제공 |
| 그래프·지도·흐름도 | 값, 관계, 방향, 읽는 순서 등 핵심 정보 | 짧은 식별 설명과 상세 대안 연결 |
| 주변 텍스트와 완전히 중복되는 그림 | 이미 제공된 정보를 유지하며 반복 줄이기 | 다른 기능이 없다면 빈 `alt` 등 검토 |

이 표의 마지막 항목은 조건부입니다. 사진 옆에 상품명만 있다고 해서 색상이나 구별에 필요한 특징까지 제공됐다고 볼 수는 없습니다. 링크 안에 있는 그림을 숨길 때는 링크의 이름이 남는지도 함께 봅니다.

### 정보 이미지: 무엇을 식별하거나 이해해야 하나요?

다음은 색상과 앞면 모양을 확인하는 상품 상세 페이지의 예입니다.

```html
<h2>클래식 재킷</h2>
<img src="jacket-front.jpg"
     alt="짙은 회색 재킷 앞면, 단추 두 개와 양쪽 덮개 주머니">
```

이 설명은 해당 사진에 실제로 보이는 특징을 전달합니다. 사진만 보고 확인할 수 없는 소재, 방수 성능, 착용감은 덧붙이지 않습니다. 상품 설명에 소재가 기재되어 있더라도 이미지가 그것을 보여주는지와 제품 정보로 확인한 사실인지는 구분합니다.

대안은 용도에 따라 달라질 수 있습니다. 색상을 고르는 화면에서 색상 이름이 이미지 밖의 텍스트로 충분히 제공된다면 같은 문구를 무조건 반복할 필요는 없습니다. 봉제 위치를 비교하는 안내라면 색상보다 봉제선의 차이를 설명하는 편이 목적에 맞습니다. `alt`를 길게 쓰는 것과 충분히 쓰는 것은 다릅니다.

문맥이 바뀌면 대안도 다시 검토합니다. 같은 이미지를 기사 본문에 옮겨 놓고 상품 페이지의 설명을 그대로 사용하면, 독자가 기사에서 알아야 할 내용을 전달하지 못할 수 있습니다.

### 장식과 중복: 빈 대안은 의도적으로 정보를 생략한 결과입니다

행사 조건이 본문에 모두 있으며 배경 사진이 분위기만 더하는 경우라면 다음처럼 처리할 수 있습니다.

```html
<img src="jacket-decoration.jpg" alt="">
<p>가을 재킷 행사: 10월 15일까지 일부 상품 10% 할인</p>
```

빈 문자열인 `alt=""`와 `alt` 속성을 아예 빼는 것은 다릅니다. 빈 대안은 이 이미지를 읽을 필요가 없다는 의도를 표현합니다. 속성을 누락하면 일부 스크린 리더가 파일명 등을 읽을 수 있습니다.

다만 위 예에서 사진 자체에 별도의 할인 조건이 적혀 있다면 본문에 그 조건이 있는지 확인해야 합니다. 그림을 숨겨도 된다는 판단은 이미지가 예쁘거나 작다는 사실에서 나오지 않습니다. 전달할 정보가 없거나 다른 경로로 충분히 제공됐다는 근거가 있어야 합니다.

캡션이 있다고 자동으로 빈 대안을 선택하지도 않습니다. 캡션이 사진의 출처만 밝히는지, 이미지의 핵심 정보까지 제공하는지, 그 내용으로 접근할 수 있는지를 확인합니다. 반복을 줄이는 목적과 정보 누락을 피하는 목적을 함께 고려합니다.

## 링크와 버튼은 생김새보다 조작 목적을 전달합니다

상품 사진만 있는 링크에는 이동 목적을 알 수 있는 이름이 필요합니다.

```html
<a href="/products/classic-jacket">
  <img src="jacket-front.jpg" alt="클래식 재킷 상세 보기">
</a>
```

이 링크에서 이용자가 먼저 알아야 할 것은 재킷의 주머니 수보다 이동할 상품입니다. 사진 자체의 세부 정보가 구매 판단에 꼭 필요하다면 주변 상품 설명 등에서 추가로 제공하는 방식을 검토합니다.

같은 링크 안에 상품 이름이 실제 텍스트로 이미 있다면 구성은 달라집니다.

```html
<a href="/products/classic-jacket">
  <img src="jacket-front.jpg" alt="">
  <span>클래식 재킷 상세 보기</span>
</a>
```

이 예에서는 링크의 텍스트가 목적을 전달하고 이미지는 추가 정보를 담지 않는다고 가정합니다. 이미지가 같은 이름의 상품 중 다른 색상을 구별한다면 그 차이는 별도로 제공해야 합니다. 서로 떨어진 두 링크에 같은 목적을 반복해서 넣는 대신 이미지와 텍스트를 하나의 링크로 묶을 수 있는지도 검토할 만합니다.

아이콘만 있는 버튼도 같은 방식으로 생각할 수 있습니다. 돋보기의 모양을 설명하는 것보다 어떤 검색을 실행하는지 알려주는 이름이 필요합니다.

```html
<!-- 수정 전: 다른 이름 제공 수단이 없는 버튼이라고 가정합니다. -->
<button type="button">
  <img src="search.svg" alt="">
</button>

<!-- 수정 후: 버튼에 목적을 주고 중복된 아이콘 설명은 숨깁니다. -->
<button type="button" aria-label="상품 검색">
  <img src="search.svg" alt="">
</button>
```

<figure class="learning-figure"><img src="/images/accessibility/non-text-content/ko/02-button-name-606d4b922f26.svg" alt="같은 돋보기 버튼의 수정 전후 비교. 수정 전에는 접근 가능한 이름이 비어 있고, 수정 후에는 버튼의 aria-label로 상품 검색이라는 이름이 제공됩니다."/><figcaption>도식 02. 화면의 아이콘은 같지만, 조작 목적을 전달하는 이름이 달라집니다. 표시한 이름은 예제 코드가 의도하는 결과이며, 실제 구현에서는 브라우저 접근성 트리로 확인합니다.</figcaption></figure>

이미지의 `alt`를 버튼 이름으로 사용하는 다른 구현도 가능합니다. 여러 방법을 중복해서 덧붙이기보다 한 가지 이름 제공 방식이 의도대로 전달되는지 확인합니다. `aria-label` 등이 지정되어 있으면 보이는 텍스트나 이미지 설명과 계산 결과가 달라질 수 있으므로, DOM의 문자열만 나열하지 않고 최종 접근 가능한 이름을 확인합니다.

버튼의 역할·상태·키보드 조작은 4.1.2와 2.1.1 등에서 추가로 다룹니다. 이번 항목에서 이름을 수정했다고 버튼의 접근성 전체를 평가한 것으로 처리하지 않습니다.

## 복잡한 그래프는 한 문장의 alt로 끝내지 않습니다

교육용 그래프에 1월 120건, 2월 80건, 3월 160건의 문의 수가 표시되어 있다고 가정해 보겠습니다. `alt="월별 문의 그래프"`는 무엇을 그렸는지는 알려주지만 값과 변화를 전달하지 않습니다. 이 값을 비교해야 하는 이용자에게는 상세 정보가 필요합니다.

짧은 대안은 그래프를 식별하고 상세 설명의 위치를 안내할 수 있습니다. 본문에는 핵심 변화와 데이터 표를 제공합니다.

```html
<img src="inquiries.png"
     alt="1~3월 문의 수. 월별 값과 추세는 아래 설명과 표에 있습니다.">
<p>문의 수는 1월 120건에서 2월 80건으로 줄고,
   3월 160건으로 늘었습니다.</p>
<table>
  <caption>1~3월 문의 수, 단위: 건</caption>
  <tr><th scope="col">월</th><th scope="col">문의 수</th></tr>
  <tr><th scope="row">1월</th><td>120</td></tr>
  <tr><th scope="row">2월</th><td>80</td></tr>
  <tr><th scope="row">3월</th><td>160</td></tr>
</table>
```

<figure class="learning-figure"><img src="/images/accessibility/non-text-content/ko/03-chart-alternative-40f98938855b.svg" alt="교육용 문의 그래프와 그 대안. 1월 120건, 2월 80건, 3월 160건을 그래프와 표로 제공하고, 2월 감소 뒤 3월 증가라는 변화를 문장으로 설명합니다."/><figcaption>도식 03. 그래프의 제목만 옮기는 대신, 이용자가 비교할 값과 추세를 제공합니다. 수치는 설명을 위한 가상 데이터입니다.</figcaption></figure>

표가 항상 유일한 대안은 아닙니다. 흐름도에서는 분기 조건과 다음 단계, 지도에서는 위치와 이동 경로, 조직도에서는 부서 간 관계가 핵심일 수 있습니다. 그림을 보지 않고도 본문이 요구하는 판단을 할 수 있는지로 상세 대안의 충분성을 검토합니다.

화면에서 수치를 읽기 어렵다면 AI가 추정한 값을 확정해서는 안 됩니다. 원본 데이터나 선명한 자료를 요청합니다. 원본 표가 있다는 사실과 이용자가 그 표에 접근할 수 있다는 사실도 다르므로, 상세 설명 링크와 연결 위치를 함께 확인합니다.

## 사진 외의 표현과 기준의 예외도 검토합니다

의미 있는 정보가 CSS 배경 이미지에만 있으면 `img[alt]` 목록을 검사하는 방식으로는 찾지 못합니다. 이미지 안에만 있는 안내 문구는 DOM의 텍스트와 비교해야 합니다. 읽어야 할 문구를 실제 텍스트로 제공할 수 있는지 검토하고, 이미지로 제공한 문구의 대안이 있는지도 확인합니다. `alt`를 추가했다고 이미지 속 텍스트에 대한 1.4.5의 별도 요구까지 해결되는 것은 아닙니다.

정보를 담은 SVG에는 그 정보의 대안이 실제로 연결되어야 합니다. 아이콘 버튼 안의 SVG를 장식으로 숨긴다면 버튼 자체의 이름은 남겨야 합니다. 캔버스에 그린 도표는 선명한 스크린샷만으로 충분하지 않으며, 텍스트 설명과 데이터 등 이용 가능한 대안을 확인합니다. 이 경우에도 특정 속성 하나를 붙였다는 이유로 통과시키지 않습니다.

1.1.1에는 다음과 같은 상황별 요구가 있습니다. 예외가 있다는 이유로 대안을 모두 생략하는 것으로 해석하지 않습니다.

| 상황 | 1.1.1에서 확인할 내용 |
| --- | --- |
| 시간 기반 미디어 | 적어도 내용을 식별하는 설명. 자막·해설 등의 상세 요구는 1.2에서 추가 검토 |
| 텍스트로 바꾸면 성립하지 않는 시험·연습 | 대상이 무엇인지 식별하는 설명. 실제로 시험 목적이 훼손되는 조건인지 확인 |
| 주로 특정 감각 경험을 제공하는 콘텐츠 | 적어도 식별하는 설명. 일반 정보 이미지를 이 조건으로 숨기지 않기 |
| CAPTCHA | 사람 확인 목적을 설명하는 대안과 다른 감각 방식의 대체 형태. 정답 공개가 대안이라는 뜻은 아님 |
| 순수 장식·시각적 서식·사용자에게 제시되지 않는 콘텐츠 | 보조 기술이 무시할 수 있도록 구현 |

화면에 보이지 않는 콘텐츠도 사용자에게 다른 방식으로 제시되거나 열린 메뉴 등에서 나타날 수 있습니다. 한 장의 닫힌 화면만으로 보이지 않는다는 예외를 적용하지 않고, 평가하는 상태와 이용 경로를 기록합니다.

## 멀티모달 AI에는 이미지와 코드, 문맥을 같은 대상으로 묶어 줍니다

대체 텍스트의 존재를 검사하는 것과 대안의 의미를 평가하는 것은 다른 작업입니다. 이미지 속 할인 문구가 대안에 빠졌는지, 사진 설명이 링크 목적에 맞는지, 상세 표가 그래프와 같은 내용을 전달하는지는 이미지와 문맥을 비교해야 합니다. 멀티모달 모델을 이 비교에 활용하는 평가를 설계할 수 있습니다.

이 설계에서는 이미지만 보고 설명을 생성하는 작업보다, 현재 대안이 이용자의 목적에 충분한지 평가하는 작업을 먼저 수행합니다. 자동 규칙 도구가 확인하지 못하는 의미를 검토하되, 모델의 응답을 실제 관찰·조작의 기록과 연결합니다. 뒤의 적용 사례에서는 실제 페이지 자료와 대조 조건으로 판정과 근거를 확인합니다.

<figure class="learning-figure"><img src="/images/accessibility/non-text-content/ko/04-evidence-flow-aee5800be0ff.svg" alt="요소 ID로 이미지, DOM, 접근성 트리, 페이지 문맥을 연결한 뒤 의미 비교, 근거 있는 판정, 개선과 동일 상태 재점검으로 이어지는 평가 흐름."/><figcaption>도식 04. 입력 자료를 같은 요소와 상태로 연결해야 비교 결과를 검증할 수 있습니다. 제안하는 평가 설계이며, 이 흐름 전체를 구현한 서비스나 실험 결과는 아닙니다.</figcaption></figure>

평가 자료는 다음처럼 준비합니다.

1. **페이지와 작업**: URL, 언어, 이용 목표, 확인할 상태를 적습니다. 상품 목록과 상세 페이지는 별도 상태로 구분합니다.
2. **시각 자료**: 페이지 전체 화면, 대상 이미지의 확대 자료, 원본 이미지 또는 그래프 데이터를 제공합니다. 전체 문맥과 세부 내용을 함께 볼 수 있게 합니다.
3. **DOM**: 대상 요소뿐 아니라 부모 링크·버튼, 주변 텍스트, 이름·설명에 참조되는 요소를 포함합니다. 이미지 누락이나 `aria-label` 등을 확인할 수 있는 범위가 필요합니다.
4. **접근성 자료**: 역할, 최종 계산된 이름·설명, 숨김 여부를 수집합니다. DOM에서 예상한 이름과 브라우저가 노출한 결과를 구분합니다.
5. **상태 연결**: 요소 ID, 수집 시각, 뷰포트와 로그인 조건 등을 붙입니다. 여러 상태의 스크린샷과 DOM을 섞으면 판정의 근거가 어긋납니다.

예를 들어 `E03`을 상품 검색 버튼의 ID로 정했다면, `E03-screen`은 화면, `E03-dom`은 코드, `E03-ax`는 접근성 트리, `E03-action`은 실제 동작 기록으로 연결할 수 있습니다. 파일 경로만 적었다고 모델이 파일을 읽었다고 간주하지 않고, 실제 첨부하거나 읽기 도구의 결과를 전달합니다.

입력에 따라 가능한 판단도 달라집니다. 화면만 있으면 시각 정보와 문제 후보를 찾을 수 있지만 실제 이름이나 숨김 처리를 확인하기 어렵습니다. DOM만 있으면 속성은 검사할 수 있어도 사진 속 누락 정보를 확인하기 어렵습니다. 도구를 가진 에이전트가 자료를 추가 수집할 수 있다면 관찰 근거와 함께 평가 범위를 넓힐 수 있습니다. 입력 부족을 영구적인 AI 능력의 한계로 단정할 필요는 없습니다.

### AI 결과를 고칠 수 있는 기록으로 받습니다

모델이 “적절합니다”라고만 답하면 수정 담당자가 판단 근거를 대조하기 어렵습니다. 현재 대안, 역할 분류의 이유, 빠진 정보, 실제 증거 ID, 이용자 영향, 수정안, 재점검 방법을 함께 받습니다.

판정과 실행 상태도 분리합니다. 자료가 도착하지 않은 상태는 **미실행**, 이미지 다운로드나 브라우저 도구가 실패한 상태는 **실행 실패**입니다. 자료를 읽었어도 의도나 문맥을 결정할 근거가 부족하면 **판단 유보**로 남깁니다. 완전히 관찰한 대상의 결과는 **충족·미충족**으로 구분하며, 대상이 범위에 없으면 그 이유를 적어 **해당 없음**으로 기록합니다.

장식 이미지를 올바르게 숨겼다는 결과는 관련 구현을 확인한 것입니다. 무조건 해당 없음으로 넘기면 필요한 숨김 처리를 확인했는지 알 수 없습니다. 빈 `alt`만 보고 통과시키거나, 빈 `alt`가 있다는 이유만으로 위반이라고 처리하는 두 오류를 모두 피해야 합니다.

분류가 애매한 이미지에는 저자의 사용 목적을 추가 자료로 요청할 수 있습니다. 다만 매번 사람에게 결론을 넘기는 형식으로 고정할 필요는 없습니다. 충분한 문맥과 관찰 자료로 판단 가능한 항목은 근거와 함께 평가하고, 부족한 부분만 명확하게 남깁니다.

## 개요 페이지에 두 프롬프트를 적용해 확인했습니다

공개된 [웹 접근성 개요](https://jangwook.net/series/accessibility/overview)의 도식과 원본 보기 링크를 대상으로 **GPT-6.1 Sol**에서 평가했습니다. 1회차의 평가 계획 프롬프트로 범위와 필요한 증거를 정리하고, 이 글의 1.1.1 프롬프트로 이미지의 의미와 현재 대안을 비교했습니다. 프롬프트의 지시문은 그대로 사용하고 입력란에 실제 페이지 자료를 채웠습니다.

제공한 자료는 도식별 화면 캡처와 원본을 렌더링한 이미지, 해당 요소와 부모 링크의 DOM, 브라우저 접근성 트리, 본문과 캡션입니다. 첫 질문은 본문의 도식 4개가 전달하는 관계·순서·비교와 원본 보기 링크의 이름입니다. 화면에 그려진 가상의 가입·배송 조회 UI를 실제로 조작했다고 판단하지 않도록 실제 DOM의 기능과 구분했습니다.

| 단계 | 확인한 결과 |
| --- | --- |
| 1회차 프롬프트 — 평가 계획 | 읽기 과정의 시작·완료 조건, 포함·제외 범위, 현재 자료와 추가로 필요한 증거, 검토·수정·재평가 순서를 구성했습니다. |
| 2회차 프롬프트 — 기준 판정 | 실제 이미지와 대안의 의미를 비교하고, 이미지 자체의 이름과 부모 링크의 이름을 나누어 기록했습니다. 각 판정에 증거 ID와 같은 조건의 재점검 방법을 남겼습니다. |

동일 입력을 반복해 최종 프롬프트의 판정과 역할 분류, 계산된 이름을 확인했습니다.

| 도식 | 대안과 비교한 핵심 정보 | 3회 반복 결과 |
| --- | --- | --- |
| WCAG 구조 | 원칙→지침→성공 기준의 관계와 A·AA·AAA의 누적 | 모두 충족 |
| 가입 상태 | 입력→약관→오류→수정→완료의 순서와 상태별 관찰 | 모두 충족 |
| 이미지 문맥 | 장식 A와 기능 B의 차이, 실제 원본 보기 링크의 목적 | 모두 충족 |
| 증거 흐름 | 수집·검토·판정·재점검, 증거 부족과 실행 실패의 구분 | 모두 충족 |

정상 입력 외에는 원본 페이지에서 만든 로컬 대조 자료로 평가했습니다. 하나는 마지막 도식의 자료를 제외하고, 다른 하나는 비교 도식의 대안을 ‘이미지’로 바꾸며 상세 설명을 제거했습니다. 공개 페이지 자체를 수정한 것은 아닙니다.

| 대조 조건 | 기대한 판단 | 실행 결과 |
| --- | --- | --- |
| 도식이 목록에 있지만 필요한 증거가 없는 경우 | 확인하지 못한 대상을 충족으로 처리하지 않음 | 판단 유보와 부분 실행을 기록하고 누락된 자료를 요청했습니다. |
| 비교 도식의 의미를 전달하는 대안이 없는 경우 | 링크의 이름과 이미지의 대안 부족을 구분 | 이미지와 범위 결과를 미충족으로 기록했습니다. 원본 보기라는 부모 링크의 이름은 별도로 충족 처리했습니다. |

이 조건에서 **필수 출력 구조, 요소별 근거 연결, 판정, 이미지와 부모 링크의 계산된 이름, 반복 일관성**을 확인했습니다. 판정은 본문 도식과 이미지 링크의 1.1.1에 한정합니다. 추가 동작이나 다른 기준을 평가할 때에는 그 질문에 필요한 상태와 증거를 새로 준비합니다.

## 사례를 넓힐 때는 정답 문장 하나보다 판단의 일관성을 봅니다

자신의 사이트에 적용할 때에는 해당 문맥에 맞는 사례를 준비합니다. 다음 표는 추가 검증 사례를 선택하는 기준입니다.

| 사례 | 확인할 결과 |
| --- | --- |
| 필요한 상품 특징이 실제 대안에 있는 정보 이미지 | 누락을 만들어내지 않는지 |
| 파일명만 대안에 있는 정보 이미지 | 핵심 정보 부족을 발견하는지 |
| 문맥상 순수 장식이고 올바르게 숨긴 이미지 | 빈 대안을 오류로 오탐하지 않는지 |
| 빈 대안 외에 이름이 없는 아이콘 버튼 | 조작 목적의 누락을 찾는지 |
| 같은 아이콘이지만 버튼에 올바른 이름이 있는 경우 | 이미지 속성만 보고 실패시키지 않는지 |
| 그래프의 값과 상세 표가 다른 경우 | 불일치를 찾고 근거 값을 제시하는지 |
| 같은 사진을 정보·링크·장식에 재사용한 경우 | 문맥에 따라 판단이 바뀌는지 |
| 흐린 그래프, 빠진 DOM, 잘못 연결된 상태 자료 | 추정값으로 통과시키지 않고 필요한 자료를 요청하는지 |

기준을 이해한 평가자가 근거를 남긴 기준 답안을 준비하고, 모델 결과의 오탐·누락·판단 유보를 비교합니다. 한 번 잘 작성된 `alt`가 나왔다고 전체 평가가 검증되는 것은 아닙니다. 같은 입력을 반복했을 때 역할 분류나 판단이 흔들리는지도 기록합니다.

화면만, 화면과 DOM, 화면·DOM·접근성 자료를 함께 주는 경우를 나누면 추가 입력이 판단에 어떻게 기여하는지 살펴볼 수 있습니다. 모델 버전, 도구, 프롬프트 버전, 입력 묶음, 실행 시각과 비용을 남깁니다. 입력 조건이 다른 실행을 같은 정확도 수치로 합치지 않습니다.

## 팀에서는 이미지 파일보다 사용 위치를 기준으로 관리합니다

CMS의 이미지 라이브러리에 저장한 기본 설명은 출발점으로 쓸 수 있습니다. 다만 실제 사용 위치가 정보 이미지인지, 링크인지, 중복 설명인지에 따라 검토할 수 있어야 합니다. 편집자가 장식 처리나 문맥에 맞는 대안을 선택할 수 있고, 개발자가 그 의도를 올바른 코드로 출력할 수 있도록 구성합니다.

상품 편집자는 필요한 상품 특징과 문구를, 디자인 담당자는 그림의 전달 목적을, 개발자는 이름·설명·숨김 처리를 확인하는 식으로 책임을 나눌 수 있습니다. 복잡한 도표의 설명과 데이터는 원본 작성자가 함께 갱신합니다. 각 조직의 역할에 맞게 조정할 제안이며 모든 팀에 같은 직무 구성을 요구하는 것은 아닙니다.

같은 컴포넌트가 여러 화면에서 쓰이면 한 곳의 속성 수정뿐 아니라 다른 문맥에서 이름이 잘 전달되는지도 표본으로 확인합니다. 이미지나 그래프가 바뀌었는데 이전 대안이 남는 경우도 점검합니다. 처음 입력했는지보다 현재 화면과 대안이 계속 일치하는지가 운영 기준이 됩니다.

## 실무 검토 체크리스트

아래 체크는 **해당 항목의 검토를 끝냈다는 기록**입니다. 체크했다고 조건을 충족했다는 뜻은 아닙니다. 각 항목 옆에 판정과 근거를 따로 남깁니다.

- [ ] **C01 범위**: 페이지·언어·상태·이용 목표를 기록하고 실제 확인한 요소 목록을 만들었습니다. 한 상태를 사이트 전체로 확대하지 않았습니다.
- [ ] **C02 대상 수집**: `img` 외에 의미 있는 SVG·캔버스·배경 이미지·이미지 속 문구가 있는지 확인했습니다.
- [ ] **C03 역할**: 정보·조작·복잡한 정보·장식·중복을 문맥으로 구분하고, 불분명한 목적은 추가 확인으로 남겼습니다.
- [ ] **C04 정보 대안**: 현재 사진이나 그림에 있는 필요한 정보가 대안으로 전달되는지 대조했습니다. 보이지 않는 성능이나 소재를 만들어 넣지 않았습니다.
- [ ] **C05 조작 목적**: 이미지 링크와 아이콘 버튼의 최종 접근 가능한 이름을 확인했습니다. 겉모습 설명만으로 목적을 대신하지 않았습니다.
- [ ] **C06 빈 대안**: 장식·중복 이미지의 생략 근거와 숨김 처리를 확인했습니다. 유일한 조작 이름까지 사라지지 않았습니다.
- [ ] **C07 복잡한 정보**: 짧은 설명과 상세 대안의 연결, 값·단위·관계·순서를 확인했습니다. 흐린 수치는 추정하지 않았습니다.
- [ ] **C08 별도 조건**: 미디어·시험·감각 경험·CAPTCHA의 상황별 요구를 확인했습니다. 적용하지 않은 조건에는 이유를 남겼습니다.
- [ ] **C09 연결 일치**: 같은 요소·시각·상태의 화면·DOM·접근성 자료를 비교했습니다. 빠진 자료와 실행 오류를 구분했습니다.
- [ ] **C10 판정 근거**: 충족·미충족·해당 없음·판단 유보와 실행 상태를 따로 기록했습니다. 모델의 추측을 직접 관찰로 쓰지 않았습니다.
- [ ] **C11 재점검**: 수정 후 같은 이용 목표와 상태에서 다시 확인했습니다. 공유 컴포넌트의 다른 사용 위치도 확인했습니다.
- [ ] **C12 운영**: 이미지 변경·언어 변경 때 대안을 갱신할 담당자와 검토 계기를 정했습니다. 실제 자료가 없는 상태는 검토 완료로 체크하지 않았습니다.

기록 양식은 `요소 ID / 페이지·상태 / 역할 / 현재 대안 / 판정 / 증거 ID / 이용자 영향 / 수정 담당 / 수정안 / 재점검 결과`로 시작할 수 있습니다. 이 양식과 프롬프트는 기록·평가를 돕는 자료이며, 자체적으로 검사를 실행하는 프로그램은 아닙니다.

## 평가 프롬프트를 사용하기 전에

아래의 통합 프롬프트에 평가할 페이지와 자료를 넣습니다. 이미지 입력을 지원하는 모델인지, 파일이나 브라우저를 실제로 읽는 도구가 있는지 먼저 확인합니다. 예시 이름만 넣지 말고 각 증거가 실제 입력에 포함되도록 연결합니다.

아래 프롬프트는 **1.1.1 평가를 위한 완성본**입니다. 실제 자료로 입력란을 채우고, 반환된 판정과 증거를 원본과 대조합니다. 같은 페이지를 반복 평가할 때에는 모델 설정과 자료 묶음을 유지합니다.
