## 同じ写真を3か所に置くなら、代替テキストも同じでよいのでしょうか？

オンラインストアのジャケットの写真を思い浮かべてください。商品詳細ページでは、正面の形と色を示しています。商品一覧では、写真を押すと詳細ページに移動します。案内ページでは、色と正面の特徴を文章ですでに説明したうえで、同じ写真を添えています。

3か所で使うファイルは同じでも、利用者が行うことは異なります。詳細ページでは、商品の特徴を知る必要があります。一覧では、リンク先がどこなのかを知る必要があります。案内ページでは、本文の説明を読み、同じ情報を不必要に繰り返し聞かずに済む必要があります。そのため、写真ファイルに1つの代替テキストを保存して、あらゆる場所で再利用するだけでは不十分な場合があります。

今回は、WCAG 2.2の**1.1.1 非テキストコンテンツ（Non-text Content）、レベル A**を扱います。商品説明やワイヤーフレーム、例に用いる数値は、理解を助けるための架空の事例です。後半では、公開されている概要ページにプロンプトを適用した実際の実行結果も取り上げます。

## 1.1.1が求めるのは、同等の目的を果たすテキストによる代替です

この基準は、利用者に提示される非テキストコンテンツに対して、そのコンテンツと同等の目的を果たすテキストによる代替を求めています。写真やアイコンだけでなく、図表、SVG、意味を持つ背景画像なども検討対象になり得ます。特定のHTML属性の存在だけを求める基準として読むと、適用範囲を見落としがちです。

`alt`は、HTMLの`img`要素に代替を提供する代表的な方法です。テキストによる代替は、画面を見ることが難しい利用者が情報を読んだり聞いたりするための経路を提供します。操作要素であれば、名前を通じてどのような動作を実行するのかも分かる必要があります。SVGやキャンバスのように表現技術が異なれば、代替を関連付ける実装方法も変わります。

実務では、次の2点を分けて確認するとよいでしょう。1つは、画像が伝える情報や機能がテキストで表現されているかです。もう1つは、そのテキストが実際の要素と関連付けられ、利用者に伝わるかです。文章が適切でも、関連付けが切れていれば代替を利用できません。逆に、属性が関連付けられていても、内容がファイル名や誤った説明であれば目的を伝えられません。

W3CのUnderstanding文書と画像チュートリアルは、この判断を説明する資料です。WCAGの要求事項と、解説に示された実装例は区別する必要があります。以下の事例別の手順は、これらをチームの作業に適用するための提案です。

## まず、画像が担う役割を定めます

画像を一時的に隠し、残った画面を考えると判断しやすくなります。利用者が情報を得たり作業を終えたりするうえで、何が失われるかを記録します。見栄えがよいという理由だけで装飾に分類することも、情報を含むという理由だけですべての視覚的な細部を説明することも避けます。

| 使用場面 | 利用者に残す必要があるもの | 代替の方針 |
| --- | --- | --- |
| 商品の特徴を示す写真 | 現在選択している商品を見分けるために必要な特徴 | 文脈に合った短い説明 |
| 内容が画像内にしかない案内バナー | キャンペーンの条件や期間などの実際の文言 | 読めるテキストで同じ情報を提供 |
| 画像が唯一の内容であるリンク | 移動先と目的 | リンクの名前で目的を伝える |
| アイコンのみのボタン | 実行する操作 | ボタンのアクセシブルな名前を提供 |
| グラフ・地図・フローチャート | 値、関係、方向、読む順序などの重要な情報 | 短い識別用の説明と詳細な代替を関連付ける |
| 周囲のテキストと完全に重複する図 | すでに提供した情報を維持し、繰り返しを減らすこと | ほかの機能がなければ空の`alt`などを検討 |

この表の最後の項目には条件があります。写真の隣に商品名があるだけでは、色や、見分けるために必要な特徴まで提供されているとはいえません。リンク内の図を隠す場合は、リンクの名前が残るかも併せて確認します。

### 情報を伝える画像：何を識別し、理解する必要があるのでしょうか？

次は、色と正面の形を確認する商品詳細ページの例です。

```html
<h2>クラシックジャケット</h2>
<img src="jacket-front.jpg"
     alt="濃いグレーのジャケットの正面。ボタン2つと両側のフラップポケット">
```

この説明は、その写真に実際に見える特徴を伝えています。写真だけでは確認できない素材、防水性能、着心地は付け加えません。商品説明に素材が記載されていても、それが画像に示されているのか、製品情報として確認した事実なのかは区別します。

代替は用途によって変わる場合があります。色を選ぶ画面で、色の名前が画像の外のテキストで十分に提供されているなら、同じ文言を必ずしも繰り返す必要はありません。縫製位置を比較する案内なら、色よりも縫い目の違いを説明するほうが目的に合います。`alt`を長く書くことと、十分に書くことは別です。

文脈が変わったら、代替も見直します。同じ画像を記事本文に移し、商品ページの説明をそのまま使うと、読者が記事で知るべき内容を伝えられない場合があります。

### 装飾と重複：空の代替テキストは、意図的に情報を省いた結果です

キャンペーンの条件がすべて本文にあり、背景写真が雰囲気を添えるだけであれば、次のように処理できます。

```html
<img src="jacket-decoration.jpg" alt="">
<p>秋のジャケットキャンペーン：10月15日まで一部商品10%割引</p>
```

空文字列の`alt=""`と、`alt`属性そのものを省くことは異なります。空の代替テキストは、この画像を読み上げる必要がないという意図を表します。属性を省略すると、一部のスクリーンリーダーがファイル名などを読み上げる場合があります。

ただし、上の例で写真自体に別の割引条件が書かれているなら、その条件が本文にあるかを確認する必要があります。図を隠してよいという判断は、画像がきれいであることや小さいことから導かれるものではありません。伝える情報がない、または別の経路で十分に提供されているという根拠が必要です。

キャプションがあるからといって、自動的に空の代替テキストを選ぶわけでもありません。キャプションが写真の出典だけを示しているのか、画像の重要な情報まで提供しているのか、その内容にアクセスできるのかを確認します。繰り返しを減らす目的と、情報の欠落を避ける目的を併せて考慮します。

## リンクとボタンでは、見た目より操作の目的を伝えます

商品写真だけのリンクには、移動の目的が分かる名前が必要です。

```html
<a href="/products/classic-jacket">
  <img src="jacket-front.jpg" alt="クラシックジャケットの詳細を見る">
</a>
```

このリンクで利用者がまず知る必要があるのは、ジャケットのポケットの数よりも、移動先の商品です。写真自体の詳細情報が購入判断に欠かせないなら、周囲の商品説明などで追加提供する方法を検討します。

同じリンク内に商品名が実際のテキストとしてすでにある場合は、構成が変わります。

```html
<a href="/products/classic-jacket">
  <img src="jacket-front.jpg" alt="">
  <span>クラシックジャケットの詳細を見る</span>
</a>
```

この例では、リンクのテキストが目的を伝え、画像は追加情報を含まないと仮定しています。画像が同じ名前の商品の色違いを区別するものなら、その違いは別途提供する必要があります。離れた2つのリンクに同じ目的を繰り返し設定する代わりに、画像とテキストを1つのリンクにまとめられるかも検討に値します。

アイコンのみのボタンも、同じように考えられます。虫眼鏡の形を説明するよりも、どのような検索を実行するのかを伝える名前が必要です。

```html
<!-- 修正前：ほかに名前を提供する手段がないボタンと仮定します。 -->
<button type="button">
  <img src="search.svg" alt="">
</button>

<!-- 修正後：ボタンに目的を示す名前を付け、重複するアイコンの説明は隠します。 -->
<button type="button" aria-label="商品検索">
  <img src="search.svg" alt="">
</button>
```

<figure class="learning-figure"><img src="/images/accessibility/non-text-content/ja/02-button-name-828e7c4ec862.svg" alt="同じ虫眼鏡ボタンの修正前後の比較。修正前はアクセシブルな名前が空で、修正後はボタンのaria-labelによって商品検索という名前が提供されます。"/><figcaption>図 02. 画面上のアイコンは同じでも、操作の目的を伝える名前が変わります。表示した名前はサンプルコードが意図する結果であり、実際の実装ではブラウザーのアクセシビリティツリーで確認します。</figcaption></figure>

画像の`alt`をボタンの名前として使う実装も可能です。複数の方法を重複して追加するよりも、1つの名前提供方法で意図どおりに伝わるかを確認します。`aria-label`などが指定されていると、見えているテキストや画像の説明と計算結果が異なる場合があるため、DOMの文字列を並べるだけでなく、最終的なアクセシブルな名前を確認します。

ボタンの役割・状態・キーボード操作は、4.1.2や2.1.1などで追加で扱います。今回の項目で名前を修正したからといって、ボタンのアクセシビリティ全体を評価したとは扱いません。

## 複雑なグラフは、1文のaltだけで終わらせません

教育用のグラフに、1月120件、2月80件、3月160件の問い合わせ数が示されていると仮定しましょう。`alt="月別の問い合わせグラフ"`は何を描いたものかは伝えますが、値や変化は伝えません。これらの値を比較する必要がある利用者には、詳細情報が必要です。

短い代替テキストは、グラフを識別し、詳細な説明の場所を案内できます。本文には、主な変化とデータ表を提供します。

```html
<img src="inquiries.png"
     alt="1～3月の問い合わせ数。月別の値と傾向は、以下の説明と表にあります。">
<p>問い合わせ数は1月の120件から2月の80件に減少し、
   3月には160件に増加しました。</p>
<table>
  <caption>1～3月の問い合わせ数、単位：件</caption>
  <tr><th scope="col">月</th><th scope="col">問い合わせ数</th></tr>
  <tr><th scope="row">1月</th><td>120</td></tr>
  <tr><th scope="row">2月</th><td>80</td></tr>
  <tr><th scope="row">3月</th><td>160</td></tr>
</table>
```

<figure class="learning-figure"><img src="/images/accessibility/non-text-content/ja/03-chart-alternative-e95ddabbc48a.svg" alt="教育用の問い合わせグラフとその代替。1月120件、2月80件、3月160件をグラフと表で提供し、2月に減少した後、3月に増加したという変化を文章で説明します。"/><figcaption>図 03. グラフのタイトルだけを写すのではなく、利用者が比較する値と傾向を提供します。数値は説明用の架空のデータです。</figcaption></figure>

表が常に唯一の代替となるわけではありません。フローチャートでは分岐条件と次の段階、地図では位置と移動経路、組織図では部署間の関係が重要になる場合があります。図を見なくても本文が求める判断を行えるかという観点で、詳細な代替が十分かを検討します。

画面上で数値を読み取りにくい場合、AIが推定した値を確定してはいけません。元のデータや鮮明な資料を求めます。元の表があることと、利用者がその表にアクセスできることも別なので、詳細説明へのリンクと関連付けられた場所も併せて確認します。

## 写真以外の表現と、基準の例外も検討します

意味のある情報がCSSの背景画像だけに含まれている場合、`img[alt]`の一覧を検査する方法では見つけられません。画像内だけにある案内文は、DOMのテキストと比較する必要があります。読む必要のある文言を実際のテキストで提供できるかを検討し、画像で提供した文言に代替があるかも確認します。`alt`を追加しても、文字画像に関する1.4.5の別の要求事項まで解決されるわけではありません。

情報を含むSVGには、その情報の代替が実際に関連付けられている必要があります。アイコンボタン内のSVGを装飾として隠す場合は、ボタン自体の名前を残す必要があります。キャンバスに描いた図表は、鮮明なスクリーンショットだけでは十分ではなく、テキストの説明やデータなど、利用可能な代替を確認します。この場合も、特定の属性を1つ付けたという理由だけで合格にはしません。

1.1.1には、次のような状況別の要求があります。例外があるからといって、代替をすべて省いてよいとは解釈しません。

| 状況 | 1.1.1で確認する内容 |
| --- | --- |
| 時間依存メディア | 少なくとも内容を識別する説明。キャプション・解説などの詳細な要求は1.2で追加検討 |
| テキストにすると成立しない試験・演習 | 対象が何かを識別する説明。実際に試験の目的が損なわれる条件かを確認 |
| 主に特定の感覚的体験を提供するコンテンツ | 少なくとも識別する説明。一般的な情報画像をこの条件で隠さないこと |
| CAPTCHA | 人間であることを確認する目的を説明する代替と、別の感覚方式による代替形式。正解の公開が代替という意味ではない |
| 純粋な装飾・視覚的な書式設定・利用者に提示されないコンテンツ | 支援技術が無視できるように実装 |

画面に見えていないコンテンツも、別の方法で利用者に提示されたり、開いたメニューなどに現れたりする場合があります。閉じた状態の画面1枚だけを根拠に、見えていないという例外を適用せず、評価する状態と利用経路を記録します。

## マルチモーダルAIには、画像・コード・文脈を同じ対象としてまとめて渡します

代替テキストの存在を検査することと、代替の意味を評価することは別の作業です。画像内の割引文言が代替から抜けていないか、写真の説明がリンクの目的に合っているか、詳細な表がグラフと同じ内容を伝えているかは、画像と文脈を比較する必要があります。この比較にマルチモーダルモデルを活用する評価を設計できます。

この設計では、画像だけを見て説明を生成する作業より先に、現在の代替が利用者の目的に対して十分かを評価します。自動ルール型ツールでは確認できない意味を検討しつつ、モデルの応答を実際の観察・操作の記録と結び付けます。後の適用事例では、実際のページ資料と対照条件を用いて、判定と根拠を確認します。

<figure class="learning-figure"><img src="/images/accessibility/non-text-content/ja/04-evidence-flow-ab257f4fed3e.svg" alt="要素IDで画像、DOM、アクセシビリティツリー、ページの文脈を関連付け、意味の比較、根拠のある判定、改善と同じ状態での再確認へと進む評価の流れ。"/><figcaption>図 04. 比較結果を検証するには、入力資料を同じ要素と状態に関連付ける必要があります。提案する評価設計であり、この流れ全体を実装したサービスや実験の結果ではありません。</figcaption></figure>

評価資料は、次のように準備します。

1. **ページと作業**：URL、言語、利用目標、確認する状態を記載します。商品一覧と詳細ページは別の状態として区別します。
2. **視覚資料**：ページ全体の画面、対象画像の拡大資料、元の画像またはグラフのデータを提供します。全体の文脈と細部を併せて見られるようにします。
3. **DOM**：対象要素だけでなく、親のリンク・ボタン、周囲のテキスト、名前・説明で参照される要素を含めます。画像の欠落や`aria-label`などを確認できる範囲が必要です。
4. **アクセシビリティ資料**：役割、最終的に計算された名前・説明、非表示かどうかを収集します。DOMから予想した名前と、ブラウザーが公開した結果を区別します。
5. **状態の関連付け**：要素ID、収集時刻、ビューポートやログイン条件などを付けます。複数の状態のスクリーンショットとDOMを混在させると、判定の根拠が食い違います。

例えば、`E03`を商品検索ボタンのIDとした場合、`E03-screen`を画面、`E03-dom`をコード、`E03-ax`をアクセシビリティツリー、`E03-action`を実際の動作記録として関連付けられます。ファイルパスを記載しただけでモデルがファイルを読んだとみなさず、実際に添付するか、読み取りツールの結果を渡します。

入力によって、可能な判断も変わります。画面だけなら視覚情報と問題候補を見つけられますが、実際の名前や非表示処理を確認するのは困難です。DOMだけなら属性を検査できても、写真内の欠落情報を確認するのは困難です。ツールを持つエージェントが資料を追加収集できるなら、観察の根拠とともに評価範囲を広げられます。入力不足を、AIの能力の恒久的な限界と決めつける必要はありません。

### AIの結果は、修正に使える記録として受け取ります

モデルが「適切です」とだけ答えると、修正担当者は判断の根拠を照合しにくくなります。現在の代替、役割分類の理由、欠落している情報、実際の証拠ID、利用者への影響、修正案、再確認方法を併せて受け取ります。

判定と実行状態も分けます。資料が届いていない状態は**未実行**、画像のダウンロードやブラウザーツールが失敗した状態は**実行失敗**です。資料を読めても、意図や文脈を決める根拠が不足していれば**判断保留**とします。十分に観察した対象の結果は**満たす・満たさない**に分け、対象が範囲に含まれなければ、その理由を記載して**該当なし**と記録します。

装飾画像が正しく隠されているという結果は、関連する実装を確認したものです。無条件に該当なしにすると、必要な非表示処理を確認したか分かりません。空の`alt`だけを見て合格にすることと、空の`alt`があるという理由だけで違反とすることの、両方の誤りを避ける必要があります。

分類が曖昧な画像については、作者の使用目的を追加資料として求めることができます。ただし、毎回人に結論を委ねる形式に固定する必要はありません。十分な文脈と観察資料で判断できる項目は根拠とともに評価し、不足している部分だけを明確に残します。

## 概要ページに2つのプロンプトを適用して確認しました

公開されている[ウェブアクセシビリティの概要](https://jangwook.net/series/accessibility/overview)の図と原本表示リンクを対象に、**GPT-6.1 Sol**で評価しました。第1回の評価計画プロンプトで範囲と必要な証拠を整理し、この記事の1.1.1プロンプトで画像の意味と現在の代替を比較しました。プロンプトの指示文はそのまま使用し、入力欄に実際のページ資料を記入しました。

提供した資料は、図ごとの画面キャプチャと原本をレンダリングした画像、該当要素と親リンクのDOM、ブラウザーのアクセシビリティツリー、本文とキャプションです。最初の評価で問うたのは、本文の4つの図が伝える関係・順序・比較と、原本表示リンクの名前です。画面に描かれた架空の登録・配送状況照会UIを実際に操作したと判断しないよう、実際のDOMの機能と区別しました。

| 段階 | 確認した結果 |
| --- | --- |
| 第1回のプロンプト — 評価計画 | 読む過程の開始・完了条件、含める範囲と除外する範囲、現在の資料と追加で必要な証拠、検討・修正・再評価の順序を構成しました。 |
| 第2回のプロンプト — 基準の判定 | 実際の画像と代替の意味を比較し、画像自体の名前と親リンクの名前を分けて記録しました。各判定に証拠IDと同じ条件での再確認方法を残しました。 |

同じ入力を繰り返し、最終プロンプトの判定と役割分類、計算された名前を確認しました。

| 図 | 代替と比較した重要な情報 | 3回の反復結果 |
| --- | --- | --- |
| WCAGの構造 | 原則→ガイドライン→達成基準の関係とA・AA・AAAの累積 | すべて満たす |
| 登録の状態 | 入力→規約→エラー→修正→完了の順序と状態ごとの観察 | すべて満たす |
| 画像の文脈 | 装飾Aと機能Bの違い、実際の原本表示リンクの目的 | すべて満たす |
| 証拠の流れ | 収集・検討・判定・再確認、証拠不足と実行失敗の区別 | すべて満たす |

通常の入力以外には、元のページから作成したローカルの対照資料で評価しました。一方は最後の図の資料を除外し、もう一方は比較図の代替を「画像」に変更して詳細な説明を削除しました。公開ページ自体を変更したわけではありません。

| 対照条件 | 期待した判断 | 実行結果 |
| --- | --- | --- |
| 図が一覧にあるが、必要な証拠がない場合 | 確認できなかった対象を、満たすと扱わない | 判断保留と部分実行を記録し、欠落した資料を求めました。 |
| 比較図の意味を伝える代替がない場合 | リンクの名前と画像の代替不足を区別 | 画像と範囲全体の結果を、満たさないと記録しました。原本表示という親リンクの名前は、別途、満たすと扱いました。 |

この条件で、**必須の出力構造、要素ごとの根拠の関連付け、判定、画像と親リンクの計算された名前、反復時の一貫性**を確認しました。判定は、本文の図と画像リンクにおける1.1.1に限定しています。追加の動作や別の基準を評価するときは、その問いに必要な状態と証拠を新たに準備します。

## 事例を広げるときは、1つの正解文より判断の一貫性を見ます

自分のサイトに適用するときは、その文脈に合う事例を用意します。次の表は、追加の検証事例を選ぶ基準です。

| 事例 | 確認する結果 |
| --- | --- |
| 必要な商品特徴が実際の代替に含まれる情報画像 | 存在しない欠落を作り出さないか |
| 代替がファイル名だけの情報画像 | 重要な情報の不足を発見するか |
| 文脈上、純粋な装飾であり、正しく隠された画像 | 空の代替を誤ってエラーと検出しないか |
| 空の代替以外に名前がないアイコンボタン | 操作目的の欠落を見つけるか |
| 同じアイコンでも、ボタンに正しい名前がある場合 | 画像の属性だけを見て不合格にしないか |
| グラフの値と詳細な表が異なる場合 | 不一致を見つけ、根拠となる値を示すか |
| 同じ写真を情報・リンク・装飾に再利用した場合 | 文脈に応じて判断が変わるか |
| 不鮮明なグラフ、欠落したDOM、誤って関連付けた状態資料 | 推定値で合格にせず、必要な資料を求めるか |

基準を理解した評価者が根拠を残した参照用の回答を用意し、モデル結果の誤検出・見落とし・判断保留を比較します。一度適切な`alt`が生成されたからといって、評価全体が検証されたわけではありません。同じ入力を繰り返したときに、役割分類や判断が揺れるかも記録します。

画面だけ、画面とDOM、画面・DOM・アクセシビリティ資料を一緒に渡す場合を分けると、追加入力が判断にどう貢献するかを検討できます。モデルのバージョン、ツール、プロンプトのバージョン、入力資料一式、実行時刻と費用を残します。入力条件が異なる実行を、同じ精度の数値にまとめません。

## チームでは、画像ファイルより使用箇所を基準に管理します

CMSの画像ライブラリに保存した基本の説明は、出発点として使えます。ただし、実際の使用箇所が情報画像なのか、リンクなのか、重複する説明なのかに応じて検討できる必要があります。編集者が装飾扱いや文脈に合う代替を選べ、開発者がその意図を正しいコードで出力できるように構成します。

商品編集者は必要な商品特徴と文言を、デザイン担当者は図の伝達目的を、開発者は名前・説明・非表示処理を確認する、といった形で責任を分担できます。複雑な図表の説明とデータは、原本の作成者が併せて更新します。これは各組織の役割に合わせて調整するための提案であり、すべてのチームに同じ職務構成を求めるものではありません。

同じコンポーネントを複数の画面で使う場合は、1か所の属性を修正するだけでなく、ほかの文脈でも名前が適切に伝わるかをサンプルで確認します。画像やグラフが変わったのに、以前の代替が残っているケースも点検します。最初に入力したかどうかよりも、現在の画面と代替が継続して一致しているかが運用の基準になります。

## 実務レビューのチェックリスト

以下のチェックは、**その項目の検討を終えたという記録**です。チェックしたからといって、条件を満たしたという意味ではありません。各項目の横に、判定と根拠を別途残します。

- [ ] **C01 範囲**：ページ・言語・状態・利用目標を記録し、実際に確認した要素の一覧を作成しました。1つの状態をサイト全体に拡大していません。
- [ ] **C02 対象の収集**：`img`以外に、意味のあるSVG・キャンバス・背景画像・画像内の文言があるかを確認しました。
- [ ] **C03 役割**：情報・操作・複雑な情報・装飾・重複を文脈で区別し、不明確な目的は追加確認事項として残しました。
- [ ] **C04 情報の代替**：現在の写真や図に含まれる必要な情報が、代替で伝わるかを照合しました。見えていない性能や素材を作り出して追加していません。
- [ ] **C05 操作の目的**：画像リンクとアイコンボタンの最終的なアクセシブルな名前を確認しました。外見の説明だけで目的の代わりにしていません。
- [ ] **C06 空の代替**：装飾・重複画像を省略する根拠と非表示処理を確認しました。唯一の操作名まで消えていません。
- [ ] **C07 複雑な情報**：短い説明と詳細な代替の関連付け、値・単位・関係・順序を確認しました。不鮮明な数値を推定していません。
- [ ] **C08 個別の条件**：メディア・試験・感覚的体験・CAPTCHAの状況別の要求を確認しました。適用しなかった条件には理由を残しました。
- [ ] **C09 関連付けの一致**：同じ要素・時刻・状態の画面・DOM・アクセシビリティ資料を比較しました。欠落した資料と実行エラーを区別しました。
- [ ] **C10 判定の根拠**：満たす・満たさない・該当なし・判断保留と、実行状態を別々に記録しました。モデルの推測を直接観察として記載していません。
- [ ] **C11 再確認**：修正後、同じ利用目標と状態で再確認しました。共有コンポーネントのほかの使用箇所も確認しました。
- [ ] **C12 運用**：画像変更・言語変更時に代替を更新する担当者と、見直しの契機を定めました。実際の資料がない状態を、レビュー完了としてチェックしていません。

記録様式は、`要素ID / ページ・状態 / 役割 / 現在の代替 / 判定 / 証拠ID / 利用者への影響 / 修正担当 / 修正案 / 再確認結果`から始められます。この様式とプロンプトは記録・評価を支援する資料であり、それ自体で検査を実行するプログラムではありません。
