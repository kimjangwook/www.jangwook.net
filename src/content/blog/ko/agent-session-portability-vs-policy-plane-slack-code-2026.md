# 에이전트 세션을 버려도 되는 캐시로 취급하고 통제를 정책 평면으로 옮겼더니 벤더 락인이 관리 가능해졌다

코딩 에이전트 세션을 다른 벤더로 옮긴다고 해서 락인이 실제로 줄어드는지, 아니면 나중에 이사를 할 때만 "아, 이 정도는 옮길 수 있구나"라는 착시를 심어 주는 건지, 그 경계가 정확히 어디에 있는지를 손으로 확인해 봤다. 동결한 Claude Code 세션 한 건을 session-migrate 0.8.0으로 일곱 개 타깃 포맷에 전송했는데, 대화와 도구 호출 맥락은 생각보다 잘 넘어갔다. 그런데 조직에서 이 에이전트 작업을 안전하게 만드는 통제 장치는 단 하나도 따라오지 않았다.

이 한 줄이 이 글의 전부다. CTO가 최적화해야 할 대상은 개발자 로컬에 쌓인 대화 기록의 이식성이 아니라, 승인과 감사의 이식성이다.

## 운영의 문제는 대화 기록이 어디에 있느냐가 아니다

프로덕션에 영향을 미치는 변경을 에이전트가 한 뒤, 3개월 뒤 그 변경의 근거를 어디서 확인하느냐. 이 질문이 올라올 때 위험한 대답은 대개 "누군가의 로컬 세션 파일 어딘가"다. 한 명은 JSONL에 맥락을 갖고 있고, 다른 한 명은 조각을 PR 설명에 옮겨 붙였고, 또 한 명은 이미 디렉터리를 정리했다. 개인 실험이라면 넘어갈 수 있다. 변경이 인증, 결제, 회원 데이터, 프로덕션 접근에 닿는 순간 그건 취향이 아니라 운영 결함이다.

반대 방향의 위험도 같이 움직인다. 세션 파일에는 프로덕션 로그 조각, 스키마 상세, 첨부 산출물, 때로는 실데이터 표본이 붙어 있다. 그런 세션을 다른 벤더의 네이티브 포맷으로 바꿔 주는 명령은 단순한 편의 기능이 아니다. 데이터 반출 경로가 하나 더 열린 것이다.

그래서 나는 에이전트 세션 이식성을 개발자 생산성 문제로 보지 않는다. CLI 기능의 얼굴을 하고 들어온 데이터 거버넌스 문제다.

Slack Code는 정반대 방향에서 출발했는데 결론은 같은 자리에 닿는다. 코딩 에이전트를 멘션하면 전용 코드 채널이 생기고, 필요한 사람들이 모이고, 코드 diff와 계획 문서와 라이브 HTML 프리뷰가 그 안에 쌓이며, 작업이 끝나면 채널은 검색 가능한 기록으로 아카이브된다. 오래 남는 작업 기록이 개인 워크스테이션에서 공용 운영 표면으로 이동한다.

> Slack Code は Slack 既存の権限と管理者コントロールを継承するため、IT 部門が新たな設定や監査を行う必要はありません。重要な変更はチャンネル内でそのまま担当者による迅速な承認フローに回すことができ、レビューの安心感を保ちながら自動化のスピードを実現します。
> — [Slack Code: チームと AI エージェントが共に作り上げる場所](https://slack.com/intl/ja-jp/blog/news/slack-code-channels-for-agents)

제품 세부보다 이 상속 구조가 중요하다. 새 에이전트 워크플로마다 IT에 권한 체계를 새로 만들라고 요구하는 대신, 이미 있는 권한과 관리자 통제를 그대로 물려받는다. 에이전트가 어떤 채널에서, 어떤 사람과, 어떤 데이터에 접근하는지를 Slack의 기존 ACL이 결정한다. 하네스가 바뀌어도 이 층은 흔들리지 않는다.

## 이식 실험에서 실제로 살아남은 것

macOS에 Python 3.12 가상환경을 만들고 session-migrate 0.8.0을 설치했다. README는 Python 3.11 이상과 Linux를 지원 범위로 적어 두었지만, 설치와 기동 모두 문제없이 됐다. 공식 지원 경계가 바뀌는 건 아니고, 통제된 포맷 변환 실험에는 충분했다.

소스는 동결한 Claude Code 세션 한 건이다. 341,646바이트, 90 레코드, tool-use 블록 20개, tool-result 블록 20개, thinking 블록 11개. 동결이 핵심이었다. 첫 시도에서 라이브 세션 파일이 실행 중에 계속 자라는 바람에, 타깃마다 서로 다른 모집단을 비교하고 있었다.

동결한 같은 세션을 Codex, Pi, GitHub Copilot CLI, Qwen Code, Kimi Code, Muse Code, Mistral Vibe로 보냈다. 타깃 홈은 전부 `/tmp` 아래로 격리해 실제 설정 디렉터리를 건드리지 않았다. 결과 레코드 수는 33개에서 50개까지 벌어졌다. 정보 보존량이 그만큼 다르다는 뜻은 아니다. 타깃 포맷이 같은 내용을 다른 레코드 단위로 쪼갤 뿐이다.

중요한 결과는 손실 매니페스트 쪽이었다. 드롭 총계는 일곱 타깃 전부에서 54에서 57 사이로 촘촘히 붙었고, thinking 드롭은 9로 고정이었다. 반복해서 빠지는 것은 소스 쪽 메타데이터 레코드, 도구 참조 레코드, 그리고 비공개 사고 흔적이다. Codex만 세션 제목 하나를 추가로 버렸고, Vibe만 다른 타깃이 버린 도구 참조 레코드 2건을 지켰다.

이 패턴이 일반적인 호환성 주장보다 훨씬 쓸모 있다. 타깃을 바꿔도 손실이 움직이지 않았다. 무엇이 중간 모델에 들어갈 수 있는지는 소스 세션의 이벤트 어휘가 결정한다.

프로젝트는 변환 경로를 이렇게 적었다.

> native session → validated event timeline → native target → resume
> — [session-migrate — Migrate your sessions to any harness](https://github.com/xhluca/session-migrate)

가운데 타임라인은 의도적으로 작다. 순서 있는 대화 이벤트는 통과하지만 클라이언트에 상주하는 설정은 통과하지 못한다. 소스 세션은 수정되지 않고, 누락과 변환은 내용 없는 마이그레이션 매니페스트에 개수로만 집계된다.

## 락인의 경계선은 대화 기록이 아니라 정책 평면이다

이 도구는 12개 하네스 포맷을 지원하고 순서 있는 경로 144개를 명시한다. 같은 포맷끼리의 이식 가능 재작성까지 포함한 숫자다. 사용자와 어시스턴트 메시지는 모든 경로에서 순서대로 보존된다. 마이그레이션이라는 이름을 붙인 평문 내보내기가 아니라, 실제로 의미 있는 이식성이다.

> Every listed format can be a source or target: 144 ordered routes, including same-format portable rewrites.
> — [session-migrate README — Compatibility](https://raw.githubusercontent.com/xhluca/session-migrate/main/README.md)

그런데 같은 호환성 문서가 결정적인 한계도 함께 적어 놓았다.

> Auth, hooks, policies, MCP, and runtime config | No | These remain with the source client
> — [session-migrate — Migrate your sessions to any harness](https://github.com/xhluca/session-migrate)

경영진이 벤더 협상 자리에서 써야 할 아키텍처 사실이 이것이다. 팀은 작업 서사와 도구 호출, 쓸 만한 맥락 상당량을 옮길 수 있다. 세션 파일 하나 옮기는 것으로 집행 환경까지 옮기지는 못한다.

인증은 클라이언트에 묶여 있다. 훅도 클라이언트에 묶여 있다. 정책 설정, MCP 접속, 런타임 설정 모두 클라이언트에 남는다. 타깃 포맷을 잘못 골라서 빠진 게 아니다. 애초에 이식 가능한 이벤트 타임라인의 구성원이 아니었다.

Antigravity와 Cursor 변환이 실패한 것도 같은 경계를 반대편에서 증명한다. 두 어댑터 모두 곧바로 네이티브 실행 파일 `agy`와 `cursor-agent`를 요구했고, 내 머신에는 둘 다 설치돼 있지 않았다. 이 어댑터들은 독립적인 파일 번역기가 아니다. 내보낸 세션만으로는 재구성되지 않는 네이티브 상태가 있어서 클라이언트에 붙어 동작한다.

개인 개발자라면 받아들일 만하다. 조직에서는 이야기가 달라진다. 진짜 교체 비용은 새 하네스 위에서 권한 매핑, 훅, 정책, 승인된 도구 접속을 다시 세우는 작업이다. 세션 파일을 옮기는 2초가 아니라, 그 뒤의 수 주가 교체 비용이다.

## 가장 강한 반론은 좁지만 중요한 구간에서 옳다

가장 강한 반대는 "재개 비용의 본체는 세션 맥락"이라는 주장이다. 도구를 갈아타며 긴 구현 세션을 이어야 하는 개인 개발자, 혹은 단일 벤더 안에서만 동작하는 소규모 팀에게는 이 주장이 정확하다. 90레코드 세션의 대화 흐름과 도구 호출 연쇄가 끊기면, 에이전트가 "지금 어디까지 했는지"를 다시 추론하는 데 소모되는 토큰과 시간이 실재한다. 세션 맥락이 재개 비용의 대부분을 차지하는 구간에서는, 이식성이 곧 생산성이다.

그런데 이 주장이 성립하는 조건을 붙여 보면, 적용 범위가 좁아진다. 단일 벤더, 단일 프로젝트, 단일 개발자, 수 시간 단위 세션. 이 조건이 하나라도 깨지면, 재개 비용의 본체는 맥락이 아니라 "이 에이전트가 이 리포지토리에 이 권한으로 이 도구를 이 정책 아래에서 호출할 수 있는가"라는 집행 환경의 재구성이다. 3개월 뒤 감사 감사자가 "이 변경을 누가, 어떤 승인 아래, 어떤 데이터에 접근해서 했는가"를 물었을 때, 답이 "어느 개발자의 로컬 JSONL 90레코드"인 조직은, 세션이 아무리 잘 이식돼도 운영 기준을 충족하지 못한다.

## 그래서 나는 세션을 캐시로 취급한다

이 실험이 내게 준 실무 결론은 단순하다. 에이전트 세션은 버려도 되는 캐시다. 대화 맥락, 도구 호출 기록, 사고 흔적, 이 모든 것은 "다음에 같은 작업을 이어 할 때 유용하면 복원되고, 없으면 처음부터 다시 하면 되는" 중간 산출물이다. session-migrate가 144개 경로를 지원하고, 54에서 57레코드의 손실을 매니페스트로 투명하게 보고하는 것은, 이 캐시 층의 이식성을 실제로 확보해 준다는 뜻이다.

그런데 캐시 위에 올라가 있는 것이 있다. 이 에이전트가 이 리포지토리에 push할 수 있는지, 이 MCP 서버에 접속할 수 있는지, 이 훅이 실행될 때 어떤 승인자가 서명하는지, 이 세션의 산출물이 어떤 데이터 분류에 해당하는지. 이 층은 클라이언트에 상주하고, 벤더에 묶여 있고, 세션 파일에 없다.

이 층을 에이전트 하네스 밖에, 조직의 기존 권한과 감사 체계 위에 올려 놓는 순간, 벤더 교체는 "세션을 옮기는 2초"가 아니라 "정책 평면의 ACL을 새 하네스에 매핑하는 수 주"로 환산된다. 그리고 그 수 주는, 세션 파일이 어느 포맷으로든 잘 넘어간다는 사실과 무관하게, 이미 조직이 다른 시스템에서 반복하고 있는 작업이다. Slack Code가 Slack ACL을 그대로 물려받는 구조, MCP 접속을 외부 하네스로 분리하는 구조, 승인과 감사를 에이전트 프로세스 밖의 독립 서비스로 두는 구조. 이 방향이 반복되는 이유는, 정책 평면이 클라이언트에 붙어 있는 한 벤더 락인은 세션 이식성으로 해결되지 않기 때문이다.

세션은 캐시다. 버려도 된다. 다시 만들면 된다. 그런데 정책은 아니다. 정책은 한 번 정하면, 그 아래에서 모든 세션이 태어나고, 모든 도구가 호출되고, 모든 변경이 승인된다. 이 층을 클라이언트 안에 두는 순간, 벤더가 바뀌면 세션은 넘어가도 "이 조직에서 이 에이전트가 무엇을 할 수 있는가"라는 답이 사라진다.

그래서 나는 세션 파일의 이식성을 개발자 생산성 지표로, 정책 평면의 이식성을 운영 리스크 지표로, 각각 다른 주기로, 다른 담당자에게 보고한다. 둘을 같은 "벤더 락인"이라는 단어 아래에 묶어 두면, 세션이 잘 넘어간다는 뉴스가 정책 평면의 공백을 가린다.
