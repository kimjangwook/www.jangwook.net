코딩 에이전트 세션을 옮길 수 있다는 말이 벤더 락인을 실제로 줄이는지, 아니면 나중의 이사를 실제보다 쉬워 보이게 만드는 착시인지 확인하고 싶었다. 실제 Claude Code 세션 한 건을 동결해 형상을 들여다본 뒤, session-migrate 0.8.0으로 일곱 개 타깃 포맷에 전송했다. 쓸모 있는 대화와 도구 맥락은 생각보다 잘 넘어갔다. 반면 조직에서 에이전트 작업을 안전하게 만드는 통제 장치는 하나도 따라오지 않았다.

이 구분이 중요하다. CTO가 최적화해야 할 대상은 개발자 로컬 기록의 이식성이 아니라 승인과 감사의 이식성이다.

## 운영의 문제는 대화 기록이 어디 사는가가 아니다

리뉴얼 프로그램에서도, 데이터 서비스 개발에서도 결국 같은 질문이 엔지니어링 리더에게 올라온다. "이 에이전트가 왜 이 변경을 했는지 3개월 뒤에 어디서 볼 수 있나."

위험한 대답은 대개 "누군가의 로컬 세션 파일 어딘가"다. 한 명은 JSONL에 맥락을 갖고 있고, 다른 한 명은 조각을 PR 설명에 옮겨 붙였고, 또 한 명은 이미 디렉터리를 정리했다. 개인 실험이라면 넘어갈 수 있다. 변경이 인증, 결제, 회원 데이터, 프로덕션 접근에 닿는 순간 그건 취향이 아니라 운영 결함이다.

반대 방향의 위험도 같이 움직인다. 세션 파일에는 프로덕션 로그 조각, 스키마 상세, 첨부 산출물, 때로는 실데이터 표본이 붙어 있다. 그런 세션을 다른 벤더의 네이티브 포맷으로 바꿔 주는 명령은 단순한 편의 기능이 아니다. 데이터 반출 경로가 하나 더 열린 것이다.

그래서 나는 에이전트 세션 이식성을 개발자 생산성 문제로 보지 않는다. CLI 기능의 얼굴을 하고 들어온 데이터 거버넌스 문제다.

Slack Code는 세션 이식과 정반대 방향에서 출발했는데 결론은 같은 자리에 닿는다. Slack의 설명에 따르면 코딩 에이전트를 멘션하면 전용 코드 채널이 생기고, 필요한 사람들이 모이고, 코드 diff와 계획 문서와 라이브 HTML 프리뷰가 그 안에 쌓이며, 작업이 끝나면 채널은 검색 가능한 기록으로 아카이브된다. 오래 남는 작업 기록이 개인 워크스테이션에서 공용 운영 표면으로 이동한다.

> Slack Code は Slack 既存の権限と管理者コントロールを継承するため、IT 部門が新たな設定や監査を行う必要はありません。重要な変更はチャンネル内でそのまま担当者による迅速な承認フローに回すことができ、レビューの安心感を保ちながら自動化のスピードを実現します。
> — [Slack Code: チームと AI エージェントが共に作り上げる場所](https://slack.com/intl/ja-jp/blog/news/slack-code-channels-for-agents)

제품 세부보다 이 상속 구조가 중요하다. 새 에이전트 워크플로마다 IT에 권한 체계를 새로 만들라고 요구하는 대신, 이미 있는 권한과 관리자 통제를 그대로 물려받는다.

## 이식 실험에서 실제로 살아남은 것

macOS에서 Python 3.12 가상환경에 session-migrate 0.8.0을 설치했다. README는 Python 3.11 이상과 Linux를 지원 범위로 적어 두었지만 설치와 기동 모두 문제없이 됐다. 공식 지원 경계가 바뀌는 건 아니고, 통제된 포맷 변환 실험에는 충분했다.

소스는 동결한 Claude Code 세션 한 건이다. 341,646바이트, 90 레코드, tool-use 블록 20개, tool-result 블록 20개, thinking 블록 11개. 동결이 핵심이었다. 첫 시도에서 라이브 세션 파일이 실행 중에 계속 자라는 바람에 타깃마다 서로 다른 모집단을 비교하고 있었다.

동결한 같은 세션을 Codex, Pi, GitHub Copilot CLI, Qwen Code, Kimi Code, Muse Code, Mistral Vibe로 보냈다. 타깃 홈은 전부 `/tmp` 아래로 격리해 실제 설정 디렉터리를 건드리지 않았다. 결과 레코드 수는 33개에서 50개까지 벌어졌다. 정보 보존량이 그만큼 다르다는 뜻은 아니다. 타깃 포맷이 같은 내용을 다른 레코드 단위로 쪼갤 뿐이다.

중요한 결과는 손실 매니페스트 쪽이었다. 드롭 총계는 일곱 타깃 전부에서 54에서 57 사이로 촘촘히 붙었고, thinking 드롭은 9로 고정이었다. 반복해서 빠지는 것은 소스 쪽 메타데이터 레코드, 도구 참조 레코드, 그리고 비공개 사고 흔적이다. Codex만 세션 제목 하나를 추가로 버렸고, Vibe만 다른 타깃이 버린 도구 참조 레코드 2건을 지켰다.

이 패턴이 일반적인 호환성 주장보다 훨씬 쓸모 있다. 타깃을 바꿔도 손실이 움직이지 않았다. 무엇이 중간 모델에 들어갈 수 있는지는 소스 세션의 이벤트 어휘가 결정한다.

프로젝트는 변환 경로를 이렇게 적었다.

> native session → validated event timeline → native target → resume
> — [session-migrate — Migrate your sessions to any harness](https://github.com/xhluca/session-migrate)

가운데 타임라인은 의도적으로 작다. 순서 있는 대화 이벤트는 통과하지만 클라이언트에 상주하는 설정은 통과하지 못한다. 소스 세션은 수정되지 않고, 누락과 변환은 내용 없는 마이그레이션 매니페스트에 개수로만 집계된다.

## 락인의 경계선은 대화 기록이 아니라 정책 평면이다

이 도구는 12개 하네스 포맷을 지원하고 순서 있는 경로 144개를 명시한다. 같은 포맷끼리의 이식 가능 재작성까지 포함한 숫자다. 사용자와 어시스턴트 메시지는 모든 경로에서 순서대로 보존된다. 마이그레이션이라는 이름을 붙인 평문 내보내기가 아니라, 실제로 의미 있는 이식성이다.

> Every listed format can be a source or target: 144 ordered routes, including same-format portable rewrites.
> — [session-migrate README — Compatibility](https://raw.githubusercontent.com/xhluca/session-migrate/main/README.md)

그런데 같은 호환성 문서가 결정적인 한계도 함께 적어 놓았다.

> Auth, hooks, policies, MCP, and runtime config | No | These remain with the source client
> — [session-migrate — Migrate your sessions to any harness](https://github.com/xhluca/session-migrate)

경영진이 벤더 협상 자리에서 써야 할 아키텍처 사실이 이것이다. 팀은 작업 서사와 도구 호출, 쓸 만한 맥락 상당량을 옮길 수 있다. 세션 파일 하나 옮기는 것으로 집행 환경까지 옮기지는 못한다.

인증은 클라이언트에 묶여 있다. 훅도 클라이언트에 묶여 있다. 정책 설정, MCP 접속, 런타임 설정 모두 클라이언트에 남는다. 타깃 포맷을 잘못 골라서 빠진 게 아니다. 애초에 이식 가능한 이벤트 타임라인의 구성원이 아니었다.

Antigravity와 Cursor 변환이 실패한 것도 같은 경계를 반대편에서 증명한다. 두 어댑터 모두 곧바로 네이티브 실행 파일 `agy`와 `cursor-agent`를 요구했고, 내 머신에는 둘 다 설치돼 있지 않았다. 이 어댑터들은 독립적인 파일 번역기가 아니다. 내보낸 세션만으로는 재구성되지 않는 네이티브 상태가 있어서 클라이언트에 붙어 동작한다.

개인 개발자라면 받아들일 만하다. 조직에서는 이야기가 달라진다. 진짜 교체 비용은 새 하네스 위에서 권한 매핑, 훅, 정책, 승인된 도구 접속을 다시 세우는 작업이다.

## 가장 강한 반론은 좁지만 중요한 구간에서 옳다

가장 강한 반대는 "재개 비용의 본체는 세션 맥락"이라는 주장이다. 이 반대는 보통 받는 대접보다 더 진지하게 다뤄야 한다.

도구를 갈아타며 긴 구현 세션 하나를 끌고 가는 개발자에게 맥락 재구축은 비싸다. 실측도 그 시각을 지지한다. 소스 세션의 순서 있는 대화, 도구 호출 이력, 도구 결과 이력은 그냥 버려지지 않았다. 이 도구는 빈 프롬프트에서 다시 시작하는 대신 작업 서사를 붙들고 갈 실용적인 경로를 준다.

규제 요구가 없고 하네스를 자주 갈아타며 승인 기록을 중앙화할 필요가 없는 개인이나 소규모 팀에게는 특히 값지다. 그 환경에서 144개 경로는 마케팅 숫자가 아니다. 실험의 마찰을 줄이고 쌓아 온 맥락을 지킨다.

정책이 안 따라오니 세션 이식이 무의미하다고 말하면 그건 과장이다. 세션은 여전히 가치 있는 연속성 자산이다.

다만 그 구간 밖에서는 내 판단이 그대로다. 옮겨진 세션은 원래 클라이언트의 인증, 훅, 정책, MCP 접속, 런타임 설정 없이 재개된다. 감사 대상 시스템을 다루는 팀에서 안전 통제는 작업 주변의 선택적 맥락이 아니다. 그 자체가 작업의 일부다.

사람, 리포지토리, 환경, 규제 제약이 늘어날수록 절약한 세션 맥락이 경제성을 좌우하는 몫은 줄어든다. 정책 통제를 다시 세우고, 권한을 검증하고, 승인 경로를 증명하고, 새로 생긴 데이터 반출 경로를 심사하는 일이 이사 예산을 다 먹는다.

## 세션은 버릴 수 있게, 거버넌스는 오래 가게

내가 권하는 운영 모델에는 게이트가 셋 있다.

첫째, 세션을 기록의 원본이 아니라 캐시로 선언한다. 결정과 근거와 되돌리기 절차는 PR 본문이나 승인된 작업 채널, 혹은 양쪽 모두에 남아야 한다. 리뷰 체크리스트에 한 줄을 추가한다. "이 판단의 근거가 에이전트 세션 밖에 있는가."

사소해 보이지만 행동을 바꾼다. 대화가 상세하다는 이유만으로 로컬 기록을 감사 산출물처럼 취급하는 습관을 막는다. 기록은 노트북 교체, 퇴사, 로컬 에이전트 디렉터리 정리 한 번으로 사라진다.

둘째, 감사 대상 리포지토리에는 반출 심사를 요구한다. 세션 이식이 꼭 필요하면 내보내기 전에 dry-run 매니페스트를 작업 티켓에 첨부하게 한다. 내용 없이 누락의 종류와 개수만 보고하는 매니페스트는 원본 세션 덤프보다 심사에 훨씬 적합하다. 심사자는 원문 내용을 더 퍼뜨리지 않고도 무엇이 나가고 무엇이 사라지는지 판단할 수 있다.

셋째, 승인과 권한과 아카이브의 집행 지점을 하나만 고른다. 채널이든 CI든 하나다. 기본값으로 둘 다 두지 않고, 에이전트 CLI마다 별도의 집행 모델을 심지도 않는다. 코드 오너와 CI 승인이 이미 단단한 팀이라면, 어떤 에이전트 제품이 채팅 승인 기능을 제공한다는 이유만으로 병렬 승인 체계를 하나 더 만들면 안 된다. 승인 평면이 둘이면 어느 결정이 유효한지가 흐려진다.

온보딩 문서에는 직설적으로 적으면 된다. CLI는 네가 편한 걸 고른다, 승인은 여기서만 나고 기록도 여기 남는다.

로컬 도구 선택의 자유는 지키되, 그 자유가 거버넌스를 조각내는 일은 막는 문장이다.

## Slack Code는 에이전트 연동 제품이 아니라 정책 평면 제품이다

Slack Code는 Claude, Devin, GitHub Copilot, Vercel 연동을 쓰는 팀에서 사용할 수 있고 ChatGPT는 조만간 지원 예정이라고 적혀 있다. 이 제품이 내건 약속은 모든 에이전트가 똑같이 사고하거나 똑같이 상태를 저장한다는 게 아니다. 작업을 공용 채널에서 시작할 수 있고, 조직에 이미 있는 Slack 통제를 그대로 물려받는다는 것이다.

코드 채널의 70% 이상이 착상에서 PR 머지까지 하루 안에 끝난다는 Slack의 수치는 벤더 참고값 이상으로 쓰면 안 된다. Slack은 방법론도, 모집단도, 측정 기간도 공개하지 않았다. 그 숫자 하나로 도입 근거를 세울 수는 없다.

그래도 워크플로 설계 자체는 전략적으로 타당하다. 기획, 디자인, 엔지니어링, 운영이 같은 요청을 보고 같은 산출물을 검토하고 그 결과 내려진 결정을 확인한다. 참여자 각자가 개발자의 로컬 하네스에 접근할 필요가 없다. 에이전트 백엔드가 바뀌어도 채널은 사람의 승인 경계를 담은 아카이브로 남는다.

Slack은 에이전트의 추론 과정 가시화를 출시된 기능이 아니라 앞으로의 과제로 적었다. session-migrate가 비공개·서명된 사고 흔적을 의도적으로 옮기지 않는다고 적은 것과 앞뒤가 맞는다. 에이전트 작업에서 설명이 가장 필요한 부분이 구조적으로 가장 덜 이식된다. 그 흔적은 모델 제공사에 묶여 있기 때문이다.

그러니 현실적인 감사 대상은 더 좁고 더 믿을 만한 쪽이다. 무엇을 요청했고, 무엇이 바뀌었고, 어떤 근거를 검토했고, 누가 승인했는가.

## CEO와 CTO가 벤더 교체 모델에 넣어야 할 것

세션 기록을 내보낼 수 있는지 물어서 에이전트 벤더 교체 비용을 추정하지 마라. 실제보다 한참 낮은 숫자가 나온다.

제대로 된 모델은 조직의 집행 평면이 하네스 밖에 있는지를 묻는다.

- 승인 규칙이 CLI 교체를 견디는가
- 권한과 MCP 접속을 중앙에서 소유한 설정으로 다시 세울 수 있는가
- 감사자가 개발자의 로컬 세션을 읽지 않고도 판단 근거와 승인 기록을 찾을 수 있는가
- 하나의 관리 화면에서 접근을 회수하거나 워크플로를 멈출 수 있는가
- 세션이 옮겨질 때 어떤 데이터가 나가는지 평가할 수 있는가

이 다섯 가지가 모두 그렇다면 에이전트 하네스는 교체 가능한 실행 도구에 가까워진다. 협상 지렛대가 생긴다. 모델이나 CLI를 바꿀 때마다 거버넌스를 새로 세울 필요가 없으니, 구매 부서가 가격과 품질과 통합 수준으로 벤더를 압박할 수 있다.

그렇지 않다면 벤더가 소유한 것은 인터페이스만이 아니다. 승인 로직과 접근 패턴과 운영 기억까지 가져간 상태다. 교체가 개발자의 불편이 아니라 조직의 리스크가 되므로 그 제품의 가격은 훨씬 통제하기 어려워진다.

에이전트 사용이 늘어날 때 어디에 투자할지도 여기서 갈린다. 라이선스를 더 사면 활동량이 늘어난다. 감사 평면의 처리량과 명료함을 올리면 조직이 늘어난다. 에이전트 도입이 아무도 검토하지 못하는 로컬 자동화 더미로 끝나지 않게 막는 쪽은 후자다.

## 이 처방이 맞지 않는 곳

Slack을 집행 평면으로 삼는 모델은 협업 표준이 Slack이 아닌 팀에는 통째로 무효다. 원칙은 그대로지만 정책 평면은 그 조직이 실제로 쓰는 공용 워크플로 시스템 위에 구현해야 한다.

CI와 코드 오너로 승인을 이미 잘 집행하는 팀에도 맞지 않는다. 채널을 두 번째 승인 권한으로 얹으면 증거 경로가 갈라져 오히려 나빠진다.

대화 로그를 제3자 SaaS에 보존하지 못하게 막힌 조직은 다른 아카이브 설계가 필요하다. 에이전트 요청이 하루 몇 건인 팀은 자동 생성된 채널이 운영 가치보다 아카이브 부담을 더 만든다고 느낄 것이다. 그리고 비공개 추론 흔적을 감사 증거로 요구하는 팀이라면, 이식 가능한 세션도 채널 아카이브도 지금은 그 요구를 풀어 주지 못한다는 사실을 인정해야 한다.

내 입장은 분명하다. 세션 이식은 개인의 연속성 도구로 쓰고 팀의 거버넌스 표준으로 올리지 않는다. 승인, 감사, 아카이브, 회수는 도구 중립적인 집행 평면 하나에 넣는다. 이 입장을 바꿀 조건은 하나다. 세션 포맷이 대화와 함께 이식 가능하고 중앙에서 검증 가능한 정책·신원 상태까지 싣기 시작할 때.
