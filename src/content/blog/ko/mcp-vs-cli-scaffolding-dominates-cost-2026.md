에이전트 구성에서 MCP 서버를 걷어내면 청구서가 실제로 줄어드는지 알고 싶었다. 내가 맡은 두 팀이 계속 당기려 하던 레버가 그것이었기 때문이다. 그래서 또 하나의 실무자 후일담 말고 통제된 측정을 찾아 나섰고, 하나 찾았다. 2026년 8월 9일 arXiv에 올라온 논문으로, 고정된 소프트웨어 태스크 하나를 에이전트 스캐폴딩 7종과 언어 모델 5종에 걸쳐 돌린 실험이다. 답은, 내가 엉뚱한 레버를 당기고 있었다는 것이다. 인터페이스는 거의 영향이 없었다. 그 위에 올라탄 하네스가 비용을 5.0배에서 28배까지 움직였다.

에이전트 예산 라인에 당신 이름이 달려 있다면 이건 남 얘기가 아니다. 내 결론은 이렇다. 비용 리포트의 그룹핑 키를 모델명에서 하네스명으로 바꿔라. 그리고 하네스를 고정하기 전까지는 "MCP가 CLI보다 N배 비싸다"류의 숫자를 의미 있는 수치로 취급하지 마라. 이 기소장에는 내 글도 포함된다. 몇 달 전 나는 MCP 토큰 비용을 인터페이스 문제로 프레이밍한 글을 냈다. 산술은 맞았더라도 진단 계층에서 틀린 프레이밍이었다.

## 이 실험이 실제로 잰 것

설계는 의도적으로 좁다. 태스크는 하나로 고정했다. 사설 온라인 git 저장소에 대한 6개 조작. 스캐폴딩 7종, 모델 5종, 모든 칸을 다 돌렸다.

> The dominant effect was the scaffolding. Two of the seven ship no MCP support at all; they completed every run using only the CLI, which shows that MCP is unnecessary for this class of work, and they were 5.0x to 28x cheaper than the five scaffoldings that do support MCP, comparing CLI runs alone with no MCP server attached anywhere.

> — [The Scaffolding Matters More Than the Interface](https://arxiv.org/abs/2608.08654)

이 비교문은 형태를 뜯어보며 읽어야 한다. 형태 자체가 논지를 떠받치고 있다. MCP 실행 대 CLI 실행이 아니다. MCP를 아예 못 쓰는 스캐폴딩의 CLI 전용 실행과, MCP를 쓸 수 있는 스캐폴딩의 CLI 전용 실행을 붙인 것이다. 양쪽 모두 서버는 붙이지 않았다. 비싼 쪽은 싼 쪽과 똑같은 일을 하면서 비쌌다.

정작 저자들이 재려고 나섰던 인터페이스 짝비교는 무너졌다. "thirteen strictly paired MCP-to-CLI ratios span 0.43x to 29x, with outliers on both sides." 양쪽 다 이상치가 나왔다. 어떤 짝에서는 MCP가 더 쌌다. 누군가 MCP 오버헤드를 단일 배수로 읊어 준다면, 그 사람은 이 분포에서 칸 하나를 골라 읽고 있는 것이다.

하네스도 태스크도 검증 코드도 데이터셋 전량도 오픈소스로 나왔다. 이 논문이 대체하려는 기존 추정치들보다는 훨씬 나은 조건이다. 논문은 자기가 무엇을 밀어내는지 직설적으로 적어 뒀다. 한 자릿수 이상 어긋나 있으면서 재현 불가능한 실무자 보고에 기대고 있던 수치들이다.

## 옛 숫자들을 무너뜨린 것은 측정 방식의 변경이다

여기서 인과로 확립된 것은 두 가지이고 나머지는 추론이다. 섞지 않고 가겠다.

첫째, 저자들은 완료 판정을 에이전트 자기보고가 아니라 저장소 상태 검사로 바꿨다. 기존 합의가 죽은 자리가 정확히 여기다. 에이전트가 스스로 했다고 말한 것으로 실행을 채점하면, 당신이 재고 있는 것은 모델이 승리를 선언하려는 성향이다. 그리고 그 성향은 하네스마다 다르다. 그동안 인터페이스 차이로 돌려졌던 분산의 상당 부분은, 완료를 어떻게 판정했느냐의 분산이었다.

둘째, 개인적으로 가장 불편했던 발견. 에이전트가 배정된 인터페이스를 자주 무시했다. 그러니 실제로 발화된 도구 호출을 검증하지 않은 A/B는 두 팔이 섞인 정체불명의 혼합물을 재고 있는 셈이다. 사내에서 돌아다니는 MCP 대 CLI 비용 비교를 여럿 봤고 그중 몇은 나도 고개를 끄덕이며 봤는데, 전부 그 검증 없이 만들어진 것들이었다.

내가 말해 줄 수 없는 것은, MCP 지원 스캐폴딩이 CLI로 돌면서 왜 더 비쌌는가다. 그럴듯한 이야기는 있다. 도구 스키마 슬롯, 디스커버리 레이어, 승인 흐름 같은 MCP 배관이 서버 부착 여부와 무관하게 매 턴 컨텍스트에 재상주한다는 설명. 그림은 맞아떨어진다. 그리고 나는 그 근거를 갖고 있지 않다. 논문은 비용을 턴 수와 턴당 입력 토큰으로 분해하지 않았고, 따라서 메커니즘은 열려 있다. 가장 극단적인 결과도 마찬가지다. 로컬에서 돌린 270억 파라미터 모델은 스캐폴딩에 따라 비용이 139배 벌어졌는데, 모든 스캐폴딩에서 태스크는 완료했다. 분산은 보고됐다. 원인은 모른다.

## 세 개의 축, 그리고 다들 만지고 있는 하나

이 실험에는 변수가 셋 있다. 얼마나 크게 움직였는가와, 당신이 얼마나 통제할 수 있는가를 나란히 놓고 순위를 매길 만하다.

인터페이스, MCP 대 CLI. 논문이 재려고 만든 축인데, 거의 아무 데서도 갈리지 않았다. 실패 빈도는 양쪽이 동일했다. 원래 실행에서도, 반복 실행에서도. 딱 한 군데서 갈렸다. 실패의 값이다. "12.9 per cent of the money spent on MCP runs bought no completed work against 2.2 per cent on CLI runs." 같은 실패율, 실패 한 번당 여섯 배의 낭비. 당신 대시보드가 완료율만 추적한다면 이 차이는 보이지 않는다.

스캐폴딩, 하네스 7종. 실제로 지배한 축이다. 모델과 태스크를 고정한 채 5.0배에서 28배.

모델, 5종. 주로 민감도 배율로 작용했다. 작은 모델일수록 하네스 선택에 더 노출됐고, 27B에서 139배가 나온 이유가 그것이다.

실무가 실제로 통제 가능한 순서는 스캐폴딩, 인터페이스, 모델 순이다. 내가 대화해 본 대부분의 팀은 이 목록을 거꾸로 붙잡고 있다. 하네스는 자유롭게 떠다니게 두고 모델 단가를 협상하고 프롬프트를 다듬는다.

## 진지하게 받는 반론, 무대가 CLI에 유리하게 짜였다

이 모든 것에 대한 가장 강한 반박은 표본이 결론을 미리 골랐다는 것이다. 태스크는 하나. 저장소에 대한 git 조작 6개. git은 20년 동안 명령줄이 다듬어져 온 영역이고, 우리 분야에서 가장 CLI 성숙도가 높은 표면이라 해도 무리가 없다. git에서 CLI가 이겼다는 말은 못이 박히는 데 망치가 이겼다는 말에 가깝다.

이 반론에는 한 문단 이상을 내주고 싶다. 트집이 아니고, 탄약도 논문이 직접 건네주기 때문이다. 5.0배에서 28배라는 수치는 애초에 인터페이스 비교가 아니다. 스캐폴딩 두 집단, MCP 미지원 2종과 MCP 지원 5종의 비교다. 집단 소속은 MCP 지원 여부와 상관있지만, 그 7개 도구가 어떻게 만들어졌는지에 관한 나머지 전부와도 상관있다. 기본 컨텍스트 처리 방식, 재시도 로직, 시스템 프롬프트 크기. 인터페이스를 분리해 낼 짝비교는 0.43배에서 29배로 돌아왔다. 그건 발견이 아니라 어깨를 으쓱한 것이다.

그래서 내가 양보하는 지점은 이렇다. 표현이 아니라 적용 범위를 양보한다. 이 논문의 처방을 그대로 옮기면 안 되는 구간이 셋 있다.

CLI 등가물이 없는 도메인. 내가 맡은 데이터 서비스 팀이 에이전트에 열고 싶어 하는 것 대부분이 여기 해당한다. 회원 레코드, 프로필 데이터, 동의 이력. 이런 호출의 권한 판정은 파일시스템 경계 바깥에 있고, 거기까지 닿는 CLI를 만든다는 것은 누군가의 노트북에 자격증명을 쥔 바이너리를 하나 심는다는 뜻이다. 비용 결정의 문제가 아니다.

하네스 선택권이 없는 팀. 보안 심사나 조달이 이미 하네스를 지정해 뒀다면, 이 실험에서 지배적이던 변수는 당신이 만질 수 있는 물건이 아니다. 그 경우 논문의 조언은 불평으로 축소된다.

git 조작 6개와 형태가 다른 태스크. 긴 다중 서비스 오케스트레이션, 승인 왕복과 대화형 확인이 도구 계층에 있어야 하는 워크플로. 표본 밖이다. 이런 자리에서 인터페이스 선택은 비용 결정의 옷을 입은 사용자 경험 결정이다.

반론을 통과하고 남는 것은 git에 전혀 의존하지 않는 부분이다. 인터페이스 효과가 가장 잘 드러났어야 할 태스크에서, 하네스가 인터페이스를 대략 한 자릿수 배수로 압도했다. 그리고 완료는 자기보고가 아니라 산출물로 검증됐다. git이 인터페이스 비교를 기울였다고 믿더라도, 변수의 서열까지 기울인 것은 아니다. 내 결론은 범위를 좁혀 그대로 선다. 성숙한 CLI가 이미 있는 작업이라면 CLI 전용 하네스를 표준으로 잡아라. 그 밖의 자리에서는 MCP를 유지하되, 어차피 하네스부터 고정하라.

## 진짜 아키텍처 질문이 놓인 자리

같은 요구가 두 팀에서 옷만 갈아입고 올라온다. 리뉴얼 팀은 에이전트에 저장소 조작, 빌드, 린트를 맡기고 싶어 한다. 데이터 서비스 팀은 에이전트가 회원과 동의 데이터를 읽게 하고 싶어 한다. 양쪽에 대한 우리 반사행동은 같았다. MCP 서버를 하나 세운다.

논문은 그 반사행동을 둘로 가른다. 그런데 그 갈라짐이 정확히 무엇인지는 두 번째 출처를 봐야 잡혔다.

> The harness guides what an agent tries. The infrastructure controls what an agent can do. Both are necessary; only one is authoritative.

> — [Where Security Fits in an AI Agent Stack](https://developer.nvidia.com/blog/where-security-fits-in-an-ai-agent-stack)

MCP 프로세스도, 플러그인도, 모델이 지시하는 코드도 전부 하네스 경계 안에서 돈다. 수정되도록 설계된 계층은 자기 자신의 수정을 상대로 통제를 강제할 수 없다. 이게 질문 전체를 다시 짠다. 애초에 MCP 대 CLI가 아니었다. 어떤 도구 호출의 권한 판정이 하네스 안에 있느냐 밖에 있느냐다. 안에 있다면 당신이 세운 것은 통제처럼 보이는 안내이고, 감사에서는 통제로 읽힐 것이다. 아닌 날이 오기 전까지는.

저장소 조작이라면 권한은 이미 바깥에 있다. git 자격증명, 브랜치 보호 규칙, CI 게이트. 감사 흔적은 셸 히스토리다. 여기에 MCP 서버를 얹으면 유지보수 대상이 하나 늘고 하네스 선택지가 좁아지며, 통제는 하나도 늘지 않는다. 회원과 동의 데이터라면 권한 판정은 마찬가지로 하네스 바깥에 있어야 하고, 그건 API 경계와 그 자체의 로깅을 뜻한다. MCP나 그에 준하는 것은 그 위를 오가는 전송 수단이다. 전송은 통제가 아니다. 내가 뭉개고 있던 구분이 그것이다.

## 넣기로 한 게이트 셋

팁이 아니다. 게이트다. 이런 통찰의 실패 양상은 시니어 한 명이 적용하고 아무도 눈치채지 못한 채 끝나는 것이기 때문이다.

하네스 단일화가 먼저다. 팀당 하네스 한 종, 버전 고정. 제일 심심한 항목이고 이게 발견의 전부다. 하네스가 떠다니는 동안에는 어떤 비용 리포트도 읽히지 않고 어떤 A/B도 의미가 없다. 누군가 도구를 업그레이드할 때마다 지배 변수를 다시 재고 있는 셈이니까.

도구 등록 심사가 둘째다. 새 MCP 서버를 붙이려면 이제 두 질문에 답하는 1페이지를 낸다. 이 작업에 성숙한 CLI가 있는가. 있으면 기각, 그걸 써라. 권한 판정이 하네스 밖에 있는가. 안에 있다면 도구 정의 근처에 오기 전에 인프라 계층으로 되돌린다.

완료 검증이 셋째고, 아플 거라고 예상하는 항목이다. 우리 CI는 에이전트 실행 결과를 그 실행이 스스로 보고한 내용으로 집계한다. 논문의 결론은 그 짓을 그만둔 순간 바뀌었고, 똑같은 약점이 우리 파이프라인에 손대지 않은 채 앉아 있다. 완료는 산출물 상태로 판정한다. 저장소 diff, 테스트 통과, 스키마 검증.

여기에 팀 대시보드 지표 하나를 1급으로 올린다. 완료 없이 태워진 토큰 비중. 12.9 대 2.2라는 격차가 두 인터페이스 사이의 실질적 차이 전부이고, 그건 성공률 차트가 정확히 가려 주는 종류의 것이다. 지금 우리 리포트에는 실패에 쓴 돈을 담는 줄이 없다.

## CTO가 여기서 가져갈 것

결론은 "MCP를 버려라"가 아니다. 당신의 비용 진단이 한 계층 아래를 겨누고 있다는 것이다.

동일한 모델과 동일한 태스크에서 스캐폴딩 교체만으로 지출이 5배에서 28배 움직이고 작은 로컬 모델에서는 139배 움직인다면, 에이전트 예산에 걸 수 있는 가장 큰 레버는 벤더 단가 협상도 프롬프트 튜닝도 아니다. 하네스 표준화다. 따라오는 따끔한 귀결이 하나 있다. 팀마다 하네스를 알아서 고르게 두면 팀 간 비용 분산이 한 자릿수 배수로 벌어지고, 그 분산은 재무 리포트에서 모델 요금 변동으로 나타난다. 엉뚱한 열에서 누수를 찾게 된다.

출시 속도도 같은 방향을 가리킨다. 그리고 여기서는 이 주장을 할 이유가 전혀 없는 벤더 쪽에서 근거가 나온다.

> Harness design can materially change results: on ARC-AGI-3, retained reasoning and context compaction raised GPT-5.6 Sol's score from 13.3% to 38.3% while reducing output tokens sixfold.

> — [Codex as a platform: build on the open agent harness](https://developers.openai.com/blog/codex-as-a-platform)

같은 모델. 하네스 변경뿐. 점수는 거의 세 배, 출력 토큰은 6분의 1. 학계와 상용, 서로 독립인 두 출처가 소유자가 거의 없는 계층 하나로 수렴한다.

컴플라이언스는 반대 방향으로 자른다. 비용 논지가 글 전체를 끌고 가게 두지 않기 위해 명시해 둔다. 권한 판정을 하네스에 두면 그건 통제가 아니라 안내다. 감사 가능한 강제는 인프라 계층의 몫이다. 민감한 시스템이라면 비용이 더 들더라도 제대로 경계 지어진 MCP 경로를 유지할 근거가 여기 있고, 비용 배수는 그에 대한 반박이 되지 못한다.

내일 딱 하나만 바꾼다면, 에이전트 비용 리포트의 그룹핑 키를 모델명에서 하네스명으로 바꿔라. 쿼리 한 줄 고치는 일이다. 그동안 모델 탓으로 돌리던 분산이 애초에 모델의 문제였는지, 하루면 알려 줄 것이다.

내 입장을 그대로 적는다. 성숙한 명령줄이 이미 있는 표면, git과 컨테이너와 클라우드 도구와 빌드 체인에서 돌리는 에이전트 작업이라면 MCP는 오버헤드이고 나는 붙이지 않겠다. 권한이 파일시스템 경계 바깥에 걸린 내부 시스템이라면 유지하고, 하네스를 고정하고, 실패 비용을 따로 예산에 잡는다.

내가 틀렸음을 증명할 방법. 같은 비교를 긴 다중 서비스 오케스트레이션 태스크에서 돌리고, 실제로 발화된 도구 호출을 검증하고, 스캐폴딩 분산이 한 자릿수 배수를 크게 밑돌 만큼 줄어드는 동시에 인터페이스 분산이 벌어지는지 보면 된다. 그렇게 나온다면 지배 변수는 처음부터 태스크였고 나는 git에서 일반화를 한 것이다.

이 논문이 가장 세게 흔든 것은 MCP의 평판이 아니었다. 에이전트를 그 자신의 증언으로 채점해 온 습관이었다. 우리 업계가 실측이라 부르는 것 대부분은 통제되지 않은 채 한 번 돌려 보고 이야기를 붙인 것이고, 그중 일부는 내가 썼다.
