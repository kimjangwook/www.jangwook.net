# 400% 줌 리플로우: 82픽셀은 어디로 사라지는가

본문 첫 단락 하나를 읽히기 위해 뷰포트에서 실제로 남는 세로 픽셀이 얼마일지, 팀에서 그 숫자를 추적하고 있는가. 우리 팀은 320px 폭, 높이 200픽셀 조건에서 그 값이 118픽셀임을 실측했다. 나머지 82픽셀은 문장 한 줄에 닿기도 전에 사라진다. 그리고 그 손실은 어느 뷰포트에서든 정확히 82픽셀로 고정되어 있었다.

이 글은 그 측정 결과를 바탕으로 세 가지를 다룬다. 손실의 주인이 누구인지, 퍼센트 지표가 왜 최악의 사례를 가려 버리는지, 그리고 수정 우선순위를 어떻게 정할지다. 스펙을 다시 읽는 일에서 시작해 실측과 귀속, 결론까지 순서대로 간다.

## 400%는 면적이 아니라 차원이다

WCAG 성공 기준 1.4.10 Reflow는 단단한 바닥을 깐다. 콘텐츠는 정보나 기능의 손실 없이, 2차원 스크롤 없이 제시될 수 있어야 한다. 세로 스크롤 콘텐츠는 폭 320 CSS 픽셀에 해당하는 너비에서, 가로 스크롤 콘텐츠는 높이 256 CSS 픽셀에 해당하는 높이에서 말이다. 400% 줌이라는 표준 관계에서 이 320px 폭은 대략 320×256 뷰포트에 대응한다.

여기서 흔히 틀리는 계산이 있다. 400%를 면적으로 읽는 것이다. W3C 이해 문서는 명확하다. 400%는 차원에 적용된다. 기본 줌 뷰포트 폭의 4배, 높이의 4배가 각각 독립적으로 적용된다. 폭과 높이를 따로 검사해야 한다는 뜻이다.

그래서 우리는 페이지 템플릿 4종(post, post2, index, home)과 뷰포트 높이 4종(844, 400, 256, 200)에서, 폭 320 고정, 페이지 상단 상태와 스크롤 중간 상태 두 가지로 뷰포트 예산 감사를 돌렸다. 결과의 헤드라인이 위의 118픽셀이다.

## 유치원생도 이해하는 예산 회의 비유

뷰포트를 한 달 예산이라고 생각해 보자. 총 수입은 뷰포트 높이라는 고정급이다. 그런데 페이지 위의 고정·스티키 요소들은 전부 선급 공제항목이다. 헤더가 먼저 급여를 가져가고, 하단 광고 컨테이너가 그다음을 가져가고, back-to-top 버튼이 명목상 지분을 주장한다.

문제는 이 회의에서 아무도 삭감안을 내지 않는다는 점이다. 뷰포트가 844픽셀일 때 헤더의 82픽셀은 월급에서 공제되는 소액 보험이라서 아무도 신경 쓰지 않는다. 뷰포트가 200픽셀로 줄어들면 같은 82픽셀이 급여의 절반 가까이를 가져간다. 고정급은 줄었는데 공제항목은 그대로다. CSS 레이아웃 엔진은 회의 진행자인데, 예산 초과를 막는 상한 제어도 없고, 초과돼도 에러를 뱉지 않는다. 조용히 마이너스 통장을 열어줄 뿐이다.

이 비유가 유치하게 들리는 이유는 레이아웃 버그가 대부분 "어디선가 뭔가가 밀린다"는 막연한 인상으로 다뤄지기 때문이다. 실측으로 바꾸면 이야기가 달라진다. 공제항목의 명세가 픽셀 단위로 나오고, 누가 얼마를 가져가는지 귀속이 나온다. 다음 절이 그 내용이다.

## 세부: 측정 결과가 말해주는 것

### 가로 판정은 깨끗하게 통과한다

먼저 좋은 소식부터. 8개 테스트 행 전부에서 1.4.10의 가로 판정이 통과했다.

| 템플릿 | h | clientWidth | scrollWidth | h_overflow_px | reflow_pass |
|--------|-----|-------------|-------------|---------------|-------------|
| post | 844 | 320 | 320 | 0 | true |
| post | 200 | 320 | 320 | 0 | true |
| post2 | 844 | 320 | 320 | 0 | true |
| post2 | 200 | 320 | 320 | 0 | true |
| index | 844 | 320 | 320 | 0 | true |
| index | 200 | 320 | 320 | 0 | true |
| home | 844 | 320 | 320 | 0 | true |
| home | 200 | 320 | 320 | 0 | true |

모든 행에서 clientWidth 320 = scrollWidth 320, 가로 오버플로 0이다. 레이아웃은 가로 차원에서 정확히 리플로우된다. 감사를 여기서 멈추면 — 많은 팀이 여기서 멈춘다 — 이 사이트는 리플로우 준수라는 결론에 도달한다.

### 세로 예산은 다른 이야기를 한다

돈이 나가는 곳은 세로다. h=200, 페이지 상단 상태에서 6회 재현 모두 동일한 값을 얻었고, 2026-08-09 자체 감사와도 일치한다.

```
usable_px 118 (h=200)
```

뷰포트 200픽셀 중 콘텐츠에 전달되는 것은 118픽셀이다. 그 82픽셀 공백은 비례항이 아니라 절대 상수다. 네 뷰포트 높이 전부에서 손실이 동일하다.

```
844 − 762 = 82
400 − 318 = 82
256 − 174 = 82
200 − 118 = 82
```

이 데이터셋에서 가장 중요한 성질이고, 퍼센트로 사고하면 직관에 반한다. 퍼센트 기반 멘탈 모델에서는 고정 헤더를 "뷰포트의 10% 비용"이라고 부른다. 틀렸다. 그 헤더는 82픽셀이다. 그 이상도 이하도 아니다. 분모인 뷰포트 높이는 바뀌어도 세금은 안 바뀐다. 이것은 트래픽 비례 과금이 아니라 정적으로 할당된 샤드 같은 고정 예약이다.

### 귀속: 82픽셀의 주인은 누구인가

각 높이에서 요소별 위치와 크기를 계측하면 귀속이 깔끔하게 나온다. 상단 상태의 82픽셀 손실 주체는 **static 헤더 블록**이지 fixed나 sticky 크롬이 아니다. 헤더는 모든 페이지, 모든 높이에서 82픽셀이고, 위치 모드는 바뀐다. h=844에서 sticky, h=200에서 static — 6회 재현 모두 확인했다.

이 반전 자체가 흥미롭다. 뷰포트가 무너지면 헤더가 sticky에서 static으로 강등된다. 들어보면 우아한 동작이다. 스티키 레이어가 물러나 주니까. 하지만 레이아웃 비용은 그대로다. 헤더는 붙든 안 붙든 같은 82픽셀을 점유한다. 동작을 강등해도 예산에는 아무 일도 일어나지 않았다.

스크롤 중간 상태에는 두 번째 소비자가 등장한다. 스크롤 후 손실은 90픽셀이고, 귀속 결과 단일 요소로 격리된다. 뷰포트와 무관하게 400px 높이를 유지하는 고정 높이 하단 광고 컨테이너(#fixed_container_bottom)다.

```
#fixed_container_bottom 제거: 200 (Δ +90)
fixed/sticky 전부 제거:       200 (Δ +90)
개별 델타 합 = ALL 제거 합
```

가산성이 정확하다. 광고 컨테이너만 제거해도 90픽셀 전부가 회복되고, 전부 제거해도 같은 90픽셀만 회복된다. 겹침도, 숨은 상호작용 비용도 없다. 각 픽셀에게 정확히 한 명의 주인이 있다. 경쟁도, 이중 계상도, 요소 겹침에서 튀어나오는 창발 비용도 없다.

이 귀속이 주는 실무적 안도감은 크다. "뭔가 복합적으로 꼬여 있을 것 같은" 세로 레이아웃 문제가 실제로는 원인 두 개, 즉 82픽셀 헤더와 90픽셀 광고 컨테이너로 완전히 분해됐다는 뜻이기 때문이다.

### back-to-top 버튼: 눈에 보이지만 공짜다

직관에 반하는 세 번째 결과가 있다. 화면 오른쪽 아래에 떠 있는 fixed back-to-top 버튼(높이 48픽셀, 스크롤 중간 상태에서 보인다)은 세로 예산 단독 비용이 0픽셀이었다.

```
#back-to-top 제거: 110 (Δ 0)
```

보이는 크롬이 전부 세로 공간을 먹는 건 아니다. 이 버튼은 콘텐츠 흐름 밖에서 떠 있고, 본문 위에 정확히 겹쳐지지 않는 자리를 차지하기 때문에 예산 계산에서 공제되지 않는다. 시각적으로는 "페이지를 덮는 요소"로 보이지만, 세로 예산 회계에서는 공짜다. 반대로 예산을 잠식하는 요소는 겉으로는 그렇게 보이지 않을 수 있다. 헤더가 그 경우다.

### 퍼센트 지표가 최악의 사례를 가리는 방법

같은 90픽셀 광고 컨테이너의 손실률을 뷰포트 높이별로 보면 이렇다.

- h=844, 스크롤 중간 상태: 10.7%
- h=200, 페이지 상단 상태: 41.0%
- h=200, 스크롤 중간 상태: 45.0%

10.7%는 회의에서 통과되는 숫자다. "모니터 사용자에게 하단 광고가 10% 정도를 차지한다"고 말하면 반론이 잘 나오지 않는다. 그런데 같은 요소가 h=200 스크롤 중간 상태에서는 본문 세로 공간의 45%를 가져간다. 거의 절반이다.

퍼센트 지표의 구조적 문제는 분모가 조용히 바뀐다는 점이다. 분모가 크면 손실이 작아 보이고, 분모가 작으면 같은 절대 손실이 격해져 보인다. 그런데 접근성이 무너지는 지점은 정확히 분모가 작은 곳, 즉 저사양 기기와 강제 줌 사용자의 뷰포트다. 평균 손실률을 보고하면 가장 도움이 필요한 사용자의 상황이 숫자상으로 가장 덜 심각해진다. 절대 픽셀 값은 이 역설을 피한다. 82픽셀은 82픽셀이고, 어느 분모에서도 같은 의미를 갖는다.

## 결정과 비용: 무엇부터 고칠 것인가

측정과 귀속이 끝났으면 남는 것은 결정이다. 픽셀 회계가 주는 결정 프레임은 단순하다. 회복 가능한 픽셀의 크기와 수정 비용을 나란히 놓고 순서를 정하는 것.

가장 큰 단일 회복처는 하단 광고 컨테이너다. 90픽셀이고, 귀속이 단일 요소라서 수정 범위가 명확하다. 뷰포트 높이에 연동해 400px 고정값을 내리거나, 저뷰포트 조건에서 렌더링을 미루는 방향이 있다. W3C 기법 C34가 정리하는 것처럼, sticky나 fixed 영역은 다른 콘텐츠가 그 아래로 사라지는 동안 항상 뷰포트에 남는다. 즉 이런 크롬은 작은 뷰포트에서 가장 먼저 희생될 후보다. 광고 수익과의 트레이드오프는 있겠지만, 45%라는 손실률은 트레이드오프 논의의 출발점이 될 만한 크기다.

헤더는 더 어렵다. 82픽셀이고, static 헤더 블록이라 귀속은 명확하지만 사이트 전역 요소라 수정 파급 범위가 넓다. 다만 h=200에서 이미 sticky에서 static으로 강등되어 있다는 사실은 힌트가 된다. 레이아웃은 이미 저뷰포트를 위한 분기를 갖고 있는데, 분기가 크기 축소까지는 하지 않는 것이다. 저뷰포트 조건에서 헤더를 압축하는 규칙을 추가하는 것이 구조 재작업보다 비용이 낮다.

back-to-top 버튼은 손대지 않는다. 비용이 0픽셀인 요소를 고치는 것은 회의 시간 낭비다. 귀속 데이터가 이런 "보이는 용의자"를 빠르게 무죄 처리해 주는 것도 감사 자동화의 이득이다.

가로 방향은 이미 8개 행 전부 통과이므로 투자할 곳이 아니다. 요점은 이것이다. 리플로우 준수 판정을 가로 차원에서만 끝내면 합격이 나오지만, 세로 차원에서는 h=200 스크롤 중간 상태에서 본문이 절반 가까이 잠식당한다. 감사 자동화를 세로 예산까지 확장하고, 보고 지표를 퍼센트가 아니라 절대 픽셀과 최악 케이스 값으로 바꾸는 것이 이번 실측이 남기는 프로세스 결론이다.
