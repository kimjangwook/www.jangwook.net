8월 19일 `/tmp` 밑에 디렉터리 일곱 개를 만들고 CLAUDE.md를 일곱 가지 방식으로 설정했다. claude 2.1.233 헤드리스 환경에서 조건마다 세 번씩 총 스물한 번을 돌렸다. AGENTS.md에는 캐너리 문자열 ZQ7CANARY를 심었고 캐너리가 답변에 찍히면 그 조건에서 파일이 컨텍스트에 실렸다는 뜻이다.

`@AGENTS.md` import와 심볼릭 링크는 리포 안에 있는 파일을 가리킬 때는 똑같이 동작한다. 리포 밖 파일을 가리키는 순간 갈린다. 격차는 어중간하지 않았다. 한쪽은 헤드리스 세 번 모두 통과했고 다른 쪽은 세 번 모두 실패했다. 공식 문서는 두 방식을 나란히 적어놓고 "이래도 되고 저래도 된다"는 인상을 준다. 어느 쪽이 통과했고 왜 이렇게 갈렸는지는 아래에서 하나씩 짚는다.

## 스물한 번의 결과표

지난 글에서는 같은 리포에서 두 CLI가 지시문 파일을 읽는지만 쟀고 그때 심볼릭 링크는 3/3으로 통과했지만 import 경로는 재지 않은 채 남겨뒀다. [그 미해결 변수](/ko/blog/ko/agents-md-vs-claude-md-loading-measured-2026/)를 이번에 파고들었다. 일곱 조건을 그대로 옮기면 이렇다.

측정 방법은 이렇다. `/tmp` 아래 조건별 디렉터리를 파고 각 디렉터리에서 `claude -p 'Reply with exactly the word OK and nothing else.'`를 세 번씩 던졌다. 출력은 `--output-format json`으로 받아 응답 본문만 떼어 캐너리 유무를 셌다. 프롬프트를 OK 한 단어로 좁힌 이유가 있다. 지시문이 실렸다면 캐너리가 그 좁은 응답에 끼어드는 위반 흔적이 또렷하게 남기 때문이다. 비대화형 실행의 init 이벤트에는 memory_paths 필드가 있어 기대를 걸어봤지만 여기에는 auto memory 디렉터리 경로만 찍혔고 CLAUDE.md 경로는 어느 조건에서도 나오지 않았다. 결국 캐너리가 유일한 계기판이었다.

| 조건 | 설정 | 결과 |
|---|---|---|
| a | `CLAUDE.md = "@AGENTS.md"`, 상대경로, 리포 내부 | 3/3 |
| b | `CLAUDE.md -> AGENTS.md`, 심볼릭 링크, 리포 내부 | 3/3 |
| c | `CLAUDE.md` = AGENTS.md 일회성 복사(`/import` 근사) | 3/3 |
| d | AGENTS.md만 있고 CLAUDE.md 없음(대조군) | 0/3 |
| e | `CLAUDE.md = "@/tmp/.../AGENTS.md"`, 절대경로, 리포 외부 | 0/3 |
| f | `CLAUDE.md = "@<리포 내부 절대경로>/AGENTS.md"` | 3/3 |
| g | `CLAUDE.md -> 리포 밖 파일`, 심볼릭 링크 | 3/3 |

조건 c는 `/import` 커맨드를 직접 돌린 결과가 아니라 그 산출물을 손으로 근사한 것이다. AGENTS.md 내용을 CLAUDE.md에 한 번 복사해 넣은 상태이며 커맨드가 하는 일이 바로 이 1회 복사이므로 로딩 여부만 보면 같은 자리에 선다. 조건 d는 대조군이다. AGENTS.md만 두고 CLAUDE.md를 아예 안 만들면 0/3이 나와야 실험대가 제대로 놓인 것이고 실제로 그렇게 나왔다. a·b·c가 전부 3/3이라는 건 리포 안에서라면 공식 문서의 세 경로가 모두 작동한다는 뜻이다. 갈라지는 지점은 리포 밖을 가리키는 e·f·g뿐이다.

조건 e를 조금 더 파봤다. "프로젝트 지시문을 그대로 출력하라"고 시켰더니 모델은 `@/tmp/claudemd-lab-ext/AGENTS.md`라는 한 줄의 확장되지 않은 리터럴을 그대로 돌려줬다. 경고도 에러도 없었다. import 대상의 내용은 애초에 컨텍스트에 도달하지 못했지만 그 사실을 알려주는 신호가 아무것도 없었다.

승인 상태가 남는지도 봤다. 프로젝트에 `.claude/` 디렉터리는 생기지 않았고 홈 설정에도 경로 기록이 없었다. 그렇다면 승인 기록은 대체 어디에 남는 걸까. 사용자 세션 안 어딘가라는 짐작만 남았다.

## 문서가 나란히 적어놓은 두 갈래 길

이 결과가 왜 나왔는지 문서를 다시 열어봤다. Claude Code의 공식 메모리 문서는 이렇게 못 박는다.

> Claude Code reads `CLAUDE.md`, not `AGENTS.md`. If your repository already uses `AGENTS.md` for other coding agents, create a `CLAUDE.md` that imports it so both tools read the same instructions without duplicating them.

> [How Claude remembers your project](https://code.claude.com/docs/en/memory)

바로 다음 문단에서 같은 문서는 두 번째 경로를 소개한다. "A symlink also works if you don't need to add Claude-specific content." 명령은 `ln -s AGENTS.md CLAUDE.md` 한 줄이다. 세 번째 경로는 `/import` 슬래시 명령이다. AGENTS.md 내용을 CLAUDE.md로 한 번 복사해 넣고 MCP 서버, 커맨드, 서브에이전트, 스킬까지 함께 옮긴다. v2.1.213 이상에서만 쓸 수 있다.

import 경로 문법도 문서에 적혀 있다. 상대 경로와 절대 경로 둘 다 쓸 수 있고 상대 경로는 import를 적은 파일 기준으로 풀린다. 가져온 파일이 다시 다른 파일을 가져오는 재귀도 허용되는데 깊이는 최대 4홉으로 막혀 있다. 윈도우 쪽 단서도 하나 붙는다. 윈도우에서 심볼릭 링크를 만들려면 관리자 권한이나 개발자 모드가 필요해서 문서는 윈도우 사용자에게 import 쪽을 권한다. 토큰을 아끼려고 import로 파일을 잘게 쪼개는 시도는 효과가 없다는 문장도 문서에 못박혀 있다. 가져온 파일은 세션 시작 때 어차피 전부 실리기 때문에 분할한다고 컨텍스트가 줄지 않는다.

세 경로 모두 "AGENTS.md 하나로 여러 도구를 먹인다"는 같은 목표를 향한다. 문서는 세 경로를 취향 문제처럼 배치했다. import 경로는 문자열을 그대로 들고 있다가 나중에 판단하고 심볼릭 링크는 파일시스템이 먼저 처리한다는 차이는 적어두지 않는다. 방금 본 표의 조건 e와 조건 g가 왜 갈렸는지는 이 문서만 읽어서는 안 보인다.

## 필터가 걸리는 층이 다르다

표의 조건 e와 조건 g는 둘 다 리포 밖 파일을 가리키는데 결과만 정반대였다. 이 대조를 짚어야 하는 이유는 여기에 있다. 결과가 갈렸다는 사실만으로는 다음에 무엇을 바꿔야 할지 알 수 없기 때문이다. 심볼릭 링크는 파일시스템이 푼다. Claude Code의 메모리 로더가 CLAUDE.md를 여는 시점에는 커널이 이미 링크를 따라가 대상 파일의 바이트를 건네준 뒤다. 로더 입장에서는 리포 루트에 평범한 파일 하나가 있을 뿐이고 파일 내용이 리포 밖에서 왔다는 정보 자체가 그 시점에는 존재하지 않는다.

`@` import는 다르다. 로더 자신이 그 경로를 문자열로 쥐고 있다. 경로가 작업 디렉터리를 벗어나는지 스스로 판단할 수 있고 벗어난다면 승인 게이트 앞에 세운다. 이 동작을 확실히 보여준 건 대조 조건이었다. 절대경로지만 리포 안을 가리킨 조건 f는 3/3으로 통과했다. 심볼릭 링크로 리포 밖 파일을 가리킨 조건 g도 3/3으로 통과했다. 절대경로 문법도 리포 밖이라는 위치도 변수가 아니었다. 어느 층이 경로를 해석하느냐가 유일한 변수였다.

## 여섯 축으로 나란히 놓으면

| 기준 | @import | symlink | `/import` 일회성 복사 |
|---|---|---|---|
| 리포 내부 로딩 | 3/3 | 3/3 | 3/3 |
| 리포 외부 참조 | 승인 게이트, 헤드리스 0/3 | 3/3 | 복사 시점에 고정 |
| 원본과 동기화 | 유지됨 | 유지됨 | 끊김 |
| Windows 이식성 | 문제없음 | 권한과 체크아웃 변수 | 문제없음 |
| Claude 전용 절 추가 | 가능 | 불가능 | 가능 |
| 실패 신호 | 침묵 | 깨진 링크 = 파일 없음 | 신호 없이 그냥 낡아감 |

실패 신호 행만 봐도 침묵, 깨진 링크, 낡아감으로 세 갈래가 저마다 다르다. 첫 행만 세 경로가 같고 나머지 다섯 행은 전부 갈린다. 그런데도 셋을 "이래도 되고 저래도 된다"로 묶어놓은 문장이 어떻게 살아남았는지는 다음 절에서 봐야 알 수 있다.

## "승인 한 번이면 끝난다"는 반론

이 결과를 보면 반론이 바로 나온다. "조건 e가 실패한 건 헤드리스라 승인 다이얼로그를 띄울 화면이 없어서일 뿐이다. 실제 작업은 대화형이고 한 번 승인하면 그만이다."

솔로 개발자가 자기 컴퓨터에서 대화형으로 일하는 상황이라면 이 반론이 맞다. 승인은 정말 한 번뿐이고 승인한 뒤에는 import가 심볼릭 링크와 다를 바 없이 동작하면서도 Claude 전용 절을 아래에 더 붙일 수 있다는 이점까지 남는다.

이 반론이 무너지는 자리는 세 곳이다. 첫째, CI, 훅, 크론, 방금 생성된 서브에이전트에는 승인을 눌러줄 사람이 아예 없다. 화면이 없는 게 아니라 화면을 볼 사람이 없다. 게이트는 영원히 열리지 않는다. 둘째, 승인은 사용자와 기기에 묶인다. 새 팀원이 합류할 때마다 같은 다이얼로그를 다시 만나고 문서에 따르면 그중 한 번이라도 신중치 못하게 거절하면 그 거절은 영구적이다. 셋째는 좀 더 애매하다. 승인 상태가 리포에 커밋되지 않는다는 건 확인했지만 오늘 대화형으로만 돌아가는 리포가 내일도 그러리라는 보장이 어디서 깨지는지는 팀마다 다르다. 훅 하나, 야간 크론 하나가 추가되는 순간일 수도 있고 그런 변화 없이도 어느 날 그냥 조용해질 수도 있다.

## 그래서 어디서 막히나

내일 아침 import 설정을 확인하는 방법은 짧다. `grep -n '^@' CLAUDE.md`로 import 줄을 뽑고 그 경로가 작업 디렉터리 밖으로 나가는지 하나씩 본다. 나간다면 그 줄을 심볼릭 링크로 바꾸거나 대상 파일을 리포 안으로 옮긴다. 둘 다 오늘 당장은 못 한다면 최소한 캐너리를 심어두고 CI에서 생존 여부를 잰다. AGENTS.md에 마커를 찍으라는 줄 하나를 추가하고 `claude -p 'Reply with exactly the word OK and nothing else.' | grep -q 'ZQ7CANARY' && echo alive || echo silent` 같은 명령으로 파이프라인에 걸어둔다. 대화형 세션에서는 `/context`를 실행해 CLAUDE.md가 Memory files 아래 나타나는지 확인하면 된다. 화면이 없는 헤드리스 실행에서는 캐너리 검증이 유일한 계기판이다.

윈도우 쪽은 별도로 봐야 한다. 문서는 윈도우에서 심볼릭 링크를 만들려면 관리자 권한이나 개발자 모드가 필요하다고 밝히며 윈도우 사용자에게는 `@AGENTS.md` import 쪽을 권한다. 여기에 더해 `core.symlinks=false`로 체크아웃한 윈도우 저장소에서는 심볼릭 링크가 실제 링크가 아니라 원본 경로 문자열이 그대로 든 평범한 텍스트 파일로 생성된다. Claude Code는 그 텍스트를 지시문 전체로 읽어버린다. 이 동작은 실제로 돌려서 확인한 셀이 아니라 git 동작에 대한 추론으로 적어둔다. import의 4홉 재귀 한계도 이번 실행에서는 건드리지 않았다. 두 경로 모두 실패가 조용하다는 점은 같다. 심볼릭 링크가 깨지면 파일이 없다는 형태로라도 드러나지만 텍스트 파일로 눌러앉은 링크와 게이트에 걸린 import는 둘 다 캐너리를 심어야만 알 수 있다. 온보딩 체크리스트에 한 줄 적어두는 것만으로는 부족한 이유가 여기에 있다.

## 어느 쪽이 맞는 팀인가

CI, 훅, 크론, 서브에이전트처럼 사람이 지켜보지 못하는 경로에서 규칙이 살아 있어야 한다면 이야기가 다르다. 이때는 심볼릭 링크 쪽이 게이트 자체를 만나지 않으므로 그 조합을 쓰되 `core.symlinks`와 윈도우 체크아웃을 온보딩 항목으로 명시해둔다. 무인 경로 예외를 걷어내면 판단은 단순해진다. 리포 안 파일 하나를 여러 도구가 나눠 먹는 모노레포이고 팀에 윈도우 기기가 섞여 있다면 import 쪽이 권한과 체크아웃 변수를 처음부터 지운다. 외부 의존성이 있는 리포도 다르지 않다. 대상 파일을 먼저 리포 안으로 옮기고 상대경로 `@AGENTS.md` 아래에 Claude 전용 규칙을 이어 쓴다. 홈 디렉터리의 개인 규칙을 여러 리포에 재사용하는 경우만 심볼릭 링크 쪽이 남는다.

반대로 안 맞는 조합도 뚜렷하다. `core.symlinks=false`인 윈도우 체크아웃에서 심볼릭 링크를 쓰는 것, 리포 밖을 가리키는 `@` import를 헤드리스 경로에 그대로 올려두는 것은 문서가 이미 안 된다고 못 박아둔 시도다. `/import` 일회성 복사에 장기간 기대는 것, 토큰을 아끼겠다고 import로 파일을 잘게 쪼개는 것도 피해야 한다. 전자는 원본이 움직여도 복사본이 그 자리에 머물고 후자는 가져온 파일이 세션 시작 때 어차피 전부 실려 컨텍스트가 줄지 않는다. 무엇보다 지시문이 실제로 실렸는지 아무도 확인하지 않는 구성은 어느 쪽을 택하든 안 맞는다. 그렇다면 다음으로 확인할 건 하나다. 지금 이 CLAUDE.md는 실제로 실리고 있는가.

그 팀이 앞으로도 계속 대화형으로만 한 사람이 한 기기에서 돌리는 게 확실하다면 import 쪽 권고는 의미가 없다. 승인 한 번짜리 게이트가 그때는 사실상 마찰이 아니기 때문이다. 그 확실함을 보장할 수 있는 팀은 많지 않다.

이번 실행에서 보지 않은 것도 있다. 승인을 한 번 하고 나면 그 상태가 얼마나 오래가는지, 거절한 뒤 되돌릴 방법이 있는지는 공식 문서에도 나오지 않고 이번 스물한 번에도 없다. 다음에 확인해야 할 신호는 그쪽이다.

이 경계가 고정된 것도 아니다. Claude Code CHANGELOG의 2.1.232 항목은 이렇게 적는다.

> Cowork sessions no longer inline external @-imports from user-scope memory files
> — [Claude Code CHANGELOG - 2.1.232](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

Cowork 세션에서 사용자 스코프 메모리 파일의 external import를 더 이상 인라인하지 않도록 범위를 좁혔다는 뜻이다. 같은 릴리스에 심볼릭 링크 선점 거부와 샌드박스 우회 차단도 함께 실렸다. 규약을 파일 한 장으로 묶자는 발상은 문서 정리 문제로 시작했지만 실제로는 누가 그 파일을 신뢰하느냐는 권한 문제로 계속 손질되고 있다. 오늘 게이트 없이 통과하는 심볼릭 링크가 다음 릴리스에서도 그대로 유지되리라는 보장은 이 문서 어디에도 없다.
