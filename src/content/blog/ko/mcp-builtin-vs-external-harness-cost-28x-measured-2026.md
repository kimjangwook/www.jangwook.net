어느 에이전트 팀이 묻는다. MCP를 걷어내면 운영 비용이 줄어드느냐. 나는 MCP와 CLI를 통제 비교한 연구를 열어 읽고, 그 옆에 MCP 도구 정의 페이로드를 직접 재본 측정치를 놓았다. 결론은 분명하다. MCP는 매 회차 상주하는 컨텍스트 무게를 더할 수 있지만, 비용 구조를 정하는 것은 하네스이고, 인터페이스만 갈아서 그 비용을 되찾기는 어렵다.

에이전트 플랫폼을 승인하는 CTO와 그 플랫폼을 운영하는 엔지니어링 리더에게 당장의 결정은 두 개다. 도구를 표준화하기 전에 하네스를 실측한다. 그리고 접근 통제를 하네스 아래, 실제로 집행되는 자리에 내려놓는다.

## 비싼 결정은 대개 도구를 호출하기 전에 끝난다

에이전트 도입에서 반복되는 관리 실패는 모델과 도구 프로토콜과 실행 시스템을 하나의 조달 결정으로 묶는 것이다. 이 셋은 한 층이 아니다.

모델은 토큰을 만든다. CLI나 MCP 같은 인터페이스는 가능한 행동을 표현한다. 하네스는 매 회차에 어떤 지시문, 어떤 도구 스키마, 얼마만큼의 대화 이력, 몇 번의 재시도, 어떤 승인 단계, 어떤 파일 읽기, 어떤 검증 루프가 올라갈지를 정한다. 그래서 그럴듯한 데모를 통제된 운영 시스템으로 만들지, 예측 불가능한 비용 센터로 만들지를 가르는 층이 하네스다.

이 논문이 다룬 것은 고정된 소프트웨어 과제 하나다. 사설 원격 git 저장소에 대한 6개 조작을 하네스 7종과 모델 5종에 걸쳐 돌렸다. 완료 판정은 에이전트가 끝났다고 말한 것이 아니라 저장소 상태를 검사해서 했다. 이 구분이 중요하다. 자기보고를 세는 팀은 납품된 작업을 재고 있는 것이 아니다. 평가 대상인 그 시스템이 스스로 내놓은, 검증되지 않은 진술을 재고 있다.

논문의 중심 결론은 직설적이다.

> "The dominant effect was the scaffolding."
>
> — [The Scaffolding Matters More Than the Interface](https://arxiv.org/abs/2608.08654)

에이전트 작업량이 git, 빌드, 파일시스템, 린터, 패키지 매니저, 이미지 변환처럼 이미 성숙한 CLI 표면 위에 놓인 조직이라면 출발점이 달라진다. MCP 서버 등록부터 시작하지 않는다. 같은 실제 과제, 같은 상태 기반 합격 기준으로 하네스를 두세 종 비교하는 작은 표부터 만든다.

## 하네스 정책은 회차마다 곱해진다

구현은 복잡해도 단위 경제성은 단순하다.

회차당 입력 비용은 시스템 프롬프트, 상주 도구 정의, 누적된 대화 이력, 그리고 하네스가 다시 보내기로 정한 반복 컨텍스트가 만든다. 총비용은 거기에 작업을 완료하고 재시도하고 들여다보고 검증하는 데 든 회차 수를 곱한 값이다.

이 항들을 전부 하네스가 정한다.

- 도구 스키마가 매 회차 상주하는지
- 이력을 통째로 다시 보내는지 압축해 보내는지
- 에이전트가 같은 파일을 다시 읽는지
- 실패 하나가 좁은 수리 루프를 도는지, 넓은 재탐색 루프를 도는지
- 완료를 시스템 상태로 한 번 확인하는지, 모델 출력에서 반복 추정하는지

도구 인터페이스는 이 시스템 안의 표현 하나를 바꾼다. 그 표현을 회차마다 실어 나르는 정책 자체를 정하지는 못한다.

나는 MCP 서버 두 개에 최소한의 JSON-RPC stdio 프로브를 돌렸다. `initialize`, `notifications/initialized`, `tools/list`를 보내고 응답의 `tools` 배열만 최소 직렬화해 바이트를 셌다. 한쪽 서버는 도구 2개를 1,451 바이트로 노출했다. 다른 쪽은 도구 29개를 23,257 바이트로 노출했다. 어느 서버를 등록하느냐만으로 매 회차 상주하는 도구 정의 바이트가 16배 갈린다.

절대 토큰 추정치는 근사값이다. 프로덕션 토크나이저가 아니라 문자수를 4로 나눈 값이다. 바이트 비율은 그 근사에 좌우되지 않는다. 더 중요한 것은 이것이 논문의 7×5 행렬 재현이 아니라는 점이다. 플랫폼 팀이 당장 통제할 수 있는 운영 사실 하나를 떼어낸 것이다. 도구 스키마는 매 요청에 포함되는 순간 추상적 메타데이터가 아니다. 반복 지불되는 입력 재고다.

MCP의 실패가 빈도는 같으면서 금액은 다를 수 있는 이유가 여기 있다. 논문에서 실패 빈도는 두 인터페이스가 같았다. 반복 실행에서도 같았다. 그런데 MCP 런에 쓴 돈의 12.9%가 완료된 작업을 사지 못했고, CLI 런은 2.2%였다. 차이는 시스템이 실패에 도달하기 전까지 이미 쌓아둔 비용이다.

총지출과 성공률만 보여주고 실패에 묶인 지출은 빼놓은 플랫폼 대시보드는 바로 이 패턴을 가린다.

## 28배는 실측된 숫자지만, 인용은 자주 틀린다

논문에서 가장 헤드라인으로 쓰기 좋은 숫자는 5.0배에서 28배까지의 비용 차이다. 이것을 MCP가 CLI보다 28배 비싸다는 근거로 쓰면 안 된다.

그 비교는 MCP를 지원하지 않는 하네스 2종과 지원하는 하네스 5종 사이의 비교이고, CLI 런끼리만 대조했으며, 어디에도 MCP 서버를 붙이지 않은 조건이었다. 인터페이스를 CLI로 고정해도 하네스 선택만으로 비용이 엄청나게 벌어진다는 증거다. MCP를 걷어낼 근거가 아니다.

하네스 쪽에서 더 강한 소견은 270억 파라미터 로컬 모델 결과다. 이 모델은 하네스에 따라 비용이 139배 갈렸고, 그러면서도 모든 하네스에서 과제를 완료했다. 같은 모델, 같은 과제, 완료된 결과, 그런데 실행 경제성은 전혀 다르다.

엄격하게 짝지은 MCP 대 CLI 비율도 13개 있었다. 0.43배에서 29배까지 흩어졌고 양쪽 모두에 이상치가 있었다. 저자들은 인터페이스 비교 자체가 불안정했다고 명시했다. 경영 판단에서 이것을 읽는 올바른 방식은 이렇다. 짝지은 근거가 방향조차 못 내는데 인터페이스 수준의 주장을 투자 메모에 올리지 않는다.

내부 벤치마크마다 들고 가야 할 방법론 경고가 하나 더 있다. 에이전트는 배정된 인터페이스를 자주 무시했다. "MCP 런"이나 "CLI 런"이라는 라벨이 붙은 보고서는 실제 행동을 검증하지 않았다면 아무 의미가 없다. 검증 없이는 사용 가능한 도구, 폴백 동작, 프롬프트 해석, 하네스 정책이 뒤섞인 정체불명의 혼합물을 재는 셈이다.

## 가장 강한 반론은 MCP에 대해 옳고, 다음 행마에 대해 틀렸다

가장 강한 반대는 손대지 않고 그대로 세워둘 만하다.

과제는 git 조작 6개였다. git은 엔지니어링에서 가장 성숙한 CLI 표면 가운데 하나다. 수십 년 쌓인 명령 관례, 조합 가능한 출력, 예측 가능한 종료 코드, 풍부한 문서, 자리 잡은 운영 습관이 있다. 이 부류의 작업을 에이전트가 CLI로 완료할 수 있다는 발견은 MCP에 대한 일반 판정이 아니다. CLI가 이미 유별나게 강한 영역이 만들어낸 결과다.

5.0배에서 28배라는 수치도 MCP 철거 프로그램을 지탱하지 못한다. MCP를 붙인 런과 CLI만 준 런을 비교한 값이 아니기 때문이다. 그 비교에는 MCP 서버가 아예 없었다. 이것을 "MCP가 28배 비싸다는 증명"이라고 부르는 경영 보고 자료는 근거를 잘못 읽었다.

이 반대는 인터페이스 우열에 관한 광범위한 주장 전부에 옳다. 과제 하나가 도구 경제 전체는 아니다. CLI가 완비된 소프트웨어 저장소는 고객 데이터 시스템도, 사유 SaaS 워크플로도, 디자인 플랫폼도, 통제되는 사업 데이터 환경도 아니다. 짝지은 비율의 불안정성이 그 한계를 다시 못 박는다.

그렇다고 반대가 하네스 결과를 지우지는 못한다. 인터페이스 라벨을 걷어낸 뒤에도 하네스 지배 효과는 남는다. 139배는 과제를 고정하고 결과가 완료된 상태에서 나온 하네스 수준의 변동이다. 여기가 실제로 행동을 걸 만한 결정 신호다.

git과 빌드 시스템, 파일시스템 조작, 패키지 관리만 다루는 팀이라면 MCP 없이 시작하는 것이 합리적이다. 쓸 만한 CLI 경로가 이미 있다. 반대로 에이전트가 동의 이력이나 고객 세그먼트, 사내 기록, 사유 SaaS 객체를 조회해야 하는데 쓸 만한 CLI가 없는 팀이라면 MCP가 유일한 경로일 수 있다. 그때 질문은 MCP가 철학적으로 우아한가가 아니다. 스키마가 차지하는 크기와 인가 설계와 실패 비용 프로필이 예산에 잡히고 통제되고 있는가다.

## 프로토콜을 표준화하기 전에 도입 절차를 표준화한다

첫 플랫폼 결정은 도구 카탈로그가 아니라 반복 가능한 평가 절차여야 한다.

하네스 두세 종을 고르고, 같은 대표 과제를 각각에 돌린다. 모델, 합격 기준, 권한, 사용 가능한 데이터를 고정한다. 완료는 저장소 상태, DB 행, 응답 코드처럼 독립적으로 들여다볼 수 있는 상태로 판정한다. 에이전트가 마지막에 쓴 문장을 성공 기준으로 삼지 않는다.

논문은 하네스와 과제, 검증 방법, 전체 데이터셋을 오픈소스로 공개했다. 운영 관점에서 이것이 중요하다. 벤더 벤치마크를 기다릴 이유가 없다. 고정된 과제, 통제된 구성, 상태 검증, 실행 증거 보존이라는 규율만 그대로 가져오면 된다.

그다음, MCP 등록을 통제되는 엔지니어링 변경으로 만든다.

MCP 서버 등록 PR은 `tools/list` 페이로드 크기와 도구 수를 밝히게 한다. 위에 쓴 기본 프로브를 CI가 그대로 돌려 서버 단위와 저장소 단위 페이로드 상한을 집행할 수 있다. 목적은 큰 도구 표면을 일괄 금지하는 것이 아니다. 도구 29개짜리 상주 세트가 왜 모든 에이전트 컨텍스트에 들어가야 하는지, 왜 쪼개거나 범위를 좁히거나 필요할 때만 로드하지 않는지를 담당자가 적어 내게 만드는 것이다.

운영 대시보드에 실패 지출 비율을 넣는다. 성공률만으로는 값싸게 일찍 죽은 실패와 컨텍스트가 커지고 도구 호출과 재시도가 쌓인 뒤의 비싼 실패를 구분하지 못한다. 이것은 직접적인 단위 경제성 지표다. 에이전트 지출 가운데 완료된 작업을 못 산 몫이 얼마인가.

마지막으로, 도구 가용성과 실행 권한을 분리한다. MCP 서버는 유용한 행동을 기술할 수 있다. 그것이 모든 에이전트와 모든 과제, 모든 환경, 위임된 모든 서브에이전트가 그 행동을 해도 된다는 뜻은 아니다.

## 보안 통제는 바뀌도록 설계된 층에 살 수 없다

하네스는 과제 정책, 컨텍스트 정책, 승인 워크플로, 사용자 경험을 두기에 맞는 층이다. 최종 보안 보증을 두기에는 틀린 층이다.

하네스는 설계상 프로그래밍 가능하다. 팀은 도구를 붙이고 프롬프트를 고치고 재시도를 조정하고 새 에이전트를 지원하고 처리량을 올리려고 하네스를 계속 개조한다. 그 유연성은 가치가 있다. 그러나 같은 유연성 때문에 하네스는 민감한 행동이 불가능했음을 증명하는 권위가 될 수 없다.

NVIDIA의 에이전트 스택 정리는 이 함의를 명시한다.

> "This programmability makes the harness a poor place for a security guarantee: a layer designed to be modified cannot reliably enforce controls against its own modification."
>
> — [Where Security Fits in an AI Agent Stack](https://developer.nvidia.com/blog/where-security-fits-in-an-ai-agent-stack)

에이전트가 저장소를 넘어 고객, 회원, 재무, 동의 관련 데이터로 들어갈 때 이 구분이 특히 중요해진다. "제한 필드에 접근하지 말라"는 프롬프트는 행동을 유도할 수 있지만 집행하지는 못한다. 에이전트가 호출을 안 하기로 선택할 수 있는 도구도 통제가 아니다. 집행 지점은 에이전트와 하네스가 넘을 수 없는 상한을 적용하는 런타임이나 인프라 경계에 있어야 한다.

실무로 옮기면, 접근 정책은 자격 증명, 데이터 스코프, 네트워크 경로, 실행 아이덴티티, 런타임 정책에 붙는다. 위임된 에이전트는 오케스트레이터보다 좁은 상한을 가진 자식 런타임을 받는다. 감사 기록은 하네스 설정에 어떤 지시가 적혀 있었는지가 아니라, 어떤 아이덴티티가 어떤 정책 아래 어떤 자원에 접근했는지를 보여야 한다.

이것은 보안 부가 기능이 아니다. 시연할 수 있는 워크플로와 감사를 통과하는 워크플로의 차이다.

## 사업 표면에 CLI가 없는 곳에서 MCP는 여전히 필요하다

성숙한 엔지니어링 워크플로에서 MCP를 걷어내면 움직이는 부품이 줄어든다. 대안 없이 사업 워크플로에서 걷어내면 유용한 자동화로 가는 유일한 길이 사라질 뿐이다.

대부분의 엔터프라이즈 데이터 표면은 사람을 위해 만들어졌다. 애플리케이션과 대시보드, 승인 흐름, 도메인 특화 API가 그렇다. 에이전트가 안전하게 조합할 수 있는 일관된 CLI를 내놓지 않는다. 고객 데이터 조회, 동의 이력 검토, 사내 SaaS 조작, 디자인 시스템 워크플로가 흔히 여기 속한다.

OpenAI의 플랫폼 방향도 그 현실을 반영한다. Codex를 컨텍스트 관리와 도구 사용, 승인 워크플로를 책임지는 재사용 가능한 하네스로 규정하고, MCP 도구는 애플리케이션이 소유하게 둔다.

> "Codex can then use the application's MCP tools to fetch current data before recommending."
>
> — [Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)

이런 팀에게 MCP는 비용 최적화 대상이 아니다. 통합 경로다. 규율 있는 결정은 그 경로를 받아들이되 비용과 위험을 함께 통제한다.

- 도구 정의를 필요한 최소 운영 표면으로 좁힌다
- 광범위한 도구 묶음을 기본값으로 등록하지 않는다
- 프로덕션 롤아웃 전에 상주 스키마 페이로드를 실측한다
- 결과를 권위 있는 시스템 상태에 대조해 검증한다
- 실패 지출을 완료 작업 지출과 따로 추적한다
- 데이터 접근과 행동 한도를 런타임과 인프라 층에서 집행한다

이것은 "어디나 MCP"와도, "어디에도 MCP 없음"과도 실질적으로 다른 전략이다. 사업 표면에서 출발한 뒤 아키텍처 규율을 적용한다.

## CEO와 CTO가 다음 검토 주기에 바꿀 것

첫째, 운영 안건에서 하네스 선택을 모델 재협상보다 앞에 놓는다. 모델 계약도 중요하지만, 실측된 139배 하네스 변동은 경영 검토에서 모델 선택만이 비용 레버가 될 수 없는 이유를 보여준다. 모델이 컨텍스트를 얼마나 자주 받고 얼마나 많이 받는지, 검증 전에 비싼 회차를 몇 번 도는지는 실행 층이 정한다.

둘째, 실패 지출을 에이전트 파일럿의 승인 지표로 만든다. 완료율은 높다고 보고하면서 예산의 큰 몫을 실패한 런에 조용히 태우는 파일럿은 확장할 준비가 안 된 것이다. 완료율은 시스템이 때때로 작동하는지에 답한다. 실패 지출은 그 운영 모델이 경제적으로 버티는지에 답한다.

셋째, MCP 등록을 용량 계획으로 취급한다. 서버의 도구 정의는 서비스 의존성이 지연과 신뢰성 예산을 먹는 것과 똑같이 컨텍스트 용량을 먹는다. 올바른 거버넌스 산출물은 실측 페이로드와 소유자, 정당화 근거, 접근 범위, 롤백 조건이 적힌 PR이다.

넷째, 편집 가능한 하네스 지시문이 아니라 런타임 경계의 집행에 예산을 쓴다. 여기서 컴플라이언스 투자가 선의로 쓰인 프롬프트 문장 모음이 아니라 감사 가능한 운영 역량이 된다.

내 판단은 단순하다. CLI가 성숙한 엔지니어링 작업에서는 같은 과제로 하네스를 비교해 추가 표면이 정당하다고 증명될 때까지 MCP 서버를 하나도 등록하지 않는다. CLI가 없는 사업 표면에서는 MCP를 쓰되, 계량되고 런타임이 통제하는 통합 층으로 관리한다.

이 판단을 바꿀 조건도 적어둔다. CLI가 없는 엔터프라이즈 과제를 다룬 통제된 상태 검증 벤치마크가, 하네스 정책과 도구 페이로드와 런타임 권한을 고정한 뒤에도 MCP를 붙인 구성이 완료 작업 비용을 일관되게 낮춘다고 보여준다면 나는 판단을 바꾼다.
