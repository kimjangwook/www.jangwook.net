可迁移的编码智能体会话，究竟能实质削减厂商锁定，还是只是让将来那次搬家看起来比实际轻松？我冻结了一个真实的 Claude Code 会话，逐条检查，再用 session-migrate 0.8.0 把它转成七种目标格式。有用的对话和工具上下文走得出乎意料地顺，而真正让智能体工作在组织里变得安全的那套管控，一样都没跟过去。

这道分界很要紧。CTO 该优化的是审批与审计的可迁移性，不是某位工程师本地记录的可迁移性。

## 运营上的难题，不在聊天记录存放在哪

在大规模重构项目和数据平台的实际推进中，工程负责人迟早会被问到同一句话：三个月后，我们从哪里能看到这个智能体为什么做了那次改动？

危险的答案往往是「大概在某个工程师本地的会话文件里」。一个人把上下文留在 JSONL 里，另一个人把片段贴进了 PR 描述，第三个人早就清空了目录。私下试验这样没问题。可一旦改动碰到身份认证、支付、会员数据或生产环境权限，这就是运营缺陷。

还有一条风险朝反方向走。会话文件里可能夹着生产日志片段、schema 细节、附件产物，有时甚至是真实数据的样本。一条把这种会话转成另一家厂商原生格式的命令，就不只是便利功能。它开出了又一条数据外流的通道。

所以我不把智能体会话的可移植性当成单纯的开发效率话题。它是一个披着 CLI 功能外衣的数据治理问题。

Slack Code 走的方向和会话迁移正好相反，落点却是同一条架构结论。按 Slack 的说法，在复杂项目里 @ 一下编码智能体，就会拉起一个专属频道，召集该到场的人，把代码差分、计划文档、可直接打开的 HTML 预览备齐；活干完，频道归档，作为可检索的记录留在 Slack 上。工作的持久记录，就此从单台工作站挪到了共享的运营台面。

> Slack Code は Slack 既存の権限と管理者コントロールを継承するため、IT 部門が新たな設定や監査を行う必要はありません。重要な変更はチャンネル内でそのまま担当者による迅速な承認フローに回すことができ、レビューの安心感を保ちながら自動化のスピードを実現します。
> — [Slack Code: チームと AI エージェントが共に作り上げる場所](https://slack.com/intl/ja-jp/blog/news/slack-code-channels-for-agents)

产品细节不重要，机制才重要：Slack Code 继承的是一套已经存在的权限与管理平面，而不是要求 IT 在每一个新的智能体工作流内部再造一套。

## 迁移实测到底保住了什么

我在 macOS 上用 Python 3.12 虚拟环境装了 session-migrate 0.8.0，尽管 README 写的支持范围是 Python 3.11+ 与 Linux。装得上，也跑得起来。这不改变官方声明的支持边界，但足够支撑一次受控的格式转换测试。

源是一个冻结的 Claude Code 会话：341,646 字节，90 条记录，含 20 个 tool-use 块、20 个 tool-result 块、11 个 thinking 块。冻结这一步不能省。第一次尝试时会话文件还在持续增长，结果每个目标格式都在跟一份不同的源作比较。

随后我把同一份冻结会话分别转入 Codex、Pi、GitHub Copilot CLI、Qwen Code、Kimi Code、Muse Code 和 Mistral Vibe，每个目标的 home 目录都隔离在 `/tmp` 下。产出的记录数落在 33 到 50 之间。这个跨度并不说明信息保全程度差别很大，只是各目标格式把等价内容切成了不同的记录单位。

真正有意思的是丢失清单。七个目标的丢弃总数密集地落在 54 到 57 之间，而丢弃的 thinking 数固定为 9。反复被舍掉的，是源侧的元数据记录、工具引用记录，以及私有思考。Codex 额外丢了一条会话标题；Vibe 则保住了另外六个目标都丢掉的两条工具引用记录。

这个规律比任何笼统的「兼容性良好」都更有用。换目标，几乎不改变损失。决定什么能进入中间模型的，是源会话本身的事件词汇表。

项目对转换路径的描述是这样的：

> native session → validated event timeline → native target → resume
> — [session-migrate — Migrate your sessions to any harness](https://github.com/xhluca/session-migrate)

那条中间时间线被刻意做小了：有序的对话事件可以穿过去，客户端本地的配置穿不过去。源会话原封不动，所有省略与变形都记进一份不含内容的迁移清单。

## 锁定的边界在策略平面，不在对话记录

这个迁移工具支持 12 种框架格式，给出 144 条有序路径，其中包含同格式之间的可移植重写。用户消息和助手消息在每条路径上都按顺序保留。这是实打实的可移植性，不是把纯文本导出包装成迁移。

> Every listed format can be a source or target: 144 ordered routes, including same-format portable rewrites.
> — [session-migrate README — Compatibility](https://raw.githubusercontent.com/xhluca/session-migrate/main/README.md)

而同一份兼容性文档，写下了那条决定性的限制：

> Auth, hooks, policies, MCP, and runtime config | No | These remain with the source client
> — [session-migrate — Migrate your sessions to any harness](https://github.com/xhluca/session-migrate)

这是管理层在与厂商谈判时该拿出来用的架构事实。团队可以带走工作叙事、工具调用记录和大部分可用上下文。但仅靠搬动一个会话文件，带不走执行环境。

认证绑在客户端。钩子绑在客户端。策略配置、MCP 连接、运行时配置，同样绑在客户端。它们缺席，并不是因为目标格式选错了；它们从一开始就不属于那条可传输的事件时间线。

Antigravity 与 Cursor 的转换失败，把同一条边界又画了一遍。两个适配器都当即要求各自的原生可执行文件 `agy` 与 `cursor-agent`，而机器上没装。这类适配器不是独立的文件翻译器。它们必须挂在客户端上，因为有些原生状态根本无法只靠一份导出的会话重建出来。

对单个开发者，这种缺失也许可以接受。对一个组织，它意味着真正的切换成本，是在新框架上重建权限映射、钩子、策略和已批准的工具连通性的那些工时。

## 最有力的反方意见，在一个窄但重要的区间里成立

最强的反驳是：会话上下文才是切换的真实成本。这个反驳值得比它通常得到的更多重视。

对一个带着长周期实现会话、在工具之间来回换的开发者来说，重建上下文很贵。测试也支持这一点：源会话的有序对话、工具调用历史、工具结果历史，并没有被简单丢弃。迁移工具给了一条务实的路径，让工作叙事得以延续，而不是从空提示框重新开始。

对不受监管约束、频繁更换框架、也没有集中留存审批记录需求的个人或小团队，这一点尤其值钱。在那种环境里，144 条迁移路径不是营销数字，它确实能降低试验摩擦，保住积累下来的上下文。

「策略迁移不了，所以会话迁移没用」是错的。会话依然是有价值的连续性资产。

出了那个区间，我的判断不变。迁移后的会话在恢复时，没有原客户端的认证、钩子、策略、MCP 连接与运行时配置。对要接受审计的系统，安全管控不是围绕工作的可选上下文。它本身就是工作的一部分。

牵涉的人、仓库、环境和合规约束越多，省下来的会话上下文在这笔账里占的比重就越小。重建策略管控、验证权限、证明审批路径、审查新出现的数据外流通道，会把迁移预算吃掉。

## 让会话可丢弃，让治理耐用

我推荐的运营模型有三道闸门。

第一，明确宣布会话是缓存，不是记录系统。决策、证据、回滚步骤必须存在于 PR 正文、已批准的工作频道，或两者兼有。给评审清单加一行：这个判断的依据，在智能体会话之外能拿到吗？

听着是小事，但它改变行为。它挡住了团队仅仅因为一段本地记录对话详尽，就把它当作审计凭证的倾向。换台笔记本、有人离职、本地智能体目录一次例行清理，这段记录就没了。

第二，受审计的仓库必须走导出评审。确有迁移必要时，先把 dry-run 生成的迁移清单附到工单上，再执行导出。一份只报省略类别和数量、不含内容的清单，比一整份原始会话导出更适合拿去评审。评审者能判断什么要出去、什么会丢，同时不必把底层内容再扩散给一批人。

第三，审批、权限和归档只选一个执行点：频道，或者 CI。默认不要两个都要，更不要在每个智能体 CLI 内部各搞一套执行模型。已经有扎实的 code owner 与 CI 审批管控的团队，不该仅仅因为某个智能体产品提供了聊天审批，就再并上一条审批线。两个审批平面，会让「哪个决定算数」变得含糊。

新人入职时可以把话说直白：CLI 你自己挑顺手的，但审批在这里发生，记录在这里留存。

本地工具选择权因此得以保留，同时不让工具选择把治理切碎。

## Slack Code 是策略平面产品，不只是智能体集成

Slack Code 面向已接入 Claude、Devin、GitHub Copilot 和 Vercel 的团队开放，ChatGPT 则标注为近日支持。Slack Code 的产品承诺，不是让所有智能体思路一致、状态存放方式一致。它承诺的是：工作可以从一个共享频道开始，并继承组织现有的 Slack 管控。

官方那句「超过 70% 的代码频道能在一天内从构想走到 PR 合并」，只能当作厂商参考值来看。Slack 没有公开方法论、样本范围和统计周期。单凭它撑不起一份商业论证。

不过这套工作流设计在战略上是站得住的。产品、设计、工程和运营能看到同一个需求，评审同一批产物，看到最终决定是什么，而不必每个人都去拿某位开发者本地框架的访问权。哪怕后端换了智能体，频道仍能作为人类审批边界的归档留下来。

Slack 也把「智能体推理过程的可视化」写成了将来要做的事，而不是已经发布的能力。这与 session-migrate 刻意不搬运私有或带签名的思考痕迹，恰好是同一件事的两面。智能体工作中最需要解释的那部分，在结构上恰恰最不可移植，因为它绑定在模型提供方身上。

于是真正可审计的范围更窄，也更可靠：请求了什么、改了什么、评审了哪些证据、谁批的。

## CEO 与 CTO 该往厂商切换模型里放什么

不要用「会话历史能不能导出」来估算智能体厂商的切换成本。那会给出一个骗人的低数字。

正确的模型问的是：组织的执行平面，是否存在于框架之外。

- 换掉一个 CLI，审批规则还活着吗？
- 权限与 MCP 连通性，能从集中管理的配置重建出来吗？
- 审计人员不去翻某位开发者的本地会话，能找到理由和审批记录吗？
- 团队能否从单一管理界面撤销权限、叫停某条工作流？
- 一次会话搬迁带走了哪些数据，组织有能力评估吗？

答案若是肯定，智能体框架就更接近一件可替换的执行工具。这直接改善谈判筹码。采购可以在价格、质量和集成度上向厂商施压，因为组织不必每换一次模型或 CLI 就重建一遍治理模型。

答案若是否定，厂商掌握的就不止一个界面。它掌握了内嵌的审批逻辑、权限模式和运营记忆。它的报价因此很难被约束，因为替换制造的是组织风险，不只是开发者的不便。

这也顺带指明了智能体用量增长时该往哪里投。多买席位放大的是活动量。提升审计平面的吞吐与清晰度，放大的是组织本身。后者才是让智能体落地不至于沦为一堆没人能审的本地自动化的那道防线。

## 这套建议不适用的地方

以 Slack 为中心的执行模型，不适合协作标准不是 Slack 的团队。原则依然成立，但策略平面必须落在这个组织真正在用的共享工作流系统里。

它同样不适合已经靠 CI 和 code owner 把审批执行到位的团队。把频道加成第二个审批权威，反而会因为证据链分叉而让系统更糟。

被禁止在第三方 SaaS 留存对话日志的组织，需要另一套归档设计。每天只有几个智能体请求的团队，会发现自动建出来的频道带来的归档开销大于运营价值。而把私有推理痕迹当作审计证据的团队应当明白：可移植会话和频道归档，目前都解决不了这个要求。

我的立场很清楚：把会话迁移当个人的连续性工具用，别把它抬成团队的治理标准。审批、审计、归档、撤销，放进一个与工具无关的执行平面。只有当会话格式开始在对话之外携带可移植、可集中校验的策略与身份状态时，我才会改变这个判断。
