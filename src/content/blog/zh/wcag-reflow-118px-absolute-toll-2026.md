# 400% 缩放下的 Reflow：82 像素到底去了哪

## 问题是量出来的，不是猜出来的

WCAG 成功标准 1.4.10（Reflow，重排）给了一个硬性下限：内容必须能在不丢失信息或功能、且不需要二维滚动的前提下呈现——纵向滚动内容对应 320 CSS 像素宽度，横向滚动内容对应 256 CSS 像素高度。理解文档对数学关系说得非常明确：400% 作用于**维度**而不是**面积**——默认视口宽度的四倍、默认视口高度的四倍，两个方向各自独立计算。

我们做了一次视口预算审计：4 个页面模板（post、post2、index、home），4 种视口高度（844、400、256、200），宽度固定 320，分别测页面顶部和滚动中途两种状态。头条数字只有一个：在 200 像素高的视口里，真正到达正文内容的纵向空间只有 **118 像素**。剩下的部分在第一段文字出现之前就被吃掉了。

这不是渲染 bug。这是一系列各自都说得过去的设计决策叠加的结果，和在分布式系统里不设上限的重试叠加是同一种病：没有单个组件是错的，但总量把预算耗光了。

## 类比：视口是集群，固定元素是常驻守护进程

把视口想成一个限容量的集群。每个 fixed / sticky 元素都是一个常驻守护进程，启动时就划走自己那块内存——头部导航划一块，底部广告容器划一块，回到顶部按钮再来一块。每个进程都能论证自己必不可少。

问题在于，这个集群**不做弹性伸缩**。视口缩小时，消费者不跟着缩小：头部永远是 82 像素，广告容器永远占 90 像素。在 844 像素高的手机视口上，这些预留是噪音；在 200 像素上，它们占了 86%。

这是经典的 noisy-neighbor 问题，只不过邻居是你自己的组件，而调度器是 CSS 布局引擎。值得注意的是，这个调度器**不做准入控制**：它会心安理得地把视口超售到什么都看不见为止，并且不报任何错。你的监控也不会报警——因为从布局引擎的角度看，一切正常。

## 细节

### 先说好消息：横向测试全过

8 行测试数据（4 个模板 × h=844 和 h=200 两种高度），1.4.10 的横向判定 8/8 全部通过：

| template | h | clientWidth | scrollWidth | h_overflow_px | reflow_pass |
|----------|-----|-------------|-------------|---------------|-------------|
| post | 844 | 320 | 320 | 0 | true |
| post | 200 | 320 | 320 | 0 | true |
| post2 | 844 | 320 | 320 | 0 | true |
| post2 | 200 | 320 | 320 | 0 | true |
| index | 844 | 320 | 320 | 0 | true |
| index | 200 | 320 | 320 | 0 | true |
| home | 844 | 320 | 320 | 0 | true |
| home | 200 | 320 | 320 | 0 | true |

每一行都是 `clientWidth 320 = scrollWidth 320`，横向零溢出。布局在横向维度上重排正确。如果审计到这里就停——很多团队确实停在这里——你会得出站点符合 Reflow 要求的结论。

### 垂直预算讲了另一个故事

钱是在纵向维度上花掉的。h=200、页面顶部状态，6/6 次复现（与 2026-08-09 的自审结果一致）：

```
usable_px 118 (h=200)
```

200 像素的视口，交付给内容的只有 118。那 82 像素的缺口是一个**绝对常量**，不是按比例的。四种视口高度下，损失完全相同：

```
844 − 762 = 82
400 − 318 = 82
256 − 174 = 82
200 − 118 = 82
```

这是整个数据集里最重要的一个性质，而且如果你用百分比思考，它是反直觉的。百分比心智模型会说：固定头部"占视口的 10%"。错。它占 82 像素，句号。视口高度是那个会变的分母，税额不变。它表现得像固定预留——一个静态分配的分片——而不是随负载伸缩的流量。

### 归因：82 像素的债主是谁

对每个元素在每个视口高度下记录位置和尺寸，归因结果很干净：top 状态的 82 像素损失属于**static 头部块**，不属于任何 fixed / sticky 外壳。头部在所有页面、所有高度下都是 82 像素，而它的定位方式会翻转：h=844 时是 `sticky`，h=200 时是 `static`——6/6 复现。

这个翻转本身就值得琢磨。视口塌缩时，头部从 sticky 退化成 static，听起来很优雅——sticky 层让位了。但布局成本一分没变。头部不管粘不粘，都占着同样的 82 像素。**退化的是行为，没退化的是预算。**

滚动中途状态出现了第二个消费者。滚动后损失变成 90 像素，归因把它锁定到单一元素：一个固定高度的底部广告容器（`#fixed_container_bottom`），不管视口多高都保持 400px 的高度：

```
#fixed_container_bottom removed: 200 (Δ +90)
ALL fixed/sticky removed:        200 (Δ +90)
individual deltas sum = ALL sum
```

可加性是精确的：只移除广告容器就能拿回全部 90 像素，移除所有 fixed / sticky 拿回的也是 90——没有重叠，没有隐藏的交互成本。用分布式系统的话说，这是一种令人愉快的串行失败模式：每个像素有且只有一个所有者。没有争用，没有重复计数，没有元素重叠产生的涌现成本。这让修复变得可执行：你可以按 delta 排序消费者，逐个修。

### 百分比陷阱，用数字说话

同一个 90 像素的消费者，看起来像两个完全不同的问题：

| viewport | state | 广告容器损失 | 占视口比例 |
|----------|-------|--------------|------------|
| h=844 | mid | 90px | 10.7% |
| h=200 | top | — | 41.0% |
| h=200 | mid | 90px | 45.0% |

在 844 像素的手机视口上，底部固定广告吃掉 10.7% 的屏幕，是大家都熟悉的、可以说是可接受的权衡——做广告的站点都这么干。在 h=200 的滚动中途，同一个容器占掉 **45.0%**。同一个元素，同样的 90 像素，报告哪个数字，感知严重程度差出四五倍。

如果你的无障碍看板用视口百分比来表达固定元素成本，它会在最坏的情况下系统性低估。失败恰恰集中在百分比看起来最小、绝对伤害最大的那一端。主指标报绝对像素；百分比只用于针对特定目标视口做优先级排序。

### 一个零成本的元素

最后一个反直觉的数据点。一个 fixed 定位的回到顶部按钮（h=48，mid 状态可见），**垂直预算成本是零**：

```
#back-to-top removed: 110 (Δ 0)
```

移除它，h=200 mid 状态下的可用空间从 110 到 110，一像素都没多。按钮浮在内容之上，不预留任何布局空间。82 像素的头部和 90 像素的广告容器是**占空间**的；按钮只是遮挡它不申领的像素。

"占空间的固定元素"和"遮挡空间的固定元素"——这才是问题的真正轴线，而且它和 W3C 自己的指导对得上。C34（延迟渲染非关键或隐藏内容）指出："sticky 区域在滚动时始终留在视口内，而其他内容会从它下面消失。" 1.4.10 的理解文档则直接警告：sticky 或 fixed 内容"可能对从 Reflow 中受益的人群造成严重问题——除了遮挡键盘焦点之外，这类内容还可能让阅读变得困难甚至不可能"。这条标准管的不只是两个方向出现滚动条，而是**外壳吃掉之后还剩不剩一块可用的阅读面**。

而在 h=200 mid 下把所有外壳全部移除，你正好拿回全部 90 像素——fixed 元素合计就是 mid 状态的整个缺口。

## 所以呢

如果你的前端要过 1.4.10，三件事会改变。

**第一，纵向也要审计，别只测横向。**横向 8/8 通过只说明你的栅格和媒体查询没问题，对 256 像素高的视口还剩不剩一段话的空间只字未提。在标准隐含的高度（400% 缩放对应的高度等价 256）加上 200 这样的压力点测 `usable_px`。一个页面可以完全通过横向测试的字面要求，同时在 h=200 下只给正文留 118 像素——技术上没有二维滚动，实际上没法读，而且正落在理解文档对 sticky 和 fixed 内容警示的那个区间里。

**第二，建一个逐元素的 delta 台账，而不是组件清单。**我们实测到的可加性——每个元素的移除 delta 精确加总等于全部移除的 delta——意味着你可以产出一张按像素成本排序的表：头部，82，static/sticky；底部广告容器，90，fixed，与视口高度无关；回到顶部按钮，0，fixed，不占流。把这个台账当成布局预算的 flame graph 来看。W3C 自己的技巧 C34 给了你修复词汇表：延迟渲染非关键内容，别让它扣住视口。广告容器就是教科书级的候选——在 h=200 mid 下花掉 45% 视口的 90 像素，不是"能不能延迟渲染"的问题，它就是 bug 本身。

**第三，砍掉百分比报表。**82 像素的头部损失从 844 到 200 一路不变。任何除以视口高度的指标，都会让同一个组件在手机上看起来比在 200 像素压力视口上"便宜四倍"，而实际伤害集中在小的一端。固定预留才是失败模式，绝对像素才是诚实的单位。还要注意，"固定高度"的消费者是最坏的一类：`#fixed_container_bottom` 不管视口多高都撑着 400px，意味着它完全不退化。如果某个组件必须 fixed，让它的预留随视口缩小，或者干脆把它移出文档流——回到顶部按钮证明了零成本 fixed 元素是做得到的。

归根结底，Reflow 合规是一个容量规划问题。视口是你的集群，fixed 和 sticky 元素是常驻守护进程。844 像素时集群有富余，大家相安无事。256 及以下，守护进程赢，用户输。标准的 320×256 下限就是你的 SLO，逐元素的像素台账就是你守住它的手段。
