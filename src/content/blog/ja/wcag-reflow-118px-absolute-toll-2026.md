# 320px 幅で本文に届くのは 118px。WCAG 1.4.10 の縦方向予算を実測する

障害対応で一番厄介なのは、単体ではどれも正常に見えるコンポーネントが、合算したときだけ予算を食い潰すケースだ。リソースの上限は決まっているのに、各消費者は自分の確保分を減らさない。私たちのサイトで幅 320px のビューポート監査を走らせたところ、ビューポート高さ 200px のとき本文に届く縦方向ピクセルは 118px だった。残りの 82px はどこへ消えたのか。誰が持っていったのか。この二つの問いを、実測値で追う。

## 何が起きているか

WCAG 2.2 の達成基準 1.4.10 Reflow は、縦スクロールするコンテンツについて「幅が 320 CSS ピクセルに相当する幅で、情報や機能を失わず、二次元スクロールを要さずに提示できる」ことを求める。判定に使われる 400% ズームの考え方は、Understanding 文書が明確に注記している。400% は面積ではなく寸法に掛かり、既定のビューポート幅の 4 倍と高さの 4 倍をそれぞれ独立に意味する。つまり判定環境の目安は幅 320px、高さは 256px 相当になる。

監査は、post、post2、index、home の 4 テンプレートについて、ビューポート高さ 844 / 400 / 256 / 200 の 4 種類、幅は 320 に固定し、ページ先頭状態とスクロール途中状態の二つを測った。手順は単純で、各状態でヘッダーや fixed 要素の位置とサイズを要素単位で記録し、本文に届く縦方向の実効ピクセル usable_px を算出した。この一連は 6 回中 6 回同じ値で再現し、2026-08-09 の自己監査とも一致した。

## ビューポートは上限付きのリソースである

ここで現場の運用に置き換えて考える。ビューポートは 1 秒あたり 200 リクエストというレート制限つきの共有資源だ。ページ上の fixed 要素や sticky 要素は、同じ枠から割り当てを引いていくバックグラウンドジョブである。ヘッダーは自分を不可欠だと言い、下部の広告コンテナもそう言い、back-to-top ボタンもそう言う。

通常の共有インフラと違うのは、この枠が弾力的に伸びない点だ。ビューポートが縮んでも、消費者側の確保量は減らない。ヘッダーは 82px のまま、広告コンテナは 90px のまま居座る。高さ 844px のときは両者ともノイズで済むが、200px になると合算で予算の過半を超える。しかも CSS のレイアウトエンジンはアドミッションコントロールを行わない。オーバーサブスクライブして実質的に何も見えない状態になっても、エラーを一つも返さない。障害検知がユーザーの「読めない」という声だけ、という構図は、容量計画を怠ったシステムと同じである。

## 詳細

### 横方向の判定は 8 件中 8 件通過する

まず良いニュースから。4 テンプレート × 2 高さの 8 行すべてで、1.4.10 の横方向判定は通過した。

| テンプレート | h | clientWidth | scrollWidth | h_overflow_px | reflow_pass |
|---|---|---|---|---|---|
| post | 844 | 320 | 320 | 0 | true |
| post | 200 | 320 | 320 | 0 | true |
| post2 | 844 | 320 | 320 | 0 | true |
| post2 | 200 | 320 | 320 | 0 | true |
| index | 844 | 320 | 320 | 0 | true |
| index | 200 | 320 | 320 | 0 | true |
| home | 844 | 320 | 320 | 0 | true |
| home | 200 | 320 | 320 | 0 | true |

clientWidth 320 = scrollWidth 320、横方向のはみ出しは全行ゼロ。グリッドとメディアクエリの設計は横方向については正しく機能している。監査をここで止めると、多くのチームがそうするように「リフロー適合」という結論になる。私たちも最初の監査では横方向だけを見ていた。

### 縦方向の 82px は比例ではなく定数

縦方向の実測はこうなる。高さ 200px、ページ先頭状態、6 回中 6 回の再現値は次の一行だ。

```
usable_px 118 (h=200)
```

ビューポート 200px のうち本文に届くのは 118px。差分の 82px が最初の段落に届く前に消えている。この 82px の性質を決めるのは、次の等式である。

```
844 − 762 = 82
400 − 318 = 82
256 − 174 = 82
200 − 118 = 82
```

4 つの高さすべてで損失が同じ 82px、つまり絶対値として一定である。パーセントの感覚で固定ヘッダーを「ビューポートの 10% ぐらいのコスト」と捉えると、ここで外す。コストは 82px であり、分母のビューポート高さが変わっても税金は変わらない。負荷比例のトラフィックではなく、静的に確保されたリソース割り当てと同じ挙動だ。これがこのデータセットで一番重要な性質である。

### 82px の帰属先と、加算が破綻しないこと

要素単位の計測で帰属は綺麗に出た。先頭状態の 82px は静的ヘッダーブロックの持ち分であり、fixed や sticky のクロームではない。header.h は全ページ・全高さで 82px に固定され、配置モードは h=844 で sticky、h=200 で static と切り替わる。こちらも 6 回中 6 回の再現である。

この切り替え自体が示唆的だ。ビューポートが潰れるとヘッダーが sticky から static に degradation する。振る舞いとしては、sticky 層が身を引く優れた挙動に見える。だがレイアウトコストは 1px も変わっていない。stick するかどうかに関係なく、ヘッダーは 82px を占有し続ける。振る舞いを劣化させても、予算はそのままだ。

スクロール途中状態では第二の消費者が現れる。こちらの損失は 90px で、帰属は単一要素に収束する。ビューポートの高さに関係なく 400px の高さを維持し続ける下部広告コンテナ `#fixed_container_bottom` である。

```
#fixed_container_bottom のみ除去: usable_px 200 (Δ +90)
fixed/sticky をすべて除去:        usable_px 200 (Δ +90)
個別 Δ の合計 = ALL 除去 Δ
```

注目すべきは加算が破綻していないことだ。広告コンテナだけ除去すれば 90px が全額回復し、全部除去しても回復は同じ 90px。要素の重なりによる二重計上も、相互作用による隠れコストもない。分散システムの用語で言えば、直列に失敗する好都合な障害様式である。ピクセルごとに所有者が一人しかいないため、Δ の大きい順にランク付けして順番に直せる。

### 同じ 90px が 10.7% にも 45.0% にも見える問題

同じ 90px の消費者が、報告の仕方によってまったく別の深刻度を持つ。

| ビューポート | 状態 | 広告コンテナの損失 | ビューポートに占める割合 |
|---|---|---|---|
| h=844 | mid | 90px | 10.7% |
| h=200 | top | (該当なし) | 41.0% |
| h=200 | mid | 90px | 45.0% |

スマートフォン相当の 844px なら、下部の固定広告が画面の 10.7% を占めるのは広告収入で運営するサイトなら誰もが受けている馴染みのあるトレードオフだ。同じ要素、同じ 90px が、h=200 のスクロール途中ではビューポートの 45.0% を占める。アクセシビリティのダッシュボードが fixed 要素のコストをビューポート比で表現しているなら、最悪ケースを体系的に過小報告する。割合が最も小さく見える領域に、絶対的な被害が集中しているからだ。

### コストゼロの fixed 要素が存在する

直感に反するデータポイントがもう一つある。fixed 配置の back-to-top ボタン(高さ 48、mid 状態で表示)の縦方向予算コストはゼロだった。

```
#back-to-top 除去: usable_px 110 (Δ 0)
```

除去しても usable_px は 110 のまま動かない。ボタンは fixed でコンテンツの上に浮いており、レイアウト空間を確保しない。82px のヘッダーと 90px の広告コンテナはフロー内で空間を予約するか、ビューポートの一定の切り取りを保持する。ボタンは、主張していないピクセルを覆い隠しているだけだ。

空間を予約する fixed 要素と、覆い隠すだけの fixed 要素、という区別が問題の本当の軸で、W3C 自身の文書と接続する。Techniques の C34 は「sticky 領域はスクロール中もビューポートに常に表示され続け、他のコンテンツはその下に隠れていく」ことを指摘する。1.4.10 の Understanding 文書は、sticky や fixed のコンテンツが「キーボードフォーカスを遮るほか、コンテンツの読書を困難にし、不可能にすらしうる」として、リフローの恩恵を受ける人々にとって重大な問題になりうると警告する。基準の本質は二次元スクロールバーの出現の有無だけではなく、読書面として使える領域がクロームを食われた後も残るか、である。実際、h=200 の mid 状態でクロームを全除去すると 90px が全額回復する。fixed 要素群は、その状態の差分の全体だった。

## それが何を変えるか

1.4.10 への適合を担うフロントエンドを持つなら、実務は三つ変わる。

**縦方向も監査する。** 横判定の 8/8 通過は、グリッドとメディアクエリが機能していることしか言わない。高さ 256px のビューポートに段落が載る余地があるかは別の計測で、判定環境の高さ相当(256)に加え、200 といったストレス点での usable_px を測る価値がある。横方向の文字面は通過しながら、h=200 で本文が 118px しか届かないページは、二次元スクロールがないという定義上は適合でも、Understanding 文書が fixed 要素の領域として警告する事態のままだ。

**コンポーネント一覧ではなく、要素別 Δ 台帳を作る。** 今回の加算性が示すとおり、除去 Δ は合計が一致するため、ピクセルコストのランク付き表を作れる。ヘッダー 82(static/sticky)、下部広告コンテナ 90(fixed、高さ非依存)、back-to-top 0(fixed、非予約)。これをレイアウト予算のフレームグラフとして扱う。直しの語彙は C34 が与えている。クリティカルでないコンテンツの描画を先送りし、ビューポートを人質に取らせないことだ。h=200 の mid でビューポートの 45.0% を食む 90px は、先送りではなく、それ自体がバグである。

**割合ベースの報告をやめる。** 82px の損失は 844 から 200 まで不変だ。ビューポート高さで割る指標は、同じコンポーネントをスマートフォンでは 4 倍安く見せる。実際の被害が小さい側に集中しているのに、だ。誠実な単位は絶対ピクセルで、割合は特定のターゲットビューポートに対する優先順位付けにだけ派生させる。もう一つ、最悪のクラスは「固定高さ」の消費者である。`#fixed_container_bottom` はビューポートに関係なく 400px の高さを保持し、まったく劣化しない。fixed にするなら確保分をビューポートとともに縮めるか、フローから外す。back-to-top が示すように、コストゼロの fixed は作れる。

結局、リフロー適合は容量計画の問題だ。ビューポートはクラスタであり、fixed 要素は常駐デーモンである。844px ならクラスタに余剰があり、誰もが共存できる。256px 以下ではデーモンが勝ち、ユーザーが負ける。基準が示す 320 × 256 の下限が SLO で、要素別ピクセル台帳がそれを維持する手段だ。冒頭の問い、消えた 82px の行き先には一つの答えがついた。ただし h=200 でヘッダーが sticky から static へ切り替わる条件そのものが、ブラウザのどの挙動で決まるのかについては、今回の計測では突き止められていない。次のプローブで確認したい。
