AGENTS.md を Claude Code に接続する方法として、@import、シンボリックリンク、ファイルコピーの三つが公式文書に並列で案内されている。この三つは実質的に同等なのか、それともどこかにコスト差があるのか。この一点を確かめるために、ツールと MCP サーバーを全部切って、モデルが自力でファイルを開けない環境で六セル十八ランの実測を回した。結果は明快だった。2,920 トークンの文書に対して、三つの接続方式の差は 116 トークン。一方で、CLAUDE.md 内にコードフェンスで囲まれた @AGENTS.md は、唯一の import 形式セルで、文書がロードされなかった。

もし今、チームの CLAUDE.md にコードフェンスの中で @AGENTS.md に触れている行があれば、その import は死んでいる。エラーは出ない。トークンスパイクも起きない。ただ、新しいセッションのたびに、あなたが書いた 2,920 トークンのコンテキストが最初から不在になる。私は火曜の朝にそのパターンを grep する方が、どの接続方式が美しいかを議論するよりずっとましだと思う。

## パーサーはフェンスの中を覗かない

> "You can also reference other files using the @ syntax. For example, you can add @AGENTS.md to your CLAUDE.md file to import its contents."
> — [Memory files — Claude Code documentation](https://docs.anthropic.com/en/docs/claude-code/memory)

ローダーはセッション開始時に CLAUDE.md を読み、@filename パターンをスキャンして、各マッチを import 指示として扱う。このスキャンは、マークダウンのコードフェンスとコードスパンの外側でだけ行われる。フェンス内のテキストはパーサーにとって不活性な文字列に過ぎない。つまり @AGENTS.md がフェンスマーカーの間に置かれている場合、ローダーはファイルをオープンしない。警告もログに残さない。リトライもしない。@記号は段落の中のただの一文字だ。コードブロック内のドル記号が通貨ではないのと同じ理屈だ。

フェンス付きセルの total_input が 141 トークン上がっているのは、フェンスマーカーと @AGENTS.md という文字列そのものが不活性テキストとしてプロンプトに投入されたからだ。2,920 トークンの文書は一度もプロンプトに入らない。「フェンス内の @ を見つけた」というエラーパスは存在しない。パーサーに「見落としたフェンス」という概念がないからだ。ファイルを見つけられなかったのではない。そこをそもそも見ていない。

## 2,920 トークンの文書に対する 116 トークン

| セル | ヒット率 | total_input | copy 比デルタ |
|---|---|---|---|
| bare-agents（無接続） | 0/3 | 対照 −2 | — |
| @import | 3/3 | 17,978 | +116 |
| symlink | 3/3 | 17,856 | −6 |
| copy | 3/3 | 17,862 | 0 |
| fenced @import | 0/3 | 15,081 | −2,781 |

キャナリー文書は 9,674 バイトで、3.31 バイト/トークンとして 2,920 トークンに課金される。@import は copy より 116 トークン多い。symlink は 6 トークン少ない。2,920 トークンの文書に対して、これは 4 パーセントの散布だ。三つの方式は機能的に同一だ。いずれも同じ 2,920 トークンをプロンプトに載せている。散布は import メカニズム自体のオーバーヘッドであり、品質差ではない。

## 三つの接続、ひとつの機能

公式文書は @import、symlink、copy を AGENTS.md を参照する三つの方法として並べている。実務では、三つの違いはローダーまたはファイルシステムがパスを解決する方法だけだ。@import はパーサーがパース時に展開する文字列。symlink はローダーが追跡するファイルシステムエントリ。copy はローダーがそのまま読むリテラルファイル。モデルが受け取るプロンプトは、いずれも同じ 2,920 トークンだ。

つまり、この選択は機能的なものではなく、メンテナンス上の好みだ。一つを選んで、コミットして、見直さない。誰かがブログ記事を読んだからといって symlink から @import に切り替えるチームは、116 トークンの差にレビュー時間を消費している。

## 「同等」が成り立たなくなる境界

最も強い反論はこれだ。9,674 バイト、セルあたり 3 ラン、macOS 一台、Claude Code のバージョン一つ。2026-08-16 の実験で、同じローダーが 31-48 KiB の文書で確率的な省略を生じていた。50 KiB 以上で三つの接続が依然 116 トークン以内に収まるかは未確認だ。

そして codex 軸。2026-08-18 の前実験で、このアカウントの codex 60 ランが全て usage limit で死んだ。制限の解除は 2026-09-15。同じリポジトリで codex と claude を両方動かしているチームには、このデータセットは質問の半分しか答えていない。「AGENTS.md をどう接続するか」は、そうしたチームにとって単一ツールの質問ではない。

この範囲には譲る。AGENTS.md が 32 KiB を超えている場合、あるいは codex と claude を並行運用している場合、「同等」はまだ検証していない主張だ。9,674 バイトの文書、単一 claude セッションに対しては、三つの接続は同じだ。

## grep と lint ルール

チームに伝えたのはこれだ。`grep -n '@' CLAUDE.md` を走らせて、コードフェンスの中に置かれた @ パスがないか確認しろ。ドキュメントテンプレートの lint に一行足す。「フェンスマーカーの間に @ パスを置くな」。30 秒で終わるチェックだ。

このフェンスの罠はバージョンに依存しない。OS に依存しない。パースルールだ。ローダーは 2.1.233 でもフェンスの中を覗かないし、来四半期に何が来ても覗かない。この罠は構造的であり、パッチで直るバグではない。

マークダウンフォーマッターでも、prettier の設定でも、CLAUDE.md をリフォーマットする CI lint でも、例示行の周りにフェンスを挿入しうる。そのリフォーマット後に新しいセッションを開く人は、import が死んでいることを知らない。シグナルがない。エラーがない。性能劣化のメトリクスもない。2,920 トークンが、ただそこにいない。

## 死んだ import の四半期コスト

エンジニア 8 人のチーム。各々が 1 日に 3 回新しいセッションを開く。四半期 1,440 セッションだ。ルール文書が 2,920 トークンで、それがプロンプトに載っていない場合、その全セッションがコンテキストなしで始まる。モデルは推測する。ターンを浪費する確認質問をする。あなたが書いた規約を無視したコードを出力する。

これはダッシュボードには出ない。コードレビューが遅くなることとして、モデルが命名規約を知らなくて二往復する PR として、文書ですでに答えられている質問をジュニアが投げてくることとして、現れる。2,920 トークンは安い。それが防ぐレビュー時間は、そうではない。

## このデータセットが答えられないこと

4 ホップの再帰 import。文書は最大 4 ホップと書いている。私が測ったのは 1 ホップだ。フェンスルールが 2 ホップ、3 ホップ、4 ホップで適用されるかは未テスト。

挿入位置。total_input は文書がプロンプト内にあることを教えてくれる。どこにあるかは教えてくれない。システムプロンプトの後か？最初のユーザーメッセージの前か？生データには、六セルのうちの二セルで 109 トークンの分散があり、利用可能なフィールドでは説明できない。

50 KiB 以上。codex 軸。両方オープン。

私の読みはこうだ。まだ AGENTS.md を Claude Code に接続していないチームは、三つの方法のいずれかを選んで、コミットして、見直さないでほしい。116 トークンの散布は意思決定軸ではない。すでに接続しているチームは、今週 CLAUDE.md のフェンス内の @ パスを grep しろ。それが唯一意味のあるチェックだ。

32 KiB の境界と codex 軸はオープンクエスチョンだ。usage limit が 2026-09-15 に解除されたら再測定する。9,674 バイト、3 ラン、単一バージョンのデータセットから言えることと、四半期の本番運用後に言えることは、違うものだ。

フェンスマーカー三行が、2,920 トークンの文書がロードされるかどうかを決めている。文書フォーマットがロードプロトコルだ。マニフェストもない。設定ファイルもない。CLAUDE.md 自体のマークダウン文法が import メカニズムだ。つまり、CLAUDE.md をリフォーマットするあらゆるツールがロード経路の依存関係であり、フェンスを挿入しても誰も警告しない。
