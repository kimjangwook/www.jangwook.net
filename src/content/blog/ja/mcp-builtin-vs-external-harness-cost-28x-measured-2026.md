MCPを外せば運用費が下がるのか。エージェント導入を進めるチームからこの問いを受けた。MCPとCLIを統制条件で比べた実験を読み、あわせて手元でMCPサーバーの道具定義がどれだけの分量になるかを実測した。結論は動かない。MCPは毎ターンの入力に重さを足しうるが、費用構造を決めているのはハーネスであり、インターフェースを差し替えても、その費用は安定して戻ってこない。

エージェント基盤の投資を承認するCTOと、それを実際に回すエンジニアリングリーダーが次にやるべきことは二つだ。道具を標準化する前にハーネスを実測で比べること。そしてアクセス制御を、ハーネスより下の、本当に執行できる層へ置くこと。

## 高い買い物は、道具が呼ばれる前に決まっている

エージェント導入でいちばん頻繁に起きる管理上の失敗は、モデルと道具プロトコルと実行系を一つの調達判断として扱うことだ。この三つは同じ層ではない。

モデルはトークンを出す。CLIやMCPといったインターフェースは、取りうる行動を表現する。ハーネスはそれとは別に、どの指示、どの道具スキーマ、どこまでの会話履歴、何回のリトライ、どの承認ステップ、どのファイル読み込み、どの検証ループを毎ターン載せるかを決める。だからハーネスが、見栄えのいいデモを統制された運用系にするか、予測不能なコストセンターにするかの分かれ目になる。

その統制実験が扱った課題は一つだけだ。私設のリモートgitリポジトリに対する6つの操作を、7種類のエージェントハーネスと5種類の言語モデルで走らせている。完了判定はリポジトリの状態を見て下した。エージェントが「終わりました」と言ったかどうかではない。ここは実務でも効く。自己申告の完了率を数えているチームは、納品された仕事を計測していない。評価対象そのものが生成した未検証の一文を計測している。

論文の中心的な結論は率直だ。

> "The dominant effect was the scaffolding."
>
> — [The Scaffolding Matters More Than the Interface](https://arxiv.org/abs/2608.08654)

エージェントの作業対象がgit、ビルド、ファイルシステム、リンター、パッケージマネージャー、画像変換のようにCLIで成熟しきった表面なら、出発点が変わる。MCPサーバーの登録から始めない。同じ実課題と同じ状態ベースの受入基準で、小さくハーネスを比べることから始める。

## ハーネスの方針は毎ターンぶん掛け算される

実装は面倒でも、ユニットエコノミクスの式そのものは単純だ。

1ターンの入力費用は、システムプロンプト、常駐する道具定義、積み上がった会話履歴、そしてハーネスが送り直すと決めた反復コンテキストで決まる。総費用はそこに、仕事を完了させ、やり直し、確認し、検証するまでに要したターン数が掛かる。

そのすべての項をハーネスが握っている。道具スキーマを毎ターンターン常駐させるのか。履歴を丸ごと再送するのか、圧縮するのか。同じファイルを何度も読み直させるのか。行動が失敗したとき、狭い修復ループに入るのか、それとも広い再探索ループに落ちるのか。完了をシステム状態に一度だけ照合するのか、モデルの出力から繰り返し推測するのか。

道具インターフェースは、この系のなかの表現を一つ差し替える。その表現を毎ターン運び続ける方針までは決められない。

手元では最小限のJSON-RPC stdioプローブを二つのMCPサーバーに当てた。`initialize`、`notifications/initialized`、`tools/list`を送り、返ってきた`tools`配列だけを最小直列化してバイト数を数える。一方は道具2個で1,451バイト。もう一方は道具29個で23,257バイトだった。どのサーバーを登録したかだけで、毎ターン常駐する道具定義のバイト数が16倍に開く。同じプロトコル、同じクライアント、違うサーバーだ。

絶対トークン数の推定値は近似でしかない。本番のトークナイザーではなく、文字数を4で割った値だ。倍率はバイト基準なので、この近似には左右されない。それより重要なのは、これが論文の7×5行列の再現ではないという点だ。ここで切り出したのは、基盤チームが今日から統制できる運用上の一点だけだ。道具スキーマは、毎リクエストに含まれるかぎり抽象的なメタデータではない。毎回積む入力在庫である。

だからMCP経路の失敗は、失敗の頻度が変わらなくても金額の意味が変わる。実験では失敗の頻度は両インターフェースで同じだった。繰り返し実行でも同じだった。それでもMCPランに使った金の12.9%が完了した仕事を一つも買えず、CLIランでは2.2%だった。差は、系が失敗に到達する前にすでに積んでいた費用だ。

総支出と成功率だけを出して、失敗した仕事に紐づく支出を出さないダッシュボードは、まさにこのパターンを隠す。

## 28倍という数字は実在するが、たいてい間違って引かれる

この実験でいちばん引きやすい見出しは、5.0倍から28倍という費用差だ。これをMCPそれ自体がCLIより28倍高い証拠として使ってはいけない。

あの比較は、MCP非対応のハーネス2種と、MCP対応のハーネス5種のあいだで、CLIランだけを突き合わせたものだ。どこにもMCPサーバーは接続されていない。インターフェースをCLIに固定してもハーネスの選択だけで莫大な費用差が生まれる証拠であって、MCPを外す根拠ではない。

ハーネス側のより強い所見は、ローカルで動かした270億パラメータのモデルの結果だ。このモデルは費用がハーネス間で139倍に開き、それでいてすべてのハーネスで課題を完了している。同じモデルクラス、同じ課題、完了という同じ結果、まったく違う実行経済。

厳密に対応づけたMCP対CLIの比率も13個ある。0.43倍から29倍まで散り、両側に外れ値がある。著者自身が、自分たちがやろうとしたインターフェース比較は不安定だったと書いている。経営判断としてはこう読むのが正しい。対応づけた証拠が方向すら定めないなら、インターフェース水準の主張を投資メモに書かない。

社内ベンチマークに必ず持ち込むべき方法論上の警告がもう一つある。エージェントは割り当てられたインターフェースを頻繁に無視した。「MCPラン」「CLIラン」というラベルの付いたレポートは、実際の行動を検証していないかぎり役に立たない。検証がなければ、利用可能な道具とフォールバック挙動とプロンプト解釈とハーネス方針が混ざった、正体不明の何かを測っていることになる。

## いちばん強い反論はMCPについて正しく、次の一手については間違っている

いちばん強い反対意見は、削らずそのまま立てておきたい。

課題は6つのgit操作だった。gitはエンジニアリングでもっともCLIが成熟した表面の一つだ。数十年ぶんのコマンド慣習があり、出力が合成可能で、終了コードが予測でき、文書が厚く、運用の作法まで定着している。この種の仕事をエージェントがCLIで完遂できたという発見は、MCP全般への評決ではない。CLIがすでに例外的に強い領域が形づくった結果だ。

5.0倍から28倍という数字も、MCP撤去プログラムを支えない。MCPを接続したランとCLIだけのランを比べていないからだ。あの比較にMCPサーバーは一台も繋がっていない。これを「MCPは28倍高いという証明」と呼ぶ経営向け資料は、証拠を読み違えている。

この反論は、インターフェースの優劣に関する広い主張のすべてに対して正しい。課題一つは道具経済の全体ではない。CLIが成熟したソフトウェアリポジトリは、顧客データ基盤でも、独自SaaSのワークフローでも、デザインプラットフォームでも、統制下の業務データ環境でもない。対応比率の不安定さも、この限界を裏打ちしている。

ただ、この反論はハーネス側の所見を消さない。インターフェースのラベルを外しても、ハーネスの支配的効果は残る。139倍は、課題を固定し結果を完了に揃えたうえでのハーネス間の変動として残る。行動に移す価値のある信号はそこにある。

git、ビルド系、ファイルシステム操作、パッケージ管理しか触らないチームなら、実用に足るCLI経路がすでにあるのでMCPなしで始めるのは筋が通る。同意履歴、顧客セグメント、社内記録、独自SaaSのオブジェクトを問い合わせなければ仕事にならないチームには、MCPが唯一使える経路になりうる。その場合の問いは、MCPが思想として美しいかではない。そのスキーマの占有量、認可設計、失敗費用のかたちを予算に載せて統制したか、である。

## プロトコルより先に、導入の手順を標準化する

基盤として最初に決めるべきは、道具カタログではなく、繰り返せる評価手順だ。

まずハーネスを2種か3種選び、同じ代表課題を通す。モデル、受入基準、権限、利用可能なデータは固定する。完了はリポジトリの状態、データベースの行、レスポンスコードのように独立して確認できる状態で判定する。エージェントの最後の一文を成功基準にしてはいけない。

この実験はハーネス、課題、検証方法、データセット一式をオープンソースで公開している。運用上これが効くのは、ベンダーのベンチマークを待たずに始められるからだ。借りるべきは数字ではなく規律のほうだ。課題を固定し、構成を統制し、状態で検証し、実行の痕跡を残す。

そのうえで、MCPの登録を統制されたエンジニアリング変更として扱う。

MCPサーバーを登録するPRには、`tools/list`のペイロードサイズと道具数を書かせる。上に書いた基本プローブをCIがそのまま回して、サーバー単位とリポジトリ単位のペイロード上限を執行できる。目的は大きな道具表面を一律禁止することではない。29個の道具が常駐で全エージェントのコンテキストに居座るべき理由を、所有者に説明させることだ。分割するのか、範囲を絞るのか、必要なときだけ読み込むのか。

運用ダッシュボードには失敗支出比率を足す。成功率だけでは、早期に安く落ちた失敗と、コンテキスト膨張と道具呼び出しとリトライを重ねた末の高い失敗を区別できない。これは直球のユニットエコノミクス指標だ。エージェント支出のうち、完了した仕事を買えなかった割合はいくらか。

最後に、道具が使えることと、実行してよいことを切り離す。MCPサーバーは有用な行動を記述できる。だからといって、あらゆるエージェント、課題、環境、委任されたサブエージェントがそれを実行してよいわけではない。

## 変更される前提の層に、セキュリティ保証は置けない

ハーネスは課題方針、コンテキスト方針、承認フロー、利用者体験を置く正しい層だ。最終的なセキュリティ保証を置く層ではない。

ハーネスは設計上プログラム可能だ。チームは道具を足し、プロンプトを書き換え、リトライを調整し、新しいエージェントに対応させ、スループットを上げるために手を入れる。その柔軟性には価値がある。だが同時に、ある機密操作が不可能だったと証明する権威をハーネスには持たせられない。

NVIDIAのエージェントスタック整理は、この含意を明示している。

> "This programmability makes the harness a poor place for a security guarantee: a layer designed to be modified cannot reliably enforce controls against its own modification."
>
> — [Where Security Fits in an AI Agent Stack](https://developer.nvidia.com/blog/where-security-fits-in-an-ai-agent-stack)

エージェントがリポジトリの外に出て、顧客、会員、財務、同意に関わるデータへ届きはじめると、この差は決定的になる。「制限フィールドにアクセスするな」というプロンプトは行動を導けるが、行動を執行できない。エージェントが呼ばないと決められる道具も、統制ではない。執行点は、エージェントもハーネスも超えられない上限を課すランタイムかインフラの境界に置く必要がある。

実務に落とすと、アクセス方針は資格情報、データスコープ、ネットワーク経路、実行アイデンティティ、ランタイムポリシーに紐づける。委任したエージェントには、オーケストレーターより狭い上限を持つ子ランタイムを渡す。監査記録に残すのは、どのアイデンティティがどのポリシーの下でどのリソースへ触ったかであって、ハーネスの設定ファイルにどんな指示文が書かれていたかではない。

これはセキュリティの追加機能ではない。デモができるワークフローと、監査に耐えるワークフローの違いだ。

## 業務側の表面にCLIがないなら、MCPは依然として必要だ

成熟したエンジニアリングのワークフローからMCPを外せば、可動部品は減る。代替のない業務ワークフローから外せば、有用な自動化への唯一の経路が消えるだけだ。

企業のデータ表面の多くは、アプリケーション、ダッシュボード、承認フロー、ドメイン固有のAPIという形で人間向けに作られてきた。エージェントが安全に組み合わせられる一貫したCLIは、そこに存在しない。顧客データの照会、同意状態の確認、社内SaaSの操作、デザインシステム連携は、たいていこの側にある。

OpenAIのプラットフォーム方針もその現実を映している。Codexをコンテキスト管理と道具利用と承認ワークフローを担う再利用可能なハーネスとして位置づけ、MCP道具はアプリケーション側が所有する構図にしている。

> "Codex can then use the application's MCP tools to fetch current data before recommending."
>
> — [Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)

こうしたチームにとって、MCPは費用削減の対象ではない。統合の経路だ。規律のある判断は、その経路を受け入れたうえで、費用とリスクを統制することになる。道具定義は運用に必要な最小の表面へ絞る。広い道具コレクションを既定で登録しない。本番展開の前に常駐スキーマの分量を測る。結果は権威あるシステム状態で検証する。失敗支出は完了支出と分けて追う。データアクセスと行動の上限は、ランタイムとインフラの層で執行する。

これは「どこでもMCP」とも「どこにもMCPなし」とも、実質的に違う戦略だ。業務側の表面から出発して、そこにアーキテクチャの規律を当てる。

## 次の経営レビューでCEOとCTOが変えること

第一に、運用アジェンダの順序で、ハーネス選定をモデルの再交渉より前に出す。モデル契約は重要だ。それでも実測された139倍のハーネス変動は、モデル選定を経営レビュー唯一の費用レバーにできない理由を示している。実行層が、モデルがコンテキストを受け取る頻度、受け取る量、検証に至るまでの高いターン数を決めている。

第二に、失敗支出をエージェントのパイロット承認指標にする。完了率が高いと報告しながら、失敗したランに予算の大部分を静かに吸わせているパイロットは、拡大の段階にない。完了率が答えるのは、その系がときどき動くかどうかだ。運用モデルが経済的に持続するかどうかに答えるのは失敗支出のほうだ。

第三に、MCPの登録をキャパシティプランニングとして扱う。サーバーの道具定義は、サービス依存がレイテンシと信頼性の予算を食うのと同じように、コンテキストの容量を食う。ガバナンスの成果物として正しいのは、実測ペイロードと所有者と正当化根拠とアクセス範囲とロールバック条件が書かれたPRだ。

第四に、書き換え可能なハーネスの指示文ではなく、ランタイム境界の執行に予算を付ける。コンプライアンス投資が、善意のプロンプト文の集まりではなく監査可能な運用能力になるのはここだ。

私の判断はこうだ。CLIが成熟したエンジニアリング作業では、同じ課題でハーネスを比べて追加表面が正当だと示されるまで、MCPサーバーを一つも登録しない。CLIのない業務表面では、MCPを使う。ただし計量され、ランタイムが統制する統合層として管理する。

この判断を変えるのは、CLIのない企業課題群について、ハーネス方針と道具ペイロードとランタイム権限を固定したうえで、MCPを接続した構成のほうが完了した仕事あたりの費用を一貫して下げると、状態検証済みの統制実験が示したときだ。
