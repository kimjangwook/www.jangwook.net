壁を八つ、わざと埋め込んだチェックアウトページを用意した。axe-coreにかけた。四つは赤で捕まり、四つは静かに通過した。通過した四つは、いずれもスクリーンリーダー利用者が実際にぶつかる本物の壁だ。ツールはそれを問題と呼ばなかった。

これが自動アクセシビリティ検査の素顔である。ツールが悪いという話ではない。axe-coreは優秀で、私も毎日使う。問題は、緑を「アクセシビリティOK」と読み替えた瞬間に生まれる。アクセシビリティをCIの一行で済ませたい気持ちはわかる。私もそうだった。だが、その一行が検査する層と、利用者が実際にぶつかる層は同じではない。今日はその緑の裏に何が残るのかを、八つ埋め込んで一つずつ確かめたログでそのまま見せる。

## 基礎: 自動ツールは「ルール違反」を見て「体験」は見ない

アクセシビリティ検査器がやることは、突き詰めれば一つだ。DOMを走査して、機械が判定できるルールに引っかかるノードを探す。`<img>`に`alt`があるかないか、`<button>`にアクセシブルな名前が付いているか、`<html>`に`lang`があるか。ここは真偽がはっきりする。属性がなければ違反。コードで判定は完了する。

ところがWCAGの達成基準の多くは、真偽で割り切れない。`alt`属性が**あるか**は機械が見るが、そのaltが画像の意味をちゃんと伝えているかは見られない。リンクにテキストが**あるか**は見るが、「こちらをクリック」が行き先を説明しているかは判断できない。これはルール違反ではなく、意味の問題だ。人が画面と文脈を読んで初めて答えが出る。

だからアクセシビリティは二つの層に分かれる。下の層は機械が走査できるルール型の違反。上の層は人が判断する体験型の壁。自動ツールは下の層をとても速く、正確に舐める。上の層には手が届かない。厄介なのは、どちらの層も等しくスクリーンリーダー利用者を止めるという点だ。利用者にとって「機械が捕まえられたか」はどうでもいい。

数で感覚をつかむとこうだ。WCAG 2.2の達成基準はいくつもの層にまたがっていて、完全に自動で真偽を出せる項目はその一部にすぎない。残りは自動ツールが「ここが怪しい」まで示して最終判定を人に回すか、そもそも手を出せない。どの項目がどちら側かはツールごとに少し違うが、「自動だけでWCAG全体を検証する」はどのツールでも成り立たない。これはツールの性能の問題ではなく、基準そのものの性質の問題だ。

頭でわかっていても忘れる。だから自分で埋め込んでみた。

## 八つの壁を埋め込んだチェックアウトページ

repoの外の一時サンドボックスに`page.html`を一枚作った。ありふれたチェックアウトフォームだ。ここに壁を八つ、意図的に入れた。四つはルール型(機械が捕まえて当然)、四つは体験型(人しか捕まえられない)で選んだ。

```html
<!DOCTYPE html>
<html>
<head><meta charset="utf-8"><title>Checkout</title></head>
<body>
  <h1>Checkout</h1>

  <!-- #1 ルール型: altのない画像 -->
  <img src="/logo.png">

  <!-- #2 ルール型: ラベルのない入力 -->
  <input type="email" name="email">

  <!-- #3 ルール型: 名前のない空ボタン -->
  <button></button>

  <!-- #4 体験型: altはあるが意味がない -->
  <img src="/chart-q3.png" alt="image">

  <!-- #5 体験型: 行き先を説明しないリンク -->
  <p>返金ポリシーは<a href="/refund">こちらをクリック</a>してください。</p>

  <!-- #6 体験型: 色だけで意味を伝える -->
  <p><span style="color:red">赤色</span>の項目は必須です。</p>

  <!-- #7 体験型: ラベルが別のフィールドを指す -->
  <label for="zip">カード番号</label>
  <input id="zip" name="postal" type="text">

  <!-- #8 ルール型: 見出しレベルの飛ばし h1 -> h3 -->
  <h3>配送</h3>
</body>
</html>
```

`html`に`lang`を付け忘れているのに気づいた人もいるかもしれない。あれは埋め込んだのではなく、うっかり抜けた。後でaxeがこれを捕まえるが、むしろツールがちゃんと仕事をする証拠として残しておいた。

検査はaxe-core 4.12.1をjsdomの上でヘッドレスに走らせた。ブラウザを立ち上げなかったのは、この実験の焦点が「環境の差」ではなく「ルールで判定できるか」にあるからだ。環境の差(ブラウザ対jsdom)が気になるなら、[axe-coreをCIに入れるとcolor-contrastだけ静かに消える理由](/ja/blog/ja/axe-core-ci-a11y-jsdom-vs-browser-2026)でそこだけ別に実測している。

```javascript
import { JSDOM } from 'jsdom';
import fs from 'fs';
import axeSource from 'axe-core';

const html = fs.readFileSync('page.html', 'utf8');
const dom = new JSDOM(html, { pretendToBeVisual: true });
const { window } = dom;
window.eval(axeSource.source);           // axeをjsdomのwindowへ注入
const results = await window.axe.run(window.document, {
  resultTypes: ['violations', 'incomplete'],
});
```

## axe-coreが捕まえたもの

実行結果のviolationsから見よう。ノイズ(landmark/region系)を除き、実際に埋め込んだ壁に当たるものだけ拾うとこうなる。

```text
[image-alt]     impact=critical  img[src$="logo.png"]  Images must have alternative text
[label]         impact=critical  input[type="email"]   Form elements must have labels
[button-name]   impact=critical  button                Buttons must have discernible text
[html-has-lang] impact=serious   html                  <html> element must have a lang attribute
[heading-order] impact=moderate  h3                     Heading levels should only increase by one
```

きれいだ。埋め込んだルール型の四つ(#1 altなし、#2 ラベルなし、#3 空ボタン、#8 見出し飛ばし)を正確に捕まえ、うっかり抜いた`lang`までおまけで噛んだ。これこそ自動ツールの本当の価値だ。人がレビューで見落としがちな機械的な抜けを、コミット数秒で漏れなく舐める。私はこの層を手で検査するのは時間の無駄だと思っている。そこはツールが圧倒的に上手い。

正直に付け足すと、実際の出力はこの五行だけではなかった。`region`(すべてのコンテンツはランドマーク内にあるべき)違反がノードごとに一つずつ、十行を超えて付いてきた。これは本物の問題というより「このページには`<main>`のようなランドマークがない」という構造のサインに近い。自動ツールを初めて当てると、こうした低重大度の項目がレポートを埋めて、肝心のcritical違反が埋もれやすい。だから私は結果をimpactで並べ替え、best-practice系は別に分けて見る。ツールが吐いたものを全部直すべきリストとして受け取ると、かえって消耗する。何から見るかを選ぶのも人の仕事だ。

ここまでならページは「違反五つ、直せば緑」の状態だ。その五つを全部直したと想像してほしい。altを埋め、ラベルを付け、ボタンにテキストを入れ、langを付け、見出しを整える。axeは通過を宣言する。ところがそのページ、まだ壊れている。

## axe-coreが捕まえられなかった四つ

埋め込んだ体験型の四つ(#4〜#7)について、axeは**違反も「要確認」も一件たりとも**出さなかった。完全な沈黙だ。一つずつ見よう。

**#4 · `alt="image"`。** axeは`alt`属性の存在だけを確認する。値が"image"だろうが"asdf"だろうが、空でなければ通過だ。ところが四半期業績のチャートに「image」と読み上げられても、スクリーンリーダー利用者は何の情報も得られない。むしろaltがまったくないより悪い。空のaltは「装飾画像」という合図にはなるが、「image」は本物の情報を偽の情報で覆う。WCAG 1.1.1は「同等の代替テキスト」を求めるが、同等かどうかは機械には判定できない。

**#5 · 「こちらをクリック」。** リンクにテキストがあるので`link-name`ルールは通過する。だがスクリーンリーダー利用者は、リンクだけを一覧で舐めてページを探索することが多い。「こちらをクリック」「こちらをクリック」「こちらをクリック」が並ぶと、どこへ行くリンクなのか知りようがない。WCAG 2.4.4はリンクの目的がリンクテキストだけで(または文脈から)わかることを求める。文脈を読むのは人の仕事だ。

**#6 · 色だけで伝える。** 「赤色の項目は必須です」は、色が見えない利用者には無意味だ。色覚の異なる利用者もスクリーンリーダー利用者も「必須」という情報を取りこぼす。WCAG 1.4.1がまさにこれを禁じている。ところがaxeは、その文が色だけに依存しているかを判断できない。`color:red`というスタイルは見えるが、その色が唯一の情報伝達手段かどうかは文脈の問題だ。

**#7 · ラベルが別のフィールドを指す。** これが一番たちが悪い。`<label for="zip">カード番号</label>`が`id="zip"`の入力ときちんと結びついている。結びつき自体は完璧なので`label`ルールは通過する。問題はその入力の`name`が`postal`であること。ラベルは「カード番号」と読み上げるのに、実際は郵便番号のフィールドだ。スクリーンリーダー利用者はカード番号を入力せよという案内を聞いて、別の欄を埋めてしまう。結びつきの**存在**は機械が見るが、結びつきの**正しさ**は見られない。

四つの共通点が見えるだろうか。どれも「属性や要素は所定の位置にあるのに、その中身が間違っている」型だ。自動ツールは構造を検査するが意味を検査しない。そして現場で本当に利用者を止める壁のかなりの部分が、まさにこの意味の層にある。私はこれが自動アクセシビリティツールをめぐる最大の誤解だと思う。緑は「ルール違反がない」であって「アクセシブルである」ではない。

具体的に描くと腑に落ちる。このページをスクリーンリーダーで上から下へ読むと、だいたいこう聞こえる。「Checkout、見出しレベル1。画像。編集、メール。ボタン。画像、image。返金ポリシーはリンク、こちらをクリック、してください。赤色の項目は必須です。カード番号、編集。」altを埋めラベルを付けてaxeを緑にした後も、利用者が聞く文は依然として「画像 image」「リンク こちらをクリック」、そして「カード番号」と案内する郵便番号欄だ。ツールの通過と利用者の体験の間に、これだけの隙間が開く。

### なぜチームは緑を誤読するのか

この誤解が生まれるのは、たいてい悪意ではなくプロセスのせいだ。アクセシビリティがスプリント終盤に「axe通過」という一行の完了条件で入ってくると、通過イコール完了で固まる。レポートに違反0と出れば、誰もその先を見ない。数字が与える安心はそれほど強い。私も緑のスクリーンショットをPRに貼って先へ進んだことがある。それがルール型の層しか見ていなかったと認めるまで時間がかかった。

ここにツールベンダーのマーケティングも一枚噛む。「自動でアクセシビリティを保証する」という文句は売るには良いが、事実ではない。標準化団体が公式に否定する主張だ(後で引用する)。自動化にできることとできないことを正確に線引きすること自体が実務力だと思う。ツールを使わないのも、ツールだけを信じるのも、どちらも間違いだ。

## color-contrastはなぜ「要確認」に落ちたか

violationsとは別に、incomplete(要確認)の一覧も出た。その一つが`color-contrast`だ。

```text
--- INCOMPLETE / needs review ---
[color-contrast]      h1    Elements must meet minimum color contrast ratio thresholds
[page-has-heading-one] html  Page should contain a level-one heading
```

色コントラストは本来axeが自動で捕まえる代表項目だ。ところがここでは違反ではなく「要確認」に落ちた。理由は単純で、jsdomは画面を実際に描画しない。コントラストを計算するには、描画されたピクセルの実際の前景色と背景色が要るのに、描画がないので計算できない。だからaxeは「判定不能、人が見よ」に回す。

これは前の体験型の見逃しとは性質が違う。体験型の四つはブラウザを立ち上げても永遠に捕まえられない。色コントラストは本物のブラウザで走らせれば自動で捕まる。混同しやすいのはここだ。同じ「捕まえられない」に見えても、片方は環境を変えれば解決し、片方は絶対に解決しない。この二つを混ぜて考えると、「ブラウザで走らせたからもう全部捕まるだろう」というまた別の緑の誤解につながる。だからCIパイプラインを組むときこの区別が効いてくる。その設計は[color-contrastがCIで静かに消える理由](/ja/blog/ja/axe-core-ci-a11y-jsdom-vs-browser-2026)に別途まとめたので、ここでは繰り返さない。要点だけ。「要確認」を空行として扱うと、実際のカバレッジに穴が開く。

## W3Cが公式に言うことと「57%」という参考値

これは私の個人的な意見ではない。W3C WAIが公式文書で釘を刺している。アクセシビリティ評価ツール選定のガイドはこう書く。評価ツールは「アクセシビリティを判定できず、判定を助けられるだけだ(cannot determine accessibility, they can only assist in doing so)」。そしてサイトがアクセシブルかを決めるには「知識を持つ人による評価が必要だ」と明記する。どのツールも単独では準拠を判定できない、というのが標準化団体の公式な立場だ。

ある数字がよく引かれる。自動ツールがアクセシビリティ問題の約57%を捕まえるというDequeの調査だ。ここには条件が付く。この57%は**問題の件数ベース(by volume)**だ。alt抜けや色コントラストのような頻度の高い問題が監査件数を支配するが、これがまさに自動ツールの得意分野である。だから件数で数えると数字が大きくなる。測り方を変えれば30%近くまで下がることもある。この数字は参考値であって公式基準ではない。私はこの57%を引くたびに「何の57%か」を必ず添えるべきだと思う。WCAG達成基準の57%ではなく、よくある問題件数の57%だ。達成基準のカバレッジで言えば、完全に自動で検証できる項目はそれよりずっと少ない。

正直に限界をもう一つ添えよう。私の実験はページ一枚、壁八つの例だ。ベンチマークではなく原理を見せる再現である。「四つ捕まえて四つ逃したから自動化は50%」と一般化すれば、それも間違いだ。比率はどんな壁を埋めるか次第でいくらでも変わる。この実験が語るのは比率ではなく**種類**だ。捕まえられないものは、偶然捕まえられないのではなく、構造的に捕まえられない。

## 自動の緑の裏で回すべき手動レビューのチェックリスト

では何をすべきか。自動ツールは使い続ける。CIに入れ、コミットごとに走らせる。それが下の層を守る一番安い方法だ。その上で、緑が出た後に人が上の層を舐める。毎回フル監査はできないので、自動化が構造的に見られない項目だけを絞ったチェックリストをレビューに添える。

- **画像altの品質**: altが「あるか」ではなく、画像の意味を代替しているかを読む。情報性の画像(チャート、図)はデータを、装飾画像は空のaltを。「image」「photo」やファイル名はすべて失敗と見なす。
- **リンク・ボタンのテキストを文脈から切り離す**: リンクテキストだけを一覧に抜いて読む。「こちら」「クリック」「もっと見る」だけで行き先がわからなければ直す。スクリーンリーダーのリンク一覧探索を真似るのだ。
- **色・形だけに頼った情報**: 「赤い項目」「緑のバッジ」「上のグラフ」のように、色や位置だけで意味を与える文を探す。色をテキストやアイコンのラベルで二重化する。
- **ラベルとフィールドの実際の対応**: ラベルが結びついているかではなく、ラベルの言うこととフィールドが受け取るものが一致するかを確認する。autocomplete属性と`name`がラベルとずれていないか見る。
- **読み上げ順序と見出しの意味**: 見出しが視覚的な大きさ調整に使われていないか、タブ順序が論理的な流れに沿っているかを見る。ここは機械が構造は見ても意図は見られない。
- **キーボードだけで全体の流れ**: マウスを片付け、タブ・エンター・矢印だけでフォームを最後まで送信してみる。5分あれば自動ツールが捕まえられないフォーカスの罠のほとんどが露わになる。フォーカスがどこにあるか見えない、モーダルを開いたのにタブが背後のページへ抜ける、順序が視覚配置とずれる。この5分でほぼ全部引っかかる。

この六行をPRテンプレートに入れておけば、自動検査が緑を出しても、人が上の層を一度は舐めて通ることになる。完璧ではない。だが「緑イコールアクセシビリティOK」という一番高くつく誤解は防げる。

チェックリストを全部自動化したい誘惑も湧くだろう。実際、最近はLLMに「このaltは適切か」と尋ねるツールも出ている。方向は面白いが、私はまだこれをゲートとしては信頼しない。LLMは「赤い項目は必須」が色だけに依存するかをそれらしく答えるが、その判断がページ全体の文脈やデザインの意図を反映している保証はない。補助ツールとしては使えるし、人の最終判断を置き換える用途にはまだ早い。上の層をまた別の自動化で覆おうとして、誤検知と見逃しを新しく持ち込む羽目になりかねない。ここでもルールは同じ。自動化が何を見られないかを正確に知って使うこと。

アクセシビリティは、ツールが代わりに判定してくれるチェックボックスではない。コードとコンテンツが実際の利用者にどう届くかの問題だ。既存サイトのアクセシビリティが自動の緑の裏で実際どこまで塞がれているかを点検したい、あるいはルール型と体験型を分けて検証するパイプラインを組みたいなら、個人的に相談と実装のご依頼を受けている。プロフィールの問い合わせ経路からご連絡を。
