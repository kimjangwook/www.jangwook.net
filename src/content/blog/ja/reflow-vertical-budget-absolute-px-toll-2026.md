## 横方向判定の死角

障害対応で最初に確認するのは「ユーザーの画面に実際に何が見えているか」だが、自動化されたアクセシビリティ判定は、その問いの一部の軸しか測っていない。WCAG 2.2 の成功基準 1.4.10 Reflow は、縦スクロール型コンテンツに対してこう要求する。

> "Vertical scrolling content at a width equivalent to 320 CSS pixels"[2]

幅 320 CSS ピクセルでの提示を求めているのはこの一文だけだ。高さについては規範テキストのどこにも規定がなく、1.4.10 が縦を保証すると明言したことは一度もない。この点に関して規格側の設計は一貫しており、反論として「1.4.10 はもともと縦を規定対象にしていない」は規範解釈としては正しい。

では実務の判定運用はどうか。リフロー判定の自動チェックが緑になると、多くのチームはそれを「拡大しても読める」の代理指標として扱う。この代理関係が成立するかどうかは、規格文書ではなく実測で確かめるしかない。公開されているライブサイトの一つを対象に、ビューポート高さ 4 段階 × スクロール状態 2 種 × chrome 要素の除去条件で 27 ランの測定を実行した。結果から先に言うと、横方向の判定は全セルで通過した。縦方向の予算はその裏で崩れていた。

まず横の確認から。幅 320px に固定したビューポートで `clientWidth 320 = scrollWidth 320, h_overflow_px 0, reflow_pass true (8/8)` であり、ドキュメントレベルの横スクロールはラダー全体のどこにも発生しなかった。1.4.10 が測る軸に限れば、このページは clean だ。post ページだけで子孫要素のあふれが offenders 97、最大 604px を記録したが、ドキュメントレベルの横スクロールは 0 であり、判定自体は通過する。次に、この通過したページの縦を見た結果が以下の通り。

## 320×200の縦予算118px

測定の基準になったのはusable_pxという値だ。定義はelementFromPointによる行単位のヒットテストで、幅320のビューポート内を2pxステップで縦に走査し、xを25%・50%・75%の3列で試して、本文要素に実際に到達できる行の合計を数える。障害対応の用語に寄せれば、ユーザーが実際に触れる画面領域の面積である。ヘッダーやオーバーレイがその座標を上から塞いでいれば、その行は本文に触れない。

手順は単純で、次の3コマンドで再現できる。envはdarwin 25.5.0、playwright 1.58.2、chromium 145.0.7632.6、対象は公開ライブサイトだ。

1. `budget-ladder-320w-4heights` … ビューポート高4段（844/400/256/200）× スクロール状態2種（top/mid）× クローム除去の有無で、usable_pxを計測
2. `chrome-stripped-recovery-844-vs-200` … 固定クロームを全除去して回復量を検証（falsifier条件）
3. `removal-decomposition-at-320x200` … 要素ごとに個別除去し、回復量を分解

top状態（ページ最上部）での結果が次の表だ。

| ビューポート高 | usable_px (top) | 損失 |
|---|---|---|
| 844 | 762 | 82 |
| 400 | 318 | 82 |
| 256 | 174 | 82 |
| 200 | 118 | 82 |

320×200で残るのは118px。フルHD級のビューポートを基準に設計された本文が、拡大ユーザーの手元では縦118ピクセルの窓からしか見えない。損失率にすると41.0%だ。ただしusable_pxの定義はこのヒットテスト方式に依存しており、スクリーンリーダーの通過や実読速度という別の定義を使うなら値は読み直す必要がある。

## 高さに依存しない82pxの通過料金

表を見て最初に確認したのは、損失が比率ではなく固定額だという点だった。844−762 = 400−318 = 256−174 = 200−118 = 82。四つの高さで損失が正確に82pxで同一である。

この数字の解釈が論点の中心になる。もし損失がビューポート高に比例して縮むなら、話は「小さい画面では少し不利になる」で済む。実際は比例ではなく絶対値なので、同じ82pxが高さ844では9.7%、高さ200では41.0%になる。比率が大きくなるのは分母が小さくなるからで、遮蔽主体の取り分が増えているわけではない。深夜オペレーションで手の届く範囲を物理的な固定物が狭めるのに近い。ビューポートがいくら縮んでも、その固定物の寸法は変わらない。

なぜ絶対値なのか。理由は遮蔽主体がビューポートの寸法に応答しないからだ。ページが高さ200ピクセルに縮んでも、fixed配置のクロームは844ピクセル時代と同じ高さを主張し続ける。この非弾力性が、判定の通過と縦の崩壊を切り離す機構である。

## 遮蔽主体の分解と90px下部広告コンテナ

通行料を誰が請求しているのか。320×200 で要素を一つずつ個別に除去し、回復量を測る分解実験を実行した。mid スクロール状態での結果が以下の通り。

| 除去した要素 | 回復量（mid） |
|---|---|
| header | Δ0 |
| reading-progress | Δ0 |
| #back-to-top（fixed, h=48） | Δ0 |
| #fixed_container_bottom | Δ+90 |
| ALL | Δ+90 |

mid 状態の遮蔽主体は、90px の下部広告コンテナ単独だ。個別除去の回復量の合計 0+0+0+90 が ALL 除去の +90 と正確に一致し、遮蔽の重なりはない。コンテナを除去すると usable_px は 110 から 200 に全量回復し、同じ結果が 3/3 のランで再現した。

表の中で説明が要る点が二つある。第一に、#back-to-top の Δ0 について。この要素は mid スクロールで visible、fixed、高さ 48px と確認できている。だが今回のデータからは、これらのランでこの要素が何も遮蔽しなかったのか、プローブが捉えられない条件でのみ遮蔽したのかを区別できない。non-null で存在しているが 0px しか遮蔽しない状態は、この測定の分解能では判別しなかった。Δ0 を「遮蔽していない証拠」と読むことは、このデータは支持しない。要素が縦予算の軸以外、たとえば WAI 文書が挙げるキーボードフォーカスの遮蔽でどれだけのコストを払っているかも、本測定は計上していない。

第二に、遮蔽が散発的に消えるランがあったことだ。fixed_container_bottom の遮蔽は 6 ランのうち欠測があり、広告ロードのタイミングを疑っているが、原因は未規明だ。mid の数字が clean sweep ではなく 3/3 や 6/6 の表記になっているのはこのためである。

## elementFromPointヒットテストと統制セル

測定手法そのものが損失を作っていないかは、統制を回して確認した。ローカルの統制文書（固定クロームが一切ない_proseのみのページ）で同じヒットテストを走らせた結果、全行でratio 1.0だった。つまり損失を作るのはページ側のクロームであって、測定方法の常套ではない。障害対応で言えば、計測器の零点合わせを先にやる手順だ。

一方で1.4.10の横方向判定はどうだったか。`reflow-1410-horizontal-pass-check`の結果、8/8セルで通過した。clientWidth 320 = scrollWidth 320、横オーバーフロー0。ただしpostページだけは子孫要素の溢れが97件あり、最悪のoverflowは604pxだった。文書レベルの横スクロールは0なので判定は通るが、要素単位では溢れている。この子孫がどこでクリップされるかまでは今回確認していない。

## falsifierが修正した帰属、staticヘッダーの分

私の当初の仮説は「82pxの損失は固定クローム（stickyヘッダー）の取り分だ」だった。検証条件として、固定クロームを全部除去したら縦の予算が回復しないなら仮説の軸が崩れる、と先に潰しを定義しておいた。実際の測定は回復を示した。h=200のmidで110から200へ、+90が3/3ランで同一だった。仮説の軸は生き残った。

だが帰属は修正が必要だった。ヘッダーのpositionは、h=844ではsticky、h=200ではstaticという挙動が6/6で再現された。staticに下がったヘッダーは文書の流れと一緒にスクロールするので、top状態の遮蔽者ではなくなる。82pxの正体は固定クロームではなく、文書フロー内のヘッダーブロックの取り分だった。「固定物が手の届く範囲を狭める」という比喩は、mid状態の90px広告コンテナにはそのまま当てはまるが、top状態の82pxには当てはまらない。順流するブロックが持っている常設の取り分だ。

未検証項目は次の通り。

- headerのstickyからstaticへの切替しきい値は特定できていない。480であることは確認できず、(400, 844]区間までしか絞れていない。
- fixed_container_bottomの遮蔽が散発的に消える原因は未解明。
- homeページのh=200 top usable_px 0の残り118pxは、blocked_pxが空のまま帰属に失敗した。他ページの82pxパターンと唯一異なる。
- #back-to-topが縦の予算以外の軸（キーボードフォーカスの遮蔽）で払うコストは今回測っていない。
- offenders 97個の子孫のクリップ先は未確認。

## 独立ゲートとしての縦予算監査とC34への切替

1.4.10の通過は「拡大しても読める」の代理指標として成り立つのか。規範の解釈としては反論が正しい。1.4.10は縦を規定の対象にしておらず、縦を保証すると規定が主張したことはない。反論が正しい範囲は規格文書の内側だ。実務の判定慣行では通過が代理指標として転用されており、この実測は82pxと90pxという絶対的な通過料金の前でその転用が壊れることを数値で示した。

W3CのUnderstanding文書自身が、stickyやfixedなコンテンツがReflowの受益者にとって読書を困難にしうると明言している[1]。 techniquesのC34はこう言う。

> Sticky regions always stay visible in the viewport while the other content will disappear underneath when scrolling.
> — [CSS technique C34: Using media queries to un-fixing sticky headers / W3C WAI](https://www.w3.org/WAI/WCAG22/Techniques/css/C34)

つまり規格側は既に危険を認識していて、対処技法（C34：メディアクエリでstickyやfixedを静的配置へ切替）も用意してある[3]。欠けているのは、通過判定の隣に置くべき第二の測定だ。

リードとして明日変えるなら、分岐は明確になる。スクリーンリーダー利用や拡大の実ユーザーを実際に受け入れるサイトでは、1.4.10の自動判定の隣に320×200でのusable_px測定を独立したCIゲートとして立て、stickyヘッダーと下部固定コンテナにC34のmin-heightメディアクエリで静的切替を仕込む。ローカル統制文書や固定クロームのないレポートのように、クロームの固定費がゼロのページでは、1.4.10の通過だけで十分であり縦予算の監査は過剰になる。固定費ゼロの現場に監査プロセスを追加しても測定値は1.0のままだ。

規格の準拠判定が通過を出したとき、その通過は規格が任意に選んだ軸の内側でのみ有効だ。規格が測らない軸は準拠証書ではなく測定が証明する。ヘッダーの切替しきい値が(400, 844]のどこにあるのか、次のランが測るべき最後の数字として残っている。
