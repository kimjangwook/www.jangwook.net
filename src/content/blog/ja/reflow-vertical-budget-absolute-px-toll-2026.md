## 400%拡大が減らすのは高さのほう

画面を拡大して文字を読む人がいる。老眼、視覚の疲れ、一時的なけが。理由はさまざまだ。ブラウザの拡大機能で文字を400%にして読むことが、 Web アクセシビリティの前提になっている。Web アクセシビリティとは、誰もが使える Web にするための国際的な決まりごとだ。

拡大すると何が起きるか。画面の幅も高さも、それぞれ4分の1になる。直感では面積が4分の1になるように感じるが、実際は縦と横の長さがそれぞれ4分の1になる。幅は320ピクセル分だけ残ればよい、という決まりがある一方で、高さについては決まりが何もない。

実際に測った。ある公開サイトを、高さ200ピクセル、幅320ピクセルの小さな画面で表示した。本文に文字が実際に置ける縦の広さを測ると、118ピクセルだった。高さ200ピクセルのうち118ピクセル。半分以上は文字のない空間で埋まっていた。

確かめたいことは二つある。一つは、公式の横方向の検査に合格したページでも縦が崩れているのか。もう一つは、縦を削っているのがどの要素なのか。

## 公式の横方向検査が測らない縦

WCAG とは Web のアクセシビリティを定めた国際規格のことだ。その中に 1.4.10「リフロー」という合格基準がある。リフローとは、画面を拡大しても文字が折り返して並び直し、横にスクロールしなくて済むこと。検査は「横にスクロールする必要がないか」だけを見る。縦のスクロールは、ページはもともと上下に読むものだから、前提として許されている。

W3Cは Web の標準を作る団体だ。その規格文書は、縦にスクロールする内容に幅320 CSSピクセルを要求する。CSSピクセルは Web で使う長さの単位だ。高さには何も言っていない。

> Content can be presented without loss of information or functionality, and without requiring scrolling in two dimensions for: Vertical scrolling content at a width equivalent to 320 CSS pixels; Horizontal scrolling content at a height equivalent to 256 CSS pixels.
> — [Understanding Success Criterion 1.4.10: Reflow / W3C WAI](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

つまり規格は縦を測る気がない。これは規格の設計どおりであり、批判すべき点ではない。問題は実務の側にある。合格マークを見て「拡大しても読めるはず」と判断してしまう慣行だ。合格は横についてしか何も言っていないのに、縦まで保証された気になる。今回の実測は、この取り違えがどこで破綻するかを数値で示したものである。

## 消えた縦の空間の正体

失われた82ピクセルの正体を確かめるには、画面に載っている要素を一つずつ外して、縦の広さがどう変わるかを見るしかない。測定では、画面の縦の長さを844、400、256、200ピクセルと段階的に狭めた。それぞれの高さで、記事の文字に実際に届く縦の幅を数えた。どの高さでも損失は82ピクセルで固定だった。では、82ピクセルを占めているのはどの要素か。

外す実験では、画面に貼りついたまま消えない要素を一つずつ取り除き、記事に届く縦のピクセルがどれだけ戻るかを数えた。結果はこうだ。

| 外した要素 | 戻ったピクセル（320x200、途中までスクロールした状態） |
|---|---|
| ヘッダー（ページ上部の帯） | 0 |
| 読み進め具合を示す帯 | 0 |
| 上へ戻すボタン | 0 |
| 下部の広告の器 | 90 |
| すべて | 90 |

戻ったのは90ピクセルだけで、その全額を下部の広告の器が一枚で占めていた。広告の器を外すと、使える縦の幅は200ピクセルすべてが回復した。上へ戻すボタンを外しても0ピクセル。全部を外しても90ピクセルのままなので、どの要素も互いに重なり合わず、それぞれが別々の場所を塞いでいたと分かる。

ここで、最初の測定結果と矛盾する点が一つ出てくる。ページの最初の状態で失われていた82ピクセルは、画面に貼りついたヘッダーの仕業ではなかった。測定した走行では、画面の高さが小さくなるとヘッダーはすでに固定表示をやめていた。固定表示とは、スクロールしても画面の端に張りついたまま消えない見せ方のことだ。ヘッダーは通常の文書の流れに戻り、ページと一緒に流れていき、何も塞がない。つまり82ピクセルは、画面の上に重なって載る固定要素の持ち分ではなく、文書の流れの中でヘッダーのブロックが占める場所だった。だからヘッダーを外しても回復は0だったのだ。

実際に塞いでいたのは、途中までスクロールした状態での下部の広告の器である。画面の高さが844でも200でも、この器は400ピクセルの高さのまま縮まない。この固定サイズが、途中までスクロールした状態での損失の正体だ。W3Cの解説も、こうした張りつく要素について読むことを難しくし得ると警告している。

> Such sticky or fixed content can pose significant issues for those who would benefit from Reflow, as aside from obscuring keyboard focus, such sticky or fixed content can make reading content difficult if not impossible.
> — [Understanding Success Criterion 1.4.10: Reflow / W3C WAI](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

W3Cは張りつく要素の定義もはっきり示している。

> Sticky regions always stay visible in the viewport while the other content will disappear underneath when scrolling.
> — [CSS technique C34: Using media queries to un-fixing sticky headers / W3C WAI](https://www.w3.org/WAI/WCAG22/Techniques/css/C34)

分母が縮んだのだ。損失そのものは増えていない。

## 損失が増えるのではなく分母が小さくなる

90ピクセルの損失の意味は、画面の高さで変わる。高さ844ピクセルなら全体の約1割で、気になる程度だ。高さ200ピクセルなら45%。半分近くの縦が文字の置けない空間になる。90ピクセルという損失そのものは一度も大きくなっていない。大きくなるのは、損失が占める割合だ。分子が同じで分母が小さくなるだけである。

拡大して読む人にとっての画面は、物理的に小さい。拡大率を上げるほど、画面は高さ200ピクセルに近づく。つまり拡大する人ほど、固定サイズの要素が占める割合が大きくなる。拡大の極限では、一つの要素で読める場所の半分が消える。

もう一つ、測定で確かめたのは、横方向の検査の結果だ。8つの条件すべてで、幅320ピクセルの中に横あふれはゼロ、リフロー検査は全件合格だった。合格と縦の崩壊が同時に成立する。両者は別の測定であり、片方がもう片方について何も語らない、というのが実測の帰結である。

## 合格判定のそばに置く縦の測定

自分のサイトで取るべき対応は、ページの種類で分かれる。

画面の拡大や読み上げ機能を使う人を実際に受け入れるサイトなら、320x200の状態で本文に届く縦のピクセルを測る検査を用意すること。これは従来の横方向の合格判定とは別に行う。

固定で浮いている要素がまったくない社内文書や報告書のようなページなら、横方向の検査の合格だけで足りて、縦の測定は不要である。

縦の測定が要るページで、固定表示の広告容器が本文を圧迫している場合は、直し方がある。W3C は C34 という手法で、画面が小さいときは固定表示をやめて本文と一緒に流す方法を示している。固定表示とは、スクロールしても要素が画面に張り付いたまま残る表示のことだ。これを小さな画面では普通の配置に切り替えれば、本文に文字が戻る。

画面を大きく拡大して読む人に対して、公式検査の合格マークは、縦にどれだけ文字が残るかを保証しない。縦にどれだけ文字が残るかは、測って初めて分かる。

## この記事が確認できなかったこと

この実測は公開サイト一つ、一台の環境、Chromium 145 の結果にすぎない。Chromium は Chrome のもとになるブラウザだ。広告の容器が本文を遮る状態が読み込みのタイミングでばらつく理由は突き止められなかった。ヘッダーが固定表示から普通の配置に切り替わる画面の高さのしきい値も、高さ400ピクセル超844ピクセル以下の範囲までしか狭められていない。また、縦の予算が実際に拡大利用者の離脱に影響するかという行動データは、この測定の範囲外である。次に確認すべきは、異なる構造のサイトでの再現と、しきい値の特定である。
