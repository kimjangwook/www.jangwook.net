エージェント構成からMCPサーバーを外せば請求書は本当に下がるのか。それが知りたかった。私が見ている二つのチームが、揃ってそのレバーに手を伸ばしていたからだ。実務者の体験談をもう一本読む代わりに統制された測定を探して、一つ見つけた。2026年8月9日にarXivへ投稿された論文で、固定した一つのソフトウェアタスクを7種のスキャフォールディングと5つの言語モデルに通している。答えは、私が引いていたレバーが間違っていた、だった。インターフェースの差はほとんど効かず、その上に乗るハーネスがコストを5.0倍から28倍動かしていた。

エージェント費用の行にあなたの名前が入っているなら、これは他人事ではない。私の結論はこうだ。コストレポートの集計キーをモデル名からハーネス名に組み替えろ。そして「MCPはCLIよりN倍高い」という数字は、ハーネスを固定するまで意味のある数字として扱うな。この告発には自分の文章も含めている。数か月前、MCPのトークンコストをインターフェースの問題として書いた記事を出した。算数が合っていた箇所でも、診断の層が間違っていた。

## 論文が実際に測ったもの

設計は意図して狭い。タスクは一つに固定してある。プライベートなオンラインgitリポジトリに対する6つの操作だ。そこにスキャフォールディング7種とモデル5種を掛け、全セルを走らせている。

> The dominant effect was the scaffolding. Two of the seven ship no MCP support at all; they completed every run using only the CLI, which shows that MCP is unnecessary for this class of work, and they were 5.0x to 28x cheaper than the five scaffoldings that do support MCP, comparing CLI runs alone with no MCP server attached anywhere.

> — [The Scaffolding Matters More Than the Interface](https://arxiv.org/abs/2608.08654)

この比較の形を丁寧に読んでほしい。効いているのは形のほうだ。MCP実行とCLI実行を比べたのではない。MCPを話せないスキャフォールディングのCLI実行と、話せるスキャフォールディングのCLI実行を比べている。しかもどちらの側にもサーバーは一つも接続していない。高いグループは、安いグループとまったく同じことをしながら高かった。

著者たちが本来やろうとしたインターフェース同士の厳密なペア比較のほうは、崩れた。「thirteen strictly paired MCP-to-CLI ratios span 0.43x to 29x, with outliers on both sides.」両側に外れ値が出た。つまりMCPのほうが安かったペアもある。MCPのオーバーヘッドを単一の倍率で語ってくる相手は、この散らばりの中の1セルを引用しているだけだ。

ハーネス、タスク、検証手順、データセットの全体がオープンソースで公開されている。これが置き換えようとしている既存の推定値については、そう言えない。論文はそこも率直だ。既存の数字は「disagree by more than an order of magnitude while resting on practitioner reports that cannot be reproduced」と書いている。

## 古い数字を壊した測定手続きの変更

因果として立っているのは二つで、残りは推論だ。混ぜずに書く。

一つ目。著者たちは「verified completion by inspecting the repository state rather than trusting the agent's self-report」した。従来の合意が死んだのはこの一行だ。エージェントが自分でやったと言った内容で採点するなら、測っているのはモデルが勝利宣言をしたがる度合いであって、その度合いはハーネスごとに違う。以前インターフェースの差だとされていた分散の多くは、完了判定の方式の差だった。

二つ目、そしてこちらのほうが私には不気味だった。「Agents frequently ignored the interface they were assigned.」実際に発火したツール呼び出しを検証していないA/Bは、MCPとCLIが未知の比率で混ざった何かを測っている。社内で回ってきたMCP対CLIのコスト比較で、私がうなずいた分も含めて、その検証を踏んでいたものは一つもない。

なぜMCP対応のスキャフォールディングがCLIを走らせているのに高くつくのか、それは私には言えない。ありそうな筋書きは、MCPの配管、つまりツールスキーマの枠、ディスカバリ層、承認フローが、サーバーの有無に関係なく毎ターンのコンテキストに再常駐するというものだ。筋は通る。そして私には証拠がない。論文はコストをターン数とターン当たり入力トークンに分解していないので、機構は開いたままだ。最も極端な結果も同じだ。ローカルで動く270億パラメータのモデルは、すべてのスキャフォールディングでタスクを完了しながら、コストが139倍に広がった。分散は報告されている。原因は分かっていない。

## 三つの軸、そしてみんなが回している一つ

実験の変数は三つある。どれだけ動いたかと、どれだけ自分の裁量が及ぶかで並べ直す価値がある。

インターフェース、MCP対CLI。論文が測るために組まれた軸で、ここはほとんど何も分けなかった。失敗の頻度は両者で同じ。初回の実行でも反復でも同じだった。分かれたのは一点だけ、失敗にいくら払うかだ。「12.9 per cent of the money spent on MCP runs bought no completed work against 2.2 per cent on CLI runs.」失敗率は同じで、失敗一件当たりの無駄が6倍。ダッシュボードが完了率を追っているだけなら、この差はあなたの目には映らない。

スキャフォールディング、ハーネス7種。支配した軸だ。モデルとタスクを固定して5.0倍から28倍。

モデル、5種。効き方は感度の乗数としてだった。小さいモデルのほうがハーネス選択の影響を強く受け、270億パラメータで139倍が出た。

実務で制御できる順番はスキャフォールディング、インターフェース、モデルの順だ。私が話を聞くチームのほとんどは、このリストを逆から潰している。モデル単価を交渉しプロンプトを詰めている間、ハーネスは誰の管理下にもなく浮いている。

## 真面目に受け取っている反論、舞台はCLIが勝つように組まれていた

ここまでの話に対する一番強い反論は、標本が結論を先に決めていた、というものだ。タスクは一つ。リポジトリに対する6つのgit操作。gitはコマンドラインを20年磨いてきた領域で、この業界で最もCLIが成熟した表面だと言っていい。gitでCLIが勝つと示すのは、釘に対してハンマーが勝つと示すのに近い。

これは難癖ではないので、一段落以上を割きたい。しかも弾は論文自身が渡してくる。5.0倍から28倍という数字はそもそもインターフェースの比較ではない。MCP非対応の2種とMCP対応の5種という、スキャフォールディングの集団間の比較だ。集団の所属はMCP対応の有無と相関しているが、同時に、その7つのツールの作りに関する他のすべてとも相関している。既定のコンテキスト処理、リトライのロジック、システムプロンプトの分量。インターフェースだけを切り出すはずのペア比較は0.43倍から29倍で戻ってきた。あれは知見ではなく、肩をすくめる動作だ。

そこで譲る部分を書く。譲るのは表現ではなく適用範囲だ。この論文の処方を持ち込んではいけない領域が三つある。

CLIに等価物がない領域。私のデータ系チームがエージェントに開きたがっているものは、ほぼ全部これだ。会員レコード、プロフィール、同意履歴。この種の呼び出しの権限判定はファイルシステムの境界の外にあり、そこへ手が届くCLIを作るというのは、誰かのラップトップの上に認証情報を抱えたバイナリを置くことになる。これはコストの判断ではない。

ハーネスを選ぶ権限がないチーム。セキュリティレビューや調達がすでにハーネスを指定しているなら、この実験の支配変数はあなたが触れる対象ではなく、論文の助言は愚痴に化ける。

6つのgit操作とは形の違うタスク。複数サービスをまたぐ長いオーケストレーション、承認の往復や対話的な確認がツール層に属するワークフロー。実験の範囲外だ。そこではインターフェースの選択は、コストの判断の服を着たユーザー体験の判断になる。

この反論を通り抜けて残るのは、gitにまったく依存しない部分だ。インターフェースの効果が最も見えやすいはずのタスクで、ハーネスがインターフェースを一桁分の差で上回った。そして完了は自己報告ではなく成果物で判定された。gitがインターフェース比較を仕込んだと信じるとしても、変数の順位付けを仕込んだわけではない。私の結論は範囲を狭めたうえで維持する。成熟したCLIが既にある作業なら、CLIだけのハーネスに統一する。それ以外の領域では、MCPを残したまま、それでもハーネスを先に直す。

## 本当のアーキテクチャの問いがある場所

二つのチームから、同じ依頼が違う服を着て届く。リニューアル側はエージェントにリポジトリ操作、ビルド、リントを回させたい。データ系はエージェントに会員データと同意データを読ませたい。私たちの反射的な答えは、どちらにも同じだった。MCPサーバーを立てる。

論文はこの反射を割ってくれるが、割れ目が何なのかを教えてくれたのは二番目の出典だった。

> The harness guides what an agent tries. The infrastructure controls what an agent can do. Both are necessary; only one is authoritative.

> — [Where Security Fits in an AI Agent Stack](https://developer.nvidia.com/blog/where-security-fits-in-an-ai-agent-stack)

MCPのプロセス、プラグイン、モデルが書いて動かすコードは、すべてハーネスの境界の内側で走る。改変されることを前提に設計された層が、自分自身への改変に対して統制を効かせられるわけがない。ここで問い全体の形が変わる。最初からMCP対CLIの話ではなかった。あるツール呼び出しの権限判定が、ハーネスの内側に座っているか外側に座っているか、という話だ。内側なら、作ったのは統制に見える案内であり、それは監査で統制として通る。通らなくなる日まで。

リポジトリ操作では、権限判定はすでに外側にある。gitのクレデンシャル、ブランチ保護のルール、CIのゲート。監査の痕跡はシェル履歴だ。ここにMCPサーバーを足せば、保守対象が一つ増えてハーネスの選択肢が狭まり、統制は一つも増えない。会員データと同意データでは、権限判定はやはりハーネスの外に置くしかない。つまりAPI境界とそこ自身のログであり、MCPやそれに類するものは搬送路として乗る。搬送路は統制ではない。私が潰してしまっていた区別はここだ。

## 入れるゲートは三つ

コツではない。ゲートだ。この種の気づきの典型的な失敗は、シニア一人が実践して他の誰も気づかないことだから。

一つ目はハーネスの単一化。チームごとに一種、バージョンを固定する。地味だが、これが知見の全部だ。ハーネスが浮いている間はどのコストレポートも読めず、どんなA/Bも意味を持たない。誰かがツールを上げるたびに、支配変数を測り直すことになる。

二つ目はツール登録の審査。新しいMCPサーバーを足すには、二つの問いに答える1ページを出してもらう。この作業に成熟したCLIはあるか。あるなら却下、それを使う。権限判定はハーネスの外にあるか。内側にあるなら、ツール定義に近づく前にインフラ層へ差し戻す。

三つ目は完了検証で、これが痛むと分かっている。うちのCIは、エージェント実行の結果をその実行自身の報告から集計している。論文はそれをやめた瞬間に結論が変わったのであって、同じ弱点が私たちのパイプラインに手つかずで残っている。完了は成果物の状態で判定する。リポジトリのdiff、テストの通過、スキーマ検証。

これに加えて、チームのダッシュボードに指標を一つ、一級として上げる。完了を伴わずに焼かれたトークンの比率だ。12.9パーセントと2.2パーセントの差が二つのインターフェースの実務上の違いの全部であり、それはまさに成功率のグラフが隠すものだ。今のレポートには、失敗に払った金額の行がない。

## CTOがここから持ち帰るもの

結論は「MCPをやめろ」ではない。あなたのコスト診断が一層下を狙っている、だ。

同一のモデルと同一のタスクで、スキャフォールディングを差し替えるだけで支出が5倍から28倍動き、小さなローカルモデルでは139倍動く。だとすれば、エージェント予算に対して使える最大のレバーはベンダー単価の交渉でもプロンプトのチューニングでもない。ハーネスの標準化だ。そして系として気持ちの悪い帰結がついてくる。各チームが好きなハーネスを選べる状態なら、チーム間のコスト分散は一桁の倍数まで広がり、その分散は財務レポート上ではモデル料金の変動として現れる。漏れを探す列を間違えることになる。

出荷速度も同じ方向を指す。しかもこちらの証拠は、この主張をする動機がないベンダーから出ている。

> Harness design can materially change results: on ARC-AGI-3, retained reasoning and context compaction raised GPT-5.6 Sol's score from 13.3% to 38.3% while reducing output tokens sixfold.

> — [Codex as a platform: build on the open agent harness](https://developers.openai.com/blog/codex-as-a-platform)

同じモデル。変えたのはハーネスだけ。スコアはほぼ3倍、出力トークンは6分の1。学術側と商用側という独立した二つの出典が、ほとんど誰も所有者になっていない層に収束している。

コンプライアンスは逆方向に切れるので、コストの議論に全部を運ばせずに明示しておきたい。権限判定をハーネスに置いた時点で、手にしているのは統制ではなく案内だ。監査に耐える強制はインフラ層に属する。これは、機微なシステムに対しては、コストが高くついても境界を切ったMCP経路を残す理由になる。倍率はその判断に対する反論にならない。

明日ひとつだけ変えるなら、エージェントのコストレポートの集計キーをモデル名からハーネス名に変えることだ。クエリの修正で済む。モデルのせいだと思っていた分散が本当にモデルの話だったのか、一日で分かる。

私の立場をはっきり書く。成熟したコマンドラインが既にある表面でのエージェント作業、gitやコンテナ、クラウドのツール群、ビルドチェーンについては、MCPはオーバーヘッドであり、私は接続しない。権限判定がファイルシステムの境界の外にある社内システムについては、残し、ハーネスを固定し、失敗分の予算を別に立てる。

私が間違っていたと示せるのはこういう結果だ。同じ比較を複数サービスにまたがる長いオーケストレーションのタスクで走らせ、実際に発火したツール呼び出しを検証し、スキャフォールディング間の広がりが一桁を大きく下回るまで縮み、インターフェース間の広がりが開くこと。そのときは支配変数は最初からタスクであって、私はgitから一般化していたことになる。

この論文が最も強く揺らしたのは、MCPの評判ではなかった。エージェントを、その本人の証言で採点するという習慣だ。この業界が測定と呼んでいるものの多くは、統制のない一回の実行に物語をつけたものであり、私もその何本かを書いている。
