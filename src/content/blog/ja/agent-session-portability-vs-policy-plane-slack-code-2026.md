コーディングエージェントのセッションを持ち運べることが、本当にベンダーロックインを減らすのか。それとも、将来の乗り換えを実際より簡単そうに見せているだけなのか。それを確かめたかった。実際の Claude Code セッションをひとつ凍結し、中身を検査し、session-migrate 0.8.0 で七つの移行先フォーマットへ転送した。会話とツールの文脈は驚くほどよく運べた。だが、組織の中でエージェントの作業を安全にしている統制は、まったく動かなかった。

この区別は経営判断に直結する。CTO が最適化すべきなのは、開発者のローカルな会話ログの可搬性ではなく、承認と監査の可搬性だ。

## 運用上の問題は、チャット履歴の置き場所ではない

リニューアル案件やデータ基盤の仕事では、いずれ同じ質問がエンジニアリングの責任者まで上がってくる。「三か月後、このエージェントがなぜその変更を入れたのかを、どこで見られるのか」。

危うい答えは、たいてい「どこかの開発者のローカルセッションファイルの中」だ。あるエンジニアは JSONL ファイルに文脈を持ち、別のエンジニアは断片を PR の説明に貼り付け、三人目はすでにローカルのエージェントディレクトリを掃除してしまっている。個人の実験なら許容できる。だが変更が認証、決済、会員データ、本番アクセスに触れるなら、これは運用上の欠陥だ。

逆向きのリスクもある。セッションファイルには本番ログの断片、スキーマの詳細、添付された成果物、ときには実データのサンプルまで入りうる。こうしたセッションファイルを別ベンダーのネイティブ形式に変換するコマンドは、単なる利便性の機能ではない。データが外に出る経路がもうひとつ増えるということだ。

だから私は、エージェントセッションの可搬性を開発者の生産性の話として扱わない。CLI の機能の顔をしたデータガバナンスの問題だと考えている。

Slack Code はセッション移行と正反対の方向を向いているのに、アーキテクチャとしては同じ結論に着地する。Slack の説明によれば、コーディングエージェントにメンションすると専用のコードチャンネルが作られ、関係者が集まり、コードの差分、計画ドキュメント、動く HTML プレビューが集約され、完了したチャンネルは検索可能な記録としてアーカイブされる。作業の恒久的な記録が、一台のワークステーションから共有の運用面へ移る。

> Slack Code は Slack 既存の権限と管理者コントロールを継承するため、IT 部門が新たな設定や監査を行う必要はありません。重要な変更はチャンネル内でそのまま担当者による迅速な承認フローに回すことができ、レビューの安心感を保ちながら自動化のスピードを実現します。
> [Slack Code: チームと AI エージェントが共に作り上げる場所](https://slack.com/intl/ja-jp/blog/news/slack-code-channels-for-agents)

製品の細かい仕様よりも、この継承のしかたのほうが重要だ。新しいエージェントのワークフローごとに IT 部門が権限と管理の面を組み直すのではなく、すでにある面をそのまま継承している。

## 移行テストが実際に保持したもの

session-migrate 0.8.0 を macOS の Python 3.12 仮想環境に入れた。README が掲げるサポート範囲は Python 3.11 以上と Linux だ。それでもインストールと起動は通った。公表されたサポート境界が変わるわけではないが、フォーマット変換を統制された条件で試すには足りた。

ソースは凍結した Claude Code セッションひとつ。341,646 バイト、90 レコード、tool-use ブロック 20、tool-result ブロック 20、thinking ブロック 11。凍結は必須の手順だった。最初の試行では、生きたセッションファイルが実行中に増え続け、移行先ごとに別の母集団と比較していたことになってしまった。

同じ凍結セッションを Codex、Pi、GitHub Copilot CLI、Qwen Code、Kimi Code、Muse Code、Mistral Vibe へ転送した。移行先のホームはそれぞれ `/tmp` 配下に隔離した。生成されたレコード数は 33 から 50 まで散らばった。この差は情報の保持量が大きく違うことを示すものではない。同じ内容を、フォーマットごとに異なる単位のレコードへ割っているだけだ。

意味があったのは損失マニフェストのほうだ。七つすべてで、ドロップ総数は 54 から 57 の狭い範囲に固まり、thinking のドロップ数は 9 で固定されていた。繰り返し落ちたのは、ソース側のメタデータレコード、ツール参照レコード、そして非公開の thinking だった。Codex はさらにセッションタイトルをひとつ落とし、Vibe は他の移行先が落としたツール参照レコードを二つ残した。

漠然とした互換性の主張より、このパターンのほうが役に立つ。移行先を変えても損失はほとんど変わらない。中間モデルに何が入りうるかを決めていたのは、ソースセッションが持つイベントの語彙だった。

プロジェクト自身は変換経路をこう説明している。

> native session → validated event timeline → native target → resume
> [session-migrate — Migrate your sessions to any harness](https://github.com/xhluca/session-migrate)

この中間のタイムラインは意図的に小さい。順序付きの会話イベントは通れるが、クライアント側に常駐する設定は通れない。ソースセッションには手を触れず、省略や変換は中身を含まないマニフェストとして件数で報告される。

## ロックインの境界は会話ログではなくポリシープレーンにある

この移行ツールは 12 のハーネス形式に対応し、同一形式への可搬な書き直しを含めて 144 の経路を数える。どの経路でもユーザーとアシスタントのメッセージは順序を保って残る。移行と名乗るだけのプレーンテキスト書き出しではなく、実質的な可搬性がある。

> Every listed format can be a source or target: 144 ordered routes, including same-format portable rewrites.
> [session-migrate README — Compatibility](https://raw.githubusercontent.com/xhluca/session-migrate/main/README.md)

ところが、同じ互換性ドキュメントが決定的な限界も書いている。

> Auth, hooks, policies, MCP, and runtime config | No | These remain with the source client
> [session-migrate — Migrate your sessions to any harness](https://github.com/xhluca/session-migrate)

経営層がベンダーとの交渉で使うべきなのは、このアーキテクチャ上の事実だ。チームは作業の経緯、ツール呼び出し、使える文脈の大半を移せる。だがセッションファイルを移しただけでは、強制力を持つ実行環境は移せない。

認証はクライアントに紐づいたままだ。フックもクライアントに残る。ポリシー設定、MCP 接続、ランタイム設定も同じくクライアントに残る。移行先の選択を誤ったから欠けたのではない。それらは最初から、運べるイベントタイムラインの一部ではなかった。

Antigravity と Cursor への変換が失敗したことも、同じ境界を裏づけた。どちらのアダプタも即座にネイティブ実行ファイル、`agy` と `cursor-agent` を要求した。今回の環境にはどちらも入れていない。この二つは独立したファイル変換器ではなく、クライアントに接続する仕組みだ。書き出したセッションだけでは再構成できないネイティブな状態があるからそうなる。

個人開発者ならこれで困らないかもしれない。組織にとっては、乗り換えの本当のコストが、新しいハーネス上でアクセスの対応関係、フック、ポリシー、承認済みのツール接続を作り直す作業だという意味になる。

## いちばん強い反論は、狭いが重要な範囲で正しい

最も強い反論は、乗り換えの本当のコストはセッションの文脈だというものだ。この反論は、ふだん受け流されているより丁寧に検討するに値する。

長期の実装セッションをひとつ抱えたまま道具を替えていく開発者にとって、文脈の再構成は高くつく。今回のテストもその見方を支持する。ソースセッションの順序付きの会話、ツール呼び出しの履歴、ツール結果の履歴は捨てられていなかった。空のプロンプトから始め直すのではなく、作業の経緯を保ったまま移る現実的な経路がある。

規制の外にいる個人や、ハーネスを頻繁に替え、承認記録を集約する必要がない小さなチームでは、この価値はとくに大きい。そういう環境なら 144 の経路はマーケティング用の数字ではない。試行の摩擦を減らし、積み上げた文脈を守ってくれる。

ポリシーが移らないからセッション移行は無意味だ、と言うのは間違いだ。セッションは継続性の資産として実際に価値がある。

それでも、その範囲の外では私の判断は変わらない。移行されたセッションは、元のクライアントの認証、フック、ポリシー、MCP 接続、ランタイム設定を欠いたまま再開する。監査対象のシステムを扱うチームにとって、安全側の統制は作業を取り巻く付随的な文脈ではない。作業そのものの一部だ。

関わる人数、リポジトリ、環境、規制上の制約が増えるほど、節約できたセッション文脈が経済性を支配する度合いは下がる。ポリシー統制の再構築、権限の検証、承認経路の証明、新しいデータ書き出し経路のレビューが、移行の予算を食い潰していく。

## セッションは使い捨て、ガバナンスは持続させる

私が薦める運用モデルには関門が三つある。

第一に、セッションはキャッシュであって記録の正本ではないと宣言する。判断、根拠、切り戻し手順は PR 本文か承認済みの作業チャンネル、あるいはその両方に存在しなければならない。レビューのチェックリストに一行足す。「この判断の根拠は、エージェントのセッションの外側で参照できるか」。

小さな一行に見えるが、行動が変わる。詳細な会話が入っているというだけの理由で、ローカルの会話ログを監査の証跡として扱う癖を止められる。会話ログはノートパソコンの交換、担当者の退職、ローカルのエージェントディレクトリの定期的な掃除で消える。

第二に、監査対象のリポジトリでは書き出しのレビューを必須にする。セッション移行が必要になったら、書き出しの前にドライランの移行マニフェストを作業チケットに添付する。省略の分類と件数だけを報告する、中身を含まないマニフェストは、生のセッションダンプよりレビューに向いている。レビュアーは、何が出ていき何が失われるかを、中身を別の読み手に広げずに判断できる。

第三に、承認、アクセス、アーカイブの強制点をひとつに決める。チャンネルか CI か。既定で両方にはしないし、エージェントの CLI ごとに別々の強制モデルを持たせもしない。コードオーナーと CI による承認統制がすでに効いているチームが、エージェント製品にその機能があるからというだけの理由でチャット上の承認をもうひとつ足すべきではない。承認の面が二つあると、どちらの決定が正なのかが曖昧になる。

オンボーディングの説明はそっけなくていい。仕事がはかどる CLI を選べばいい、ただし承認はここで行い、記録はここに残る、と。

これならローカルの道具の選択の自由を守りながら、その選択がガバナンスを分断することを防げる。

## Slack Code はエージェント連携ではなくポリシープレーンの製品だ

Slack Code は Claude、Devin、GitHub Copilot、Vercel との連携を使うチームで利用でき、ChatGPT は今後対応と説明されている。この製品の約束は、どのエージェントも同じように考え同じように状態を保存する、ということではない。共有チャンネルから作業を始められ、組織にすでにある Slack の統制をそのまま継承できる、という点にある。

コードチャンネルの 70% 以上がアイデアから PR のマージまで一日で完了するという公式の主張は、ベンダーの参考値として扱うのが妥当だ。Slack は方法論も母集団も測定期間も公開していない。これ単独で事業判断の根拠にはならない。

それでも、ワークフローの設計としては戦略的に筋が通っている。プロダクト、デザイン、エンジニアリング、運用が同じ依頼を見て、同じ成果物をレビューし、結果として何が決まったかを見られる。誰も開発者のローカルなハーネスに入る必要がない。エージェントのバックエンドが替わっても、チャンネルは人間の承認境界のアーカイブとして残りうる。

Slack はエージェントの推論過程の可視化についても、リリース済みの機能ではなく今後の課題として説明している。これは session-migrate が非公開の thinking や署名付きのトレースを意図的に落としているのと符合する。エージェントの作業のうち、いちばん説明を必要とする部分が、構造的にいちばん運べない。モデル提供者に縛られているからだ。

だから現実的な監査対象は、もっと狭く、そのぶん信頼できる。何が依頼され、何が変わり、どの根拠がレビューされ、誰が承認したか。

## CEO と CTO が乗り換えコストのモデルに入れるべきもの

エージェントのベンダー乗り換えコストを、セッション履歴を書き出せるかどうかで見積もってはいけない。実態よりはるかに安い数字が出る。

正しいモデルが問うのは、強制力を持つ面が組織のハーネスの外側に存在するかどうかだ。

- CLI を入れ替えても承認ルールは生き残るか
- アクセスと MCP 接続を、中央で管理している設定から再構築できるか
- 監査担当者が、開発者のローカルセッションを読まずに判断の根拠と承認記録にたどり着けるか
- ひとつの管理面から、アクセスの剥奪やワークフローの停止ができるか
- セッションを動かしたとき、どのデータが出ていくのかを組織として評価できるか

答えが「はい」なら、エージェントのハーネスは差し替え可能な実行ツールに近づく。交渉力が上がる。モデルや CLI を替えるたびにガバナンスを作り直す必要がないから、調達は価格、品質、連携でベンダーに圧力をかけられる。

答えが「いいえ」なら、そのベンダーが握っているのはインターフェースだけではない。埋め込まれた承認ロジック、アクセスのパターン、運用上の記憶までを握っている。置き換えが開発者の不便ではなく組織のリスクになるから、価格を規律づけるのは格段に難しくなる。

エージェントの利用が増えていくとき、どこに投資すべきかもここではっきりする。ライセンスを買い足せば活動量は増える。監査の面の処理能力と明瞭さを上げれば、組織のほうが伸びる。エージェント導入が、誰もレビューできないローカル自動化の寄せ集めに終わらずに済むのは後者だ。

## この提言が当てはまらないところ

Slack を中心に据えた強制モデルは、Slack が協業の標準になっていないチームには合わない。原則そのものは有効だが、ポリシープレーンは組織が実際に使っている共有ワークフローの上に実装しなければならない。

CI とコードオーナーですでに承認が効いているチームにも合わない。チャンネルを第二の承認権限として足すと、証跡が分かれて、かえって悪くなる。

会話ログをサードパーティの SaaS に保持することを禁じられている組織には、別のアーカイブ設計が要る。一日のエージェント依頼が数件しかないチームでは、自動生成されるチャンネルが運用上の価値よりアーカイブの手間を増やすかもしれない。そして非公開の推論トレースを監査証拠として要求するチームは、可搬なセッションもチャンネルのアーカイブも、いまのところその要求を満たさないと理解しておいたほうがいい。

私の立場ははっきりしている。セッション移行は個人の継続性のための道具として使えばいい。ただし、それをチームのガバナンス標準に格上げしてはいけない。承認、監査、アーカイブ、権限剥奪は、道具に依存しない強制点ひとつに置く。この立場を変えるとすれば、セッション形式が会話と並べて、可搬で中央から検証できるポリシーとアイデンティティの状態を運ぶようになったときだ。
