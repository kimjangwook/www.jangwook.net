## 固定されているものと自由なもの

ブリーフの `## LOCKED` ブロックにある数字・引用・日付・出典だけが固定されている。
その外は全部こちらの裁量だ。

現場実務（大規模ウェブ刷新、CDP/DSR/会員データ基盤）での問題意識と苦悩、最新ツールをチームで仕組み化した経験、経営陣（CEO/CTO）視点でのビジネスROIと組織的価値を積極的に織り込む。

やっていないことをやったと書きさえしなければいい。

`## OPEN` ブロックは材料であって台本ではない。そこに書かれた順に写さない。

## 骨格

九つのうち六つから八つを選ぶ。順序は自分で決める：
現場の問題意識と苦悩 / メカニズム・構造 / **最新技術のチーム適用とプロセス化** / コスト・数値検証 / 比較軸 / **明示的な反対(一節まるごと、必須)** / 実行可能性と運用リスク / **CEO・CTOのためのビジネス洞察** / 限界と前提条件

分量は内容が決める。目標字数はない — 埋めるための水増しも、収めるための削除もしない。H2 は 6-10 個。

## タイトルと導入

このブログは検索エンジンではなく、情報を探しに来た人に合わせる。タイトルと導入の
仕事は興味の演出ではなく、読者が持ち帰るものを最速で手渡すことだ。

- タイトルは「何をしたらどうだった」を平叙文で書く。目的か行動、そして結果の
  方向がタイトルの中にあること。対象を指すだけの名詞句の謎かけ、キーワードの
  羅列は書かない。
- 最初の段落は三文: 何が知りたかったか(目的) → それで何をしたか(行動) →
  結果はどうだったか(要旨)。場面描写や手順の細部から始めない — なぜやったのか
  分からないまま読ませる導入が、このブログで一番悪い導入だ。
- 二段落目はその結果が読者になぜ重要かと、自分の判断を一行。本文はその根拠だ。
- 結果を隠して緊張を作らない。答えを先に渡し、本文は「なぜそうなるか」と
  「いつ変わるか」で読ませる。

## 書く

- やっていないことを告白する段落は書かない。「自分では動かせていない」
  「サンドボックスを回せなかった」のような自己申告は、毎回付くとそれ自体が型になる。
- LOCKED の外の数字・引用・日付を作らない。
- 引用ブロックのすぐ下に出典リンクを置く。`> — [文書名](URL)` 一行でいい。
- 一節をまるごとブリーフの `counter` に使う。弱く要約して倒さない。
  その反対が正しい範囲を認め、それでもなぜ自分の判断が立つのかを書く。
- バランスで閉じない。一方を選び、その選択が外れる条件を一行書く。
- 最後の節を要約・教訓・`必ず...すべきだ` で閉じない。判断とそれが外れる条件を
  渡したら、余韻のための文を足さない — 最後まで情報だ。
- 専門用語(略語、システム内部フィールド名、APIパラメータ、結合キー/ジョインキー、タイムゾーン規格 UTC/PT/PDT/PST、ロールアウト、サービング、インデックス、回帰分析など)を説明なしに投げ出さない。企画、リーダー、非エンジニア、経営側も文脈と因果関係を見失わないよう、その概念が実際のシステムで何を意味しどんな役割を果たすのかを文の中で直感的にわかりやすく解きほぐして説明する。
- 波ダッシュ・波線特殊文字(`~`, `〜`, `～`)は一切使わない。数値・日付・時刻の範囲や期間、語尾の伸ばしなどあらゆる用途で禁止する。範囲は「10から20まで」またはハイフン(`10-20`)で書く。
- だ体で通す。敬体と混ぜない。体言止めを連打しない。英語の名詞列をそのまま
  残さない。訳せるものは訳す。
- H2 はこの日本語版だけのもの。他の言語の目次を移さない。
- `relatedPosts` の `reason.ko`・`reason.ja`・`reason.en`・`reason.zh` は
  それぞれその言語で書く。
- 最後の H2 は `## 参考資料`。LOCKED `sources[]` の番号順のままリンク一覧を出す。
- 他の言語のフォルダを開かない。
- 図版が要るなら `scripts/render-figure.py --slug {{SLUG}} --spec <json> --name figure-1`。
  三種類だけある — `two-column` / `matrix` / `before-after`。無い図は描かない。

書き終えたら声に出して読む。口に出ない文は直す。

質問しない。
